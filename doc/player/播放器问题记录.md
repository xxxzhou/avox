# 播放器问题记录

记录播放器在实际使用中遇到的问题、原因与处理逻辑，涵盖音视频同步、硬解 NALU 格式适配、视频包拆分合并等。
问题独立成节，按遇到顺序整理，持续补充。

## AI 维护

每节保持精简：问题描述 ≤2 行，原因/解决方法 ≤2 行，代码片段 ≤10 行。只留定位问题的关键信号与落点，不展开推导。

## 问题一：音视频时间基不同（起点 PTS 不一致）

音视频首包 PTS 起点不一致，例如视频从 100 开始、音频从 10000 开始，两条轨道活在各自的时间基里。
播放器在 `syncPts` 时分别取双方 `basePts` 比较，起点不同即关闭同步，任由音视频按自身时钟推进。

> `src/avox/player/MediaPlayer.cpp` — `cmdSyncPts`

```cpp
ioStatus.baseVideoMs = ioSource->getBaseTime(TrackType::video);
ioStatus.baseAudioMs = ioSource->getBaseTime(TrackType::audio);
// 视频与音频起点PTS不同(如视频100、音频10000)，时间基不一致
if ((ioStatus.videoCount > 0 && ioStatus.audioCount > 0) &&
    (ioStatus.baseVideoMs != ioStatus.baseAudioMs)) {
  closeSync(true);   // 起点不同，关闭同步
} else {
  closeSync(false);  // 起点相同，要求同步
}
```

## 问题二：音频 PTS 是视频的 9~11 倍（采样率未换算）

音频 PTS 生成时采样率未正确换算（疑似把采样数直接当作毫秒），导致音频 PTS 数值约为视频的 9~11 倍。
播放器比较两条轨道 IO 包的 PTS 差，差异远超缓冲阈值即判为不对齐、关闭同步，并恢复 1.0x 速度。

> `src/avox/player/MediaPlayer.cpp` — `collectStatus`（`ioTime` 来自 `AVTrack.cpp: queueStatus.ioTime = data.pts`）

```cpp
// ioTime 为 IO 线程插入包的 PTS；音频PTS若为视频9~11倍，ioDiff会远超delayMs
int64_t ioDiff = std::abs(audioStatus.ioTime - videoStatus.ioTime);
if (ioDiff > delayMs * 2) {
  bAVAlign = false;  // 不对齐：恢复1.0x，停止变速追赶
  if (cspeed == 1.0 && clock->getSpeed() != 1.0) {
    setSpeed(1.0);
  }
}
// 同步状态切换：不对齐→关闭同步，重新对齐→恢复同步
if ((!bAVAlign && syncType != SyncType::none) ||
    (bAVAlign && syncType == SyncType::none &&
     preSyncType != SyncType::none)) {
  closeSync(!bAVAlign);
}
```

## 问题三：不同平台硬解需要不同的 NALU 格式

iOS VideoToolbox 要 avcc/hvcc（4 字节长度前缀），Android MediaCodec 要 annexb（`00 00 00 01` 起始码），FFmpeg 只要 extradata 与后续包格式一致即可。
进包格式由首个配置帧探测（`checkAvccPacket` → `bvcc`），`decoderImp` 按目标平台互转：MAC 把 annexb 转 avcc/hvcc，Android 把 avcc 转 annexb。

> `src/avox/video/VideoDecoder.cpp` — `decoderImp`（探测见 `pushConfig`）

```cpp
// ffmpeg 只需 extradata 与包格式一致；MAC 原生解码要 avcc/hvcc，android 要 annexb
// 进包格式由首包探测：bvcc = checkAvccPacket(...)
if (bMustVcc && !bvcc) {            // iOS/MAC：annexb → avcc/hvcc
  splitAnnexbNalu(vdata, spiltBufs);
  for (auto& buf : spiltBufs) { annexb2AvccPacket(buf); }
}
if (bMustAnnexb && bvcc) {          // android：avcc → annexb
  splitAvccNalu(vdata, spiltBufs);
  for (auto& buf : spiltBufs) { avcc2AnnexbPacket(buf); }
}
```

## 问题四：配置帧 / I 帧的拆分与合并

IO 来的包结构不可控：配置帧（SPS/PPS/VPS）常与 I 帧合在一个包里，也可能一个包塞多个 I 帧分片；zlmediakit 还会把大 I 帧拆成多个包。
处理顺序是先拆后合：`splitNalu` 打散成单个 NALU，配置帧单独记录（`updateConfig`）、I 帧前补发，同一帧的分片按"是否新帧"拼回去；zlm 侧另用 `mk_frame_merger` 先把同一 AU 合并。

> `src/avox/source/AVSource.cpp` — `processVideo`（zlm 合并见 `src/avox_zlmediakit/IOParseZM.cpp` `mk_frame_merger_create(1)`）

```cpp
// 先拆成单个 NALU：配置帧+I帧、多I帧分片都先打散
if (bvcc) { splitAvccNalu(packet, spiltBufs); }
else      { splitAnnexbNalu(packet, spiltBufs); }
// 拆出多个时按"是否新帧"重新合并，同一帧的分片拼回去
if (spiltBufs.size() > 1) {
  for (auto& buf : spiltBufs) {
    bool bNew = naluNewFrame(vcodecId, buf.data.data + buf.prefixSize);
    if (bNew) { combineBufs.push_back(buf); }            // 新帧起头
    else if (!combineBufs.empty()) {
      combineBufs.back().data.size += buf.data.size;     // 分片拼回上一帧
    }
  }
  for (auto& buf : combineBufs) { singleVideo(buf); }    // 配置帧在此记录、I帧前补发
}
```

## 问题五：音频 PTS 跨度大于实际数据时长（主时钟被拉快，playing↔buffering 循环）

音视频 PTS 量级一致、`ioDiff` 正常看似对齐，但音频 PTS 推进约为实际数据时长的 2 倍（AAC 1024@16kHz 应 64ms/帧，实测 ~120ms）。
以音频为主时钟→主时钟被带成 ~2x→渲染 2x 消费、IO 1x 补充→缓冲见底→`playing↔buffering` 循环（VLC 同遭殃：日志狂报 `picture too late` / `playback way too early`，靠插入静音样本 + 重采样补缺口而非变速）。

"PTS 跨度 ≠ 数据时长"是二义、单凭音频分不开：A=PTS 错（可重打戳）/ B=数据少（重打戳会把丢帧变 2x 变速，绝不能）；本例 `ioDiff` 正常反而更偏 B，故一律不重打戳。
现状：检测到错配即关同步各播各的。⚠️反向（数据>PTS）直播下会反压 IO、堵死 socket，比"数据少"更危险，暂无对策。

> `src/avox/player/AudioTrack.cpp` — `onDecode`（错配经 `matchPtsData()` 回 `collectStatus` 关同步）

```cpp
checkDataSize += size;
if (spts - checkPts > checkInterval) {                      // PTS 推过 2000ms 结算
  int32_t intervalMs = checkDataSize * frameMs / frameSize; // 累计数据折合毫秒
  bCheckfail = intervalMs > checkInterval * 1.5 ||
               intervalMs < checkInterval * 0.7;            // 偏离跨度 ±30% 即错配
  startCheck = false;
}
```
