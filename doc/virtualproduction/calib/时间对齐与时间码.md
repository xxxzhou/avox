# 时间对齐与时间码

> 整理自 aocec 仓库 `doc/virtualproduction/时间对齐.md`、`时间码.md` 及《摄像机校正程序开发》中时间码相关段落, 2026-09 同步合并。

## 时间码

[深入聊聊时间码](https://zhuanlan.zhihu.com/p/101728723) 时间码一般以如下形式(时:分:秒:帧)显示, 时码一般与以下几个对象关联: 帧数、时间戳、帧率。

时码与帧率一起, 可以推算出帧数与对应时间; 同样知道帧率, 帧数与时间这二者之一都可以推断出时间码。

### 丢帧时间码

丢帧时间码一般对应 30/60, 如正常 30 帧对应一小时有 108,000 帧, 但是在 29.97 丢帧时间码下, 一小时只有 107,892 帧。

### 实现相关坑

- 时码、帧数、时间戳、帧率相关逻辑与方法参照 UE4 设计, 主要是丢帧时间码的逻辑处理。
- Redspy 得到时间码的功能参照先壤完成。
- BMD(DeckLink)采集卡得到时间码: 先壤实现太迂回; UE4 里该功能是封闭动态库提供的; 最终参照网上相关逻辑自行实现。
- **Redspy 时码去重**: Redspy 以 double 发送时间码, 同一时码会出现两次, 如 `00:01:22:00,00:01:22:00,00:01:22:01,00:01:22:01`。

## 时间对齐

假定相机、追踪器都是硬件, 导致有可能丢帧, 或是延迟的情况, 或是只有一方有时码, 如何对齐这些数据?

在固定帧率下, 来的数据与固定频率偏差不大的情况, 如是 25fps, 那么正常间隔大约是 0,40,80,120,160 这样, 实际大约是 0,33,90,110,170 这种。

### 延迟对齐实现要点 (源自《XR演播技术整理》)

Track 发出数据影响虚拟相机的姿态, 对应的现实相机的姿态变化, 这二者会有一个延迟, 导致移动时混合显示二者的图像不匹配。

- 延迟对齐要求硬件以固定的帧率匹配的间隔发出, 现实情况下一般有各种问题, 需要检测帧率不匹配的情况; 延迟需要队列 Buffer 保存帧信息。
- 相机是图像源, Track 是变换矩阵, 在队列延迟上的逻辑大致相同。不同之处: 图像源数据一般只分配一个空间不断更新, 入队需要复制内存; Track 的变换矩阵直接放入队列即可。二者可能不是帧间整对齐, 需要支持数据平滑——图像的平滑比较复杂, Track 的平滑比较容易, 需分别处理。
- 实现上针对之前的图像帧/Track 姿态回调 Observer 扩展子类, 在子类中扩展延迟对齐功能, 能根据 flag 自动切换正常模式与延迟对齐模式(aoce 对应 `AoceDelaySync`, avox 对应标定方案 M3 的 `ITrackSource` + 延迟对齐线程)。
- 现场遗留问题: 快速转动时融合效果仍不太行, 测试的相机没有 genlock 锁功能, 不确定是否是这个影响, 仅供参考。
