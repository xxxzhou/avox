## 起源与 HTV Vive Tracker 验证

2021 年末, 看到手眼标定算法, 看原理是可以解决虚拟制片中求得摄像机与追踪器的偏移的, 于是根据算法相关流程, 封装了 opencv 相关算法, 包含求内参, 摄像机与追踪器的偏移的相关实现在 aoce_opencv 里。

来年开始继续完善, 整合 decklink 采集卡, aoce 的 C++ 层与 C# SharpDX 采集画面展示功能, 都还算比较顺利, 然后到现场看过 Redspy 才发现一个问题, Redspy 给的旋转是欧拉角, 以及当时 Redspy 的坐标系与 OpenCV 不同, 需要转换同坐标系计算(需要指出, 后面发现在手眼标定算法这步里是不需要转化的)。

在完成相关坐标系变换库后, 又去坪山测试了下, 效果还是差, 又发现个问题, Redspy 提供的位移与现实尺寸有个不知道的缩放值, 而这个缩放值导致结果特别差。发现测试太麻烦, 于是加了个功能, 可以序列化手眼标定算法中间的姿态/图像, 这样就可以保存数据然后没有设备也能用这数据提供计算查看结果。

后来深圳疫情封控期间, 一直得不到正常结果, 都怀疑这算法有问题了。先验证了坐标系变换/旋转各项与 UE4 里同样功能各种数值比较, 再用手眼标定算法提供随机量生成验证数据, 然后计算结果与随机量比较, 这些都很正常。在锐哥提示下, 用 HTC Vive Tracker 验证了, 发现得到比较好的结果, 总算看到结果了。于是结合 HTC Vive Tracker 把当时算法流程及界面仔细完善, 最后开始解决缩放: 查看 Redspy 数据时发现一个现象, 虽然给的结果误差很大, 但是感觉计算出来的位移在 XYZ 上的比例是对的, 后面把手眼标定的算法看了, 才想明白是什么原因, 因为那个缩放当时比较大, 而摄像机与 track 的偏移造成的影响就很少, 导致算出来的结果从比例来说是对的。后面仔细查看算法原理, 加了个 Scale 参数进去一样使等式成立, 详见《[手眼标定算法改进](手眼标定算法改进.md)》。

改进手眼标定算法, 验证 HTC Vive Tracker 把相应值位移缩放后与求解的结果比对是正确的, 认为Redspy 求解马上要解决了, 其间还顺带把 LED 幕墙的标定也写完了。但再次到坪山测试, 结果还是不对。

## Redspy 结果不对问题解决 (欧拉角 Y/Z 取负)

期间在 4A 搭了个 Redspy 环境, 验证并解决各种猜想, 加上先壤与腾讯合同的虚拟制片工具源码来了, 验证其中一些坑的解决方法。不出意外, 他们摄像机与追踪器偏移也是用的手眼标定, 与我们求追踪器与现实世界的缩放思路都一样, 就更奇怪了, 为啥得不到好的结果。

参照先壤源码, 改进了计算误差的方式: 原来是计算映射后的摄像机姿态与平均姿态的差别, 后改为使用 SVD 求解出 Track 坐标系到标定板坐标反转换的最优解, 然后再反推出摄像机相对标定板姿态, 并把原三维点通过 projectPoints 映射二维 UV 后与根据图片找到的角点亚像素精确二维 UV 比较像素级别上的差异。后面请锐哥在 4A 用先壤的标定工程演示下完整过程, 发现其最后验证选择结果和想象的不一样, 最后是组合已有数据所有排列组合, 选择一个最好的, 不同于只选择排除一个再计算的组合, 这明显是不信任任何一个数据, 只相信结果更好的数据, 确实更科学。重新实现了结果验证逻辑, 效果确实提升明显, 误差从上万可以达到几百了, 但和现场要求的精度还差得远。

4 月 18 号, 上午还在工位考虑这问题的时候, 忽然想到一个问题: HTC Vive Tracker 为什么可以, Redspy 不行? 从表现上来说, Redspy 的精度比 HTC Vive Tracker 要高不少, 后面过程如果都验证没问题的话, 那有一步还是有差别的。HTC Vive Tracker 的 SDK 直接发给开发者的就是 4x4 的矩阵, 而 Redspy 只有欧拉角与位移, 如果欧拉角转旋转矩阵这步有问题, 那是不是无论后面怎么测, 都不行。于是午睡后, 直接到 4A 测试, 发现同样位置, 算出的 Redspy 旋转矩阵和预期不一样。比较先壤的矩阵计算方法, 没有问题, 最后查才发现**先壤把 Redspy 给的 YZ 旋转角度取负值**。用 Redspy 测试了下, 先确定对应的 XYZ 轴各方向, 根据所定方向用右手法则测试了下 XYZ 各个旋转方向与给的数值, YZ 真的是给的反值。改了后, 重新校准一次外参, 然后开始标定摄像机与追踪器的偏移, 测试多次, 一般来说, 取 8 组数据, 算的结果就直接在 10 个像素偏移以内, 算是可以现场使用了。

> 这是最重要的一个坑: Redspy 欧拉角 Y/Roll(Z) 与 Y/Pan(Y) 分量取负值才是真实旋转方向, 不处理则手眼结果完全错误, 曾为此排查数月。

## 结果传递给 UE4 (放弃先壤格式的教训)

最开始的想法, 是把自己的结果导成先壤格式, 还是让先壤发送, 这样比较简单与快。在经过很久的折磨后(其间把先壤的标定算法仔细研究)后, 还是决定放弃。主要中间有个问题: 先壤把 OpenCV 坐标系转 Track 坐标系是非基坐标系变换。为什么不这样做? 其实是后面手眼标定要用到这矩阵的逆, 基坐标变换是 TA^T 形式, 这个逆了会很麻烦, 所以先壤用了另外一种, 直接把 Redspy 姿态由 X 轴转了 180 度, 和 OpenCV 重合了。这样做有没问题? 至少先壤可以使用这个结果得到一套逻辑自洽的结果, 但是要把我们的结果转成他这中间做了特殊转化得到的结果, 尝试了很多次, 没找到解决方法。在这必须要说下, **手眼标定并不管标定板相对摄像机的坐标系**, 这个坐标系不管你怎么设, 最后手眼标定得到的结果(摄像机相对 Track 的姿态)都是在 Track 的坐标系下的, 但是做了这个特殊转化后, 这个结果就不成立了。

后面自己看了下他的发送相关逻辑, 经过 C# 已用的库, 加上更简洁的使用方法, 一天就完成了并发送 UE4 验证得到正常的结果。原来看着简单的方法更麻烦, 而看着麻烦的方法更简单。

然后去坪山验证了下, 结果很奇怪, 原点对上了, 旋转差了几十度, 后面才发现, 把第一块屏幕当成 1 传入计算, 实际应该是 0(从零开始计数)。

## 序列化结果精度不高

一个现象: 刚计算的结果明明好好的, 关闭程序保存结果, 然后打开程序, 反序列化结果后再次使用, 像素误差偏移从三点多直接到十点多了。

分析: Redspy 原始数据是欧拉角, 当时多方面考虑, 姿态使用 4float 的轴角/3float 的位移表示, 轴角相对欧拉角来说没有万向锁的问题, 能精确表示一个旋转, 相对四元数来说人更好理解。故最后结果两个 4x4 矩阵转化成 4float 轴角/3float 位移序列化, 反序列化时再转回 4x4 矩阵, 怀疑是这个过程精度丢失。

得到摄像机相对 UE4 坐标的链路: 矩阵1 现实摄像机相对 Track 变换 → 姿态2 Track 在自身坐标系下姿态 → 矩阵3 Track 坐标系到 LED 坐标系变换(根据 LED 标定时, 可以直接把 LED 坐标系对应 UE4 坐标系)。

经测试分析, 3x3 矩阵转四元数/轴角再转回来会有非常少的变化, 初步认为是 3x3 矩阵转四元数/轴角会因为求反平均根这步引入误差; 本身姿态问题不大, 关键是经过三个矩阵相乘的细小偏移累积后, 还投射到屏幕上, 非常细小的偏移就会造成在 LED 屏上有几个像素的偏移, 这是不能接受的。

改进两步:
1. 数学库把原来相关向量类使用 float 表示、中间计算用 double 的方式全改成泛型化类与方法, 这样原来一些模块还是继续用 float, 而在标定模块全用 double。
2. 序列化后的结果旋转用 3x3 矩阵表示。

这两步后, 序列化的结果再次使用, 感觉不到在屏幕上的偏移误差了。

## 高效率图像展示

最开始图像采集后使用 OpenCV 的图像处理并展示, 1080P 分辨率下 CPU 占用高, 刷新慢。改版后使用 vulkan compute shader 处理 YUV 转 RGBA 并直接对接 WinForm 的 DX11 窗口, 中间不经过内存, 直接对接 Vulkan/DX11 纹理, 并使用游戏方式高帧率刷新窗口, 保证非常低的 CPU 占用显示高清实时图像, 并且后续每帧在图像上超过上千点精准展示都可以动态添加 vulkan compute shader 滤镜层。

## 时间码相关坑

基本类时码、帧数、时间戳、帧率相关逻辑与方法参照 UE4 设计, 主要是丢帧时间码的逻辑处理(详见《[时间对齐与时间码](时间对齐与时间码.md)》)。

- Redspy 得到时间码的功能参照先壤完成。
- BMD 采集卡得到时间码的功能先壤写得太迂回, 想参照 UE4 的, 发现 UE4 里把这功能是以封闭的动态链接库提供的, 最后参照网上相关逻辑自己实现。
- Redspy 以 double 发送时间码, 会出现同样的时码二次, 如 `00:01:22:00,00:01:22:00,00:01:22:01,00:01:22:01`, 需要去重。
