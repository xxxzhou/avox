# 虚拟制片的相机标定方案

## 相机标定做啥


简单来说,虚拟制片通过标定,能把绑定在相机上的Track给出的姿态数据,转换成虚拟空间(如UE4)下对应摄像机的姿态.

[标定代码](../../code/aoce_opencv/)

## 标定流程总结

在摄像机与Track绑定在一起,满足钢体关系,分别在N个不同位置下方向下,同时拍摄角点图案与记录追踪器数据,得到N组数据(一组数据包含拍摄画面与追踪器数据),根据其N组数据里的画面先得到摄像机内参,然后根据内参与画面得到摄像机在幕墙坐标系下姿态,根据手眼标定算法,在钢体关系下,N(大于4)组(摄像机在幕墙坐标系下姿态)与(追踪器在追踪器坐标下姿态),可得到(摄像机相对追踪器在追踪器空间下的4x4偏移矩阵).

在虚拟制片中,我们还需要知道(幕墙坐标系到追踪器坐标系)的4x4的转换矩阵,根据其关系有摄像机在幕墙坐标系A(4N,4)x幕墙坐标系到追踪器坐标系X(4,4)=摄像机到追踪器坐标系B(4N,4).其A表示根据N次拍摄图使用PNP得到(摄像机在幕墙坐标系的4x4矩阵).而B对应的是N次(摄像机相对追踪器偏移矩阵[手眼标定求])*(追踪器在追踪器坐标系)而得到的(摄像机到追踪器坐标系的N个4x4矩阵).这样A与B都算已知的.根据关系AxX=B,A/B都是(4N,4)的矩阵,N表示拍摄图片/记录追踪器姿态的次数,根据SVD算法求得X(幕墙坐标系到追踪器坐标系),依据SVD算法性质,其X满足N组A与B关系的最优解.

根据(摄像机相对追踪器偏移)x(追踪器在追踪器坐标系)x(追踪器坐标系到幕墙坐标系)=(摄像机在幕墙坐标系姿态).这样屏幕不需要打印角点图,也能根据(追踪器在追踪器坐标系姿态)得到(摄像机在幕墙坐标系姿态)了.

如何确定求得二个(摄像机相对追踪器偏移)(追踪器坐标系到幕墙坐标系)矩阵结果好坏?首先根据拍摄图使用PNP得到摄像机在幕墙坐标系姿态,这个我们当做真实的值,而根据(摄像机相对追踪器偏移)x(追踪器在追踪器坐标系)x(追踪器坐标系到幕墙坐标系)=(摄像机在幕墙坐标系姿态)我们得到是计算值,直接比较姿态的误差,不太好评价,故我们会把角点三维坐标通过方法cv::projectPoints映射到画面中,比较与真实角点UV在像素上的误差,这样对于人眼更直观,评价也更科学.

## 坐标系变换

首先左右坐标系,本质上Z轴方向不一样,比如右手大拇指向右,食指向上,其余手指向你的眼睛,而左手刚向反,眼睛看向你其余手指,那么余下那么多种如UE4里,X轴从眼到手,Y向右,Z向上,本质是上面默认左手旋转出来,而右手是转不出来的,还有什么OpenCV的X向右,Y向下,Z从眼到手是右手坐标系,不要看到从眼到手,就是左手,这个是上面标准右手向右旋转180度的样子,如果你用上面说的默认左手是转不出来这个指向的,而追踪器一般来说,用的上面所说默认那种右手坐标系,就是X向右,Y向上,Z从手指向你.你的库如果确定坐标系后,那么Z轴的方向就确定了,一般数学上来说,用右手的多,你想下你课本里的XY轴,角度计量都是与X轴的夹角,这个夹角就是当Z轴是由书指向你,就是右手的前向的方向正方向,类似的,确定左右手后,你旋转的方向也固定了,简单来说,对应坐标系,分别手握住相应的轴,手握的方向就是对应轴的旋转正方向,在这里,我们自己库首先定义自己坐标系,用右手,X向右,Y向上,Z从手到眼,那么UE4里的顶点数据到我们库就是X是Y,Y是Z,Z是负X,OpenCV就是X,负Y,负Z.

然后确定你使用矩阵算法要用列主序还是行主序,注意这个列主序/行主序和左右坐标系没关,他们是可以组合的,确定这个列主序还是行主序后矩阵相乘的顺序就确定,我们知道矩阵乘法不满足交换律,顺序不一样导致的结果不一样,OpenCV/OpenGL应该都是列主序,所以是从右向左乘,我是感觉这方式有点别扭,我自己写就要写自己顺手的,于是我用行主序,从左向右乘.列主序与行主序的转化就是转置一下,也不需要计算.

最后旋转的常用表达方式吧,这个有几种常用的,欧拉角,四元数,轴角,3x3旋转矩阵(正交矩阵),确定上面内容后,参照网上一些代码,完成这几个比较常用表达旋转方式的互转,注意3x3旋转矩阵因为是正交矩阵,他的逆等于他的转置,特别简单,也需要注意欧拉角不能用来表达一个完整的旋转,他一般需要配合一个旋转顺序,一般来说Pitch/Yaw/Roll的组合,分ABC/ABA二种组合方法,内旋ABC=外旋CBA,所以只看内旋与外旋一种,就算一种也有12个组合,确定Pitch/Yaw/Roll的值以及组合顺序就可以正常转化成别的表达方式,这里说个点,opencv里的旋转可以3x3矩阵表示,也可以用三个浮点数表示,但是他不是用欧拉角,而是用的一种轴角的变体,轴角一般来说,有三个浮点表示方向,一般norm化,再加个浮点数表示旋转角度,而opencv里的三个浮点数是由方向norm*旋转角度来表示四个浮点数,外面使用他的这种旋转方向需要自己做对应转化.

## 图像展示

最开始图像采集后使用OpenCV的图像处理并展示,1080P分辨率下CPU占用高,刷新慢.改版图像采集后,使用vulkan compute shader处理YUV转RGBA并直接对接WinForm的DX11窗口,中间不经过内存,直接对接Vulkan/DX11纹理,并使用游戏方式高帧率刷新窗口,保证以及非常低的CPU占用显示高清实时图像,并且包含后续每帧在图像超过上千点精准展示都可以动态添加vulkan compute shader滤境层.

## 手眼标定算法改进

Redspy给的位移与现实有个缩放关系,比如现实中移动了1M,但是他姿态显示可能只移动了0.1M,所以手眼标定算法不能直接套用.

我们使用opencv源码解析,可以看到默认选择使用Tsai方法,余下几种大部分和Tasi类似,使用二步法,先求得旋转,再求得位移,可以看到求旋转的过程没有用到位移数据,所以可以保证旋转不会因摄像机与追踪器位移尺寸不匹配出现问题.

我们改进的主要就是求得位移的过程,先来看下opencv手眼标定里求位移相关逻辑.

``` c++
    // 解决追踪器与摄像机使用不同尺寸问题.
    Mat A(3 * K, 3, CV_64FC1);
    // Will store: Pcij - Pgij
    Mat B(3 * K, 1, CV_64FC1);
    idx = 0;
    for (size_t i = 0; i < Hg.size(); i++)
    {
        for (size_t j = i+1; j < Hg.size(); j++, idx++)
        {
            //Defines coordinate transformation from Gi to Gj
            //Hgi is from Gi (gripper) to RW (robot base)
            //Hgj is from Gj (gripper) to RW (robot base)
            Mat Hgij = vec_Hgij[static_cast<size_t>(idx)];
            //Defines coordinate transformation from Ci to Cj
            //Hci is from CW (calibration target) to Ci (camera)
            //Hcj is from CW (calibration target) to Cj (camera)
            Mat Hcij = vec_Hcij[static_cast<size_t>(idx)];

            //Left-hand side: (Rgij - I)
            Mat diff = Hgij(Rect(0,0,3,3)) - Mat::eye(3,3,CV_64FC1);
            diff.copyTo(A(Rect(0, idx*3, 3, 3)));

            //Right-hand side: Rcg*Tcij - Tgij
            diff = Rcg*Hcij(Rect(3, 0, 1, 3)) - Hgij(Rect(3, 0, 1, 3));
            diff.copyTo(B(Rect(0, idx*3, 1, 3)));
        }
    }

    Mat Tcg;
    //Translation from camera to gripper is obtained from the set of equations:
    //    (Rgij - I) * Tcg = Rcg*Tcij - Tgij    (eq 15)
    solve(A, B, Tcg, DECOMP_SVD);
```

利用等式

$$ (Rgij - I) * Tcg = Rcg*Tcij - Tgij $$

其中Rgij表示标定记录中二次记录之间追踪器空间下追踪器之间的旋转,根据记录是已知量.I表示3x3的单位矩阵,是固定量.Tcg表示追踪器空间下,摄像机相对追踪器的位移偏移,也就是我们要求解的值.Rcg表示追踪器空间下,摄像机相对追踪器的旋转偏移.Tcij 表示标定记录中二次记录之间摄像机空间下标定板之间的旋转,根据记录是已知量.Tgij 表示标定记录中二次记录之间追踪器空间下追踪器之间的位移,根据记录是已知量.

$$ (Rgij - I) * Tcg - Rcg*Tcij*Scale = -Tgij $$

原来矩阵算式如下.

$$\begin{bmatrix}
A_{00}&A_{01}&A_{02}\\
A_{10}&A_{11}&A_{12}\\
A_{20}&A_{21}&A_{22}\\
\end{bmatrix} * \begin{bmatrix}
T_{0}\\
T_{1}\\
T_{2}\\
\end{bmatrix} = \begin{bmatrix}
B_{0}\\
B_{1}\\
B_{2}\\
\end{bmatrix}
$$

现在变换后,矩阵算式如下.

$$\begin{bmatrix}
A_{00}&A_{01}&A_{02}&C_{03}\\
A_{10}&A_{11}&A_{12}&C_{13}\\
A_{20}&A_{21}&A_{22}&C_{23}\\
\end{bmatrix} * \begin{bmatrix}
T_{0}\\
T_{1}\\
T_{2}\\
S_{3}\\
\end{bmatrix} = \begin{bmatrix}
B_{0}\\
B_{1}\\
B_{2}\\
\end{bmatrix}
$$

其中新变换里的C表示- Rcg*Tcij,这样就把缩放参数带入要求解的[T0,T1,T2,S3]中的S3里面,新的代码如下.

```c++
    // 解决追踪器与摄像机使用不同尺寸问题.
    Mat TA(3 * K, 4, CV_64FC1);
    // Will store: Pcij - Pgij
    Mat TB(3 * K, 1, CV_64FC1);
    idx = 0;
    for (size_t i = 0; i < Hg.size(); i++) {
        for (size_t j = i + 1; j < Hg.size(); j++, idx++) {
            // Defines coordinate transformation from Gi to Gj
            // Hgi is from Gi (gripper) to RW (robot base)
            // Hgj is from Gj (gripper) to RW (robot base)
            Mat Hgij = vec_Hgij[static_cast<size_t>(idx)];
            // Defines coordinate transformation from Ci to Cj
            // Hci is from CW (calibration target) to Ci (camera)
            // Hcj is from CW (calibration target) to Cj (camera)
            Mat Hcij = vec_Hcij[static_cast<size_t>(idx)];

            // Left-hand side:3x3_(Rgij - I) 3x1_(Rcg*Tcij)
            Mat ldiff1 = Hgij(Rect(0, 0, 3, 3)) - Mat::eye(3, 3, CV_64FC1);
            ldiff1.copyTo(TA(Rect(0, idx * 3, 3, 3)));
            Mat ldiff2 = -(Rcg * Hcij(Rect(3, 0, 1, 3)));
            ldiff2.copyTo(TA(Rect(3, idx * 3, 1, 3)));

            // Right-hand side: -Tgij
            Mat diff = -Hgij(Rect(3, 0, 1, 3));
            diff.copyTo(TB(Rect(0, idx * 3, 1, 3)));
        }
    }
    Mat Tcg;
    solve(TA, TB, Tcg, DECOMP_SVD);
```

## 使用LED当标定板使用

使用标定板就需要绑定一块标定板,考虑现场的LED屏幕肯定多,LED幕墙可能不是平面的,如果角点组成面是非平面的,就需要传入一个默认的摄像机内参,这个默认内参非常方便给,其中心点取(0.5,0.5),FX/FY如果知道真实传感器尺寸,根据传感器尺寸与焦距就可以知道大致结果,不知道传感器尺寸其实也没关系,其FX/FY的求解只需要传感器尺寸的比例,对应图像比例,如1080P下,你传入16mm/9mm就行,但是因其计算焦距为FX/FY*传感器长宽,所以计算出来的焦距就会有问题,这种情况下,一般是根据焦距反推出使用的传感器尺寸真实大小,然后再FOV等参数.

用LED做标定板还有一个优点,可以一次得到LED面板/追踪器/摄像机三者的相对姿态关系.并且最后的像素误差也是直接直接针对在屏幕上的对应的像素误差,给的误差结论相对使用标定板,得到的误差像素是在这标定板上的,而我们最后显示是在屏幕上,使用LED标定给的误差就是屏幕上的误差,会更精确.

## Aruco标识用于标定


使用多块LED用棋盘格标定有个特征,假如针对第四块标定,那么最后结果在第四块自然比较完美,但是你把结果移到第一块/第八块后,其结果就不怎么好了,因为张正友内参计算/手眼标定都是针对给的数据经过计算,模拟而最匹配这些数据的结果,那么如何能匹配多块屏幕了,给定棋盘格规格后,就要用摄像机拍摄对应全部才行,这个大部分镜头都不满足,并且把拍摄角度也给固定范围有限了.

想到UE4里,得到摄像机相对Track的姿态后,用Aruco标识来查找LED屏幕位置,这里是根据已知摄像机问题使用PNP反推屏幕位置,和我们需要求同时求现实摄像机相对Track变换/Track坐标系到UE4坐标系下变换需求完全不同,但是Aruco标识有个特点,每个Aruco标识有一个markid(理解为索引),这样我们可以根据LED模型,根据自己设定,每块屏幕上放置特定markid,使用opencv查找到markid找到对应屏幕,也就知道对应屏幕在UE4上LED模型上的三维顶点,这样我们可以每帧拍摄任何位置,都可以二维UV与三维顶点的信息,反推出LED屏幕相对摄像机姿态,用于手眼标定求解.

不同于棋盘格固定大小,使用Aruco标识很自由,对应逻辑更复杂,每帧动态求得不同的二维UV/三维顶点,为了适配这二种逻辑,底层手眼标定计算类全部重构.

当然结果也证明是成功的,坪山使用Aruco标定,结果可以在各个块上得到非常好的匹配,在保证Redspy追踪准确的情况标定,可以得到对应LED屏上5个像素内的误差,可用于XR.

## FBX集成

FBX导入UE4,会把25fps的旋转插值成30fps,经同事帮忙,发现对应Scene里的TimeMode没值,添加Scene里的GlobeSetting相关设置解决.

欧拉角用三个顺序的由轴转动角度表示旋转,其在特定情况下会丢失第三轴,其表现为第二个旋转顺序如果在90左右,会发生万向锁问题.[欧拉角、欧拉旋转矩阵与万向锁](https://zhuanlan.zhihu.com/p/452494063)

其三坐标系分别是UE4坐标系(X:Back Y:Right Z:Up)左手,UE4 FBX所需坐标是(X:Right Y:Back Z:Up)右手,FBX坐标系(X:Right Y:Up Z:Front)右手.

如下例子,UE4坐标系(X:Back Y:Right Z:Up),其欧拉角旋转顺序为Yaw[Z]→Pitch[Y]→Roll[X],假设其对应(yaw:-89.83,Pitch:0.356,Roll:0.154),转到FBX所需的UE4摄像机坐标系(X:Back Y:Up Z:Right),可以看到与UE4的YZ刚好反过来了,其欧拉角顺序为Roll[X]→Yaw[Y]→Pitch[Z],转到FBX里欧拉角对应(Roll:-43.53, Yaw:89.81, Pitch:-32.31),欧拉因旋转顺序,其第二旋转顺序如果在90左右,会发生万向锁问题,在这FBX欧拉第二个角度为Y[Yaw]89.81,所以此时XZ会因万向锁问题与正常值差别比较大.

一般来说,各自的坐标系都会选择不会旋转90的轴来当锁死方向,比如UE4选择的Pitch,简单来说,UE4抬头或是向天空看的时候会出现万向锁的问题,转化到FBX后,其第二个角度变成Yaw,不幸的是,这个角度是常见的旋转到90的轴,这样我们需要改变其FBX坐标系避免这个问题.

最终参照UE4的FBX导出逻辑重新修改,其不用基坐标系转换,而是先设定FBX所需要的坐标系是(X:Right Y:Back Z:Up),然后把UE4 姿态转成这个坐标系下然后导出,可以避免Yaw90变换万向锁问题.

添加一个导出给Maya/Nake使用的空间姿态,对应Y向上,X向右(右手坐标系,YXZ顺序).
