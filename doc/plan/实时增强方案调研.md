# H.264/H.265 压缩伪影实时增强方案调研

> 评估针对 H.264/H.265 压缩造成的"糊/块/蚊噪"在 compute shader 实时管线下的处理方案。
> 前序结论：FSR 2.0 因缺运动矢量/深度/jitter 不适用播放器（已废弃，本文件转向压缩伪影专题）。

## 1. 背景：监控画面的"糊"主因

监控画面标称 1080P/2K 但观感差，主因不是分辨率而是 **H.264/H.265 高 QP 压缩伪影**：

| 伪影类型 | 表现 | 成因 |
|---------|------|------|
| 块效应 | 8×8/16×16 网格 | DCT 量化 + 码率不足时环路滤波器未抹平 |
| 蚊噪 | 边缘附近的闪烁小点 | 量化误差在 DCT 高频系数 |
| 振铃 | 边缘外晕开 | 截断高频系数 |
| 色度块 | 颜色阶梯 | 4:2:0 色度下采样 + 色度量化 |

**关键认知**：这些是**压缩伪影**，不是分辨率不足。纯空间超分（FSR 1.0/Anime4K）放大伪影，方向错。需要的是**压缩伪影修复**（deblock/dering/denoise），而非超分。

## 2. 现有 GLSL compute shader 生态盘点

mpv shader 生态有大量 compute shader，但**逐个核实训练数据后**，结论令人失望：

### 2.1 压缩伪影相关 shader 的真实适用性

| Shader | 官方定位 | 退化模型 | 适合真实视频？ |
|--------|---------|---------|--------------|
| **ACNet** (F8B4/8/18) | mpv_PlayKit 明确标注 **"仅适合2D动画"** | 推测 JPEG + 动漫退化 | ❌ |
| **ARNet** (F8B8~64) | ACNet 升级版（ResNet） | 同 ACNet | ❌ |
| **ArtCNN** | 作者明写 **"aimed at anime content"** | JPEG 444/420（非 H.264） | ❌ |
| **ArtCNN_DN/DS** | 动漫降噪变体 | JPEG | ❌ |
| **Anime4K Restore CNN** | 动漫专用（项目已集成） | 动漫退化 | ❌ |
| **ESRGAN 系列** | `modernAnime`/`AnimeJaNai`/`AnimeVideo` 等，全仅2D动画 | 动漫退化 | ❌ |
| **ESPCN** (aoxo/Lornatang) | 古典端侧超分 | bicubic/JPEG | ⚠️ 通用但非压缩伪影专用 |
| **CuNNy** | 偏动漫 | — | ⚠️ 部分 |
| **AiUpscale (Photo 版)** | 有 Photo/LineArt 分版 | — | ⚠️ Photo 版可能通用 |
| **Deband (neo_f3kdb)** | 去色带 | 位深不足 | ✅ 通用 |
| **CfL (KrigBilateral)** | 色度修复 | 4:2:0 色度 | ✅ 通用 |
| **nlmeans** | 非局部均值降噪 | 通用噪声 | ✅ 通用但慢 |

### 2.2 核心结论：没有针对 H.264/H.265 的开源 shader

**mpv/GLSL compute shader 生态里，没有一个 CNN shader 是专门针对 H.264/H.265 真实视频压缩伪影训练的。** 原因：

1. **训练数据问题**：这些 CNN 的训练流程几乎都走 JPEG 退化（Python 一行 `img.compress('jpeg')` 生成），H.264 退化需跑 FFmpeg 编码（每帧几十 ms，训练成本高 100×）
2. **用户群**：mpv shader 主力是动漫观众 → 训练偏动漫
3. **商业闭源**：真实视频/监控画质增强是安防厂商商业方案，不开源

### 2.3 JPEG 退化 vs H.264 退化的差异（为何 JPEG 训练的网络不最优）

| | JPEG | H.264/H.265 |
|---|------|------------|
| 块大小 | 固定 8×8 DCT | 4×4~16×16（H.264）/ 最大 64×64 CTU（H.265） |
| 块边界 | 规整、明显（无环路滤波） | 经环路滤波器抹平，更柔和、不规则 |
| 时域 | 单帧 | I/P/B 帧间预测，伪影沿运动方向传播 |
| 量化 | 每 8×8 块独立 QP | 宏块级 QP，可自适应 |

针对 JPEG 训练的网络（ACNet/ArtCNN）对 H.264 块效应**有部分帮助**（都是块边界伪影），但因为块模式不同，不是对口训练，效果打折。

## 4. 导向滤波去块（项目已有基础设施，P0 首选）

### 4.1 为什么导向滤波比 bilateral 更适合去块

| | 双边滤波（当前 FSR 前置） | 导向滤波自引导去块（改造） |
|---|---|---|
| **保边原理** | sigma_color 全局阈值——对比度高于阈值保边，低于阈值平滑 | **逐像素自适应 a/b 系数**——从局部协方差矩阵求解 |
| **对压缩块** | 块边界对比度低→被当成"该保的边缘"保住（不该保）；或 sigma_color 调大→真实边缘也糊 | 块边界是低方差结构→a 小→平滑掉；真实边缘高方差→a≈1→保留 |
| **自适应度** | ❌ 全局参数 | ✅ 逐像素（3×3 协方差 + eps 正则化） |
| **性能** | kernel=9 → ~1ms/1080P | zoom=8 下采样优化 → **~0.5ms/1080P**（更快） |

**核心差异**：bilateral 的 sigma_color 是一把全局尺子，块边界和弱纹理用同一把尺子量；导向滤波的 a/b 是从局部统计自适应算出来的，天然区分"低方差的块边界"和"高方差的真实边缘"。

### 4.2 项目已有完整的导向滤波实现

- `glsl/source/guidedFilter1.comp` — 计算 I*p、I*I 等协方差矩阵
- `glsl/source/guidedFilter2.comp` — 求解 a/b 线性系数（3×3 矩阵求逆）
- `glsl/source/guidedMatting.comp` — 抠图合成
- `src/avox_vulkan/extra/VkGuidedLayer.hpp/.cpp` — 完整的 GroupLayer，含 zoom=8 下采样优化
- 5 个 box blur + 1 个 solve pass，在 1/8 分辨率算 a/b 再上采样

### 4.3 改造方案：自引导去块

当前 `VkGuidedLayer` 做抠图（2 输入：图像 + 掩码），去块需改成**自引导**（guidance = input = 同一帧）：

1. 新建 `VkGuidedDeblockLayer`（简化版 VkGuidedLayer）：
   - 输入 = 单帧 rgba8（同 bilateral 的输入）
   - guidance I = 输入帧自身（转 rgba32f）
   - filtering input p = 输入帧自身
   - eps 参数暴露为 `deblockStrength`（类似 FSRParamet.deblockStrength → eps 映射）
   - 输出 = 平滑后的 rgba8

2. 管线中**替代 bilateral**：
   ```
   旧: bilateral → decode → EASU → RCAS → encode
   新: guidedDeblock → decode → EASU → RCAS → encode
   ```

3. eps → deblockStrength 映射（需实测调参）：
   - deblock=0 → eps=∞（不平滑）
   - deblock=0.5 → eps=0.01（轻度去块）
   - deblock=1.0 → eps=0.001（强去块）

4. 保留 zoom=8 下采样优化，1080P 性能 ~0.5ms

### 4.4 与 bilateral 对比预期

| 维度 | bilateral | 导向滤波去块 | 预期改善 |
|------|----------|------------|---------|
| 块边界消除 | 中（sigma_color 全局，块边界有时保住不该保） | ✅ 更好（a 系数自适应压低块边界） | **明显** |
| 真实边缘保留 | 中（sigma_color 调大时边缘也糊） | ✅ 更好（高方差区 a≈1 保留） | **明显** |
| 纹理保留 | 中 | ⚠️ 需实测（eps 太小会抹细节纹理） | 待验证 |
| 性能 | ~1ms | ~0.5ms | **2× 快** |
| 改造量 | — | 小（已有 VkGuidedLayer 基础，改自引导+接 FSR 管线） | — |

## 5. 可行的实时方案（更新）

### 5.1 方案 A：传统 ISP 兜底（当前方案，已实现）

```
bilateral 去块 → sRGB decode → EASU 放大 → RCAS 锐化 → sRGB encode
```

- bilateral 是通用保边平滑，不"知道"压缩块长什么样，靠 sigma_color 调参
- 优势：零训练、实时 30fps、所有硬件可用
- 劣势：不区分"真实边缘"和"压缩块边界"，可能抹真实细节

### 3.2 方案 B：移植 ACNet（折中，能做但非对口）

虽标注"仅2D动画"，但 ACNet 的 CNN 在 JPEG 退化上训练，块模式与 H.264 有重叠。对监控压缩画面**可能**比 bilateral 好（CNN 学过块边界模式），但：

- 训练数据是动漫，对真实监控纹理（人脸/车牌/树叶）可能过度处理
- 退化是 JPEG 非 H.264，块模式不完全对口
- 需实测才能判断是否比 bilateral 改善

**移植代价**：ACNet_F8B4 ≈ 9 pass compute shader，49KB 硬编码权重，1080P 集显 ~1-3ms。

### 3.3 方案 C：自训 H.264 压缩修复 CNN（最优，工作量大）

用 Real-ESRGAN 训练框架，但退化管线换成 **H.264/H.265 真实压缩**：

1. 收集高清监控源 → FFmpeg 用目标 QP 范围（QP=30~40，对监控码率）压成 H.264 → 形成 (压缩, 原始) 配对
2. 训一个小 SRVGGNet（类似 ACNet 架构，~12K 参数）
3. 训出的权重硬编码进 Vulkan compute shader（照 Anime4K/ACNet 的硬编码权重模式）
4. 对口 H.264 块效应、对口监控纹理

**代价**：需训练（GPU 数小时）+ 转 shader。但这是一次性工作，训完即用。

### 3.4 方案 D：Real-ESRGAN general-x4v3（ONNX，最强但集显不实时）

详见 `监控画质增强方案调研.md`。1.21M 参数，盲退化训练覆盖压缩，效果最好。但集显 540P~15fps，需抽帧/降采样，不能全帧实时。

## 6. 推荐路径（更新）

| 优先级 | 方案 | 理由 |
|--------|------|------|
| **P0** | 导向滤波自引导去块（替代 bilateral） | 项目已有完整基础设施、比 bilateral 更自适应（逐像素 a/b）、性能更快（zoom=8）、改造量小 |
| P1 | 保留 bilateral + FSR 1.0（兜底） | P0 实测不够好时回退 |
| P2 | 实测 ACNet_F8B4_hdn 移植 | CNN 学习型修复，但训练偏动漫/JPEG |
| P3 | 自训 H.264 压缩修复 CNN | 唯一口口对口 H.264 的路线，工作量大 |
| P4 | Real-ESRGAN ONNX | 独显/未来硬件可用，效果上限最高 |

## 5. ACNet 移植技术细节（若做 P1）

**架构**（ACNet_F8B4）：
- 1 head conv(1→8, 3×3) + 4 body blocks(8→8, 3×3, LeakyReLU) + upscale conv(8→4, 3×3) + pixel shuffle → 2× 放大
- 9 pass（mpv 把 8 通道拆 2 个 4 通道 pass，avox 不需拆分，可减到 ~5 pass）
- 权重硬编码为 `mat4(...)` 常量，无外部模型加载
- 每 conv 层 9~18 次纹理采样

**avox 集成**：
- 新建 `VkACNetLayer`（VkGroupLayer），5 个子 conv pass
- 放在 bilateral 之前或替代 bilateral
- 与现有 FSR 1.0 管线串联或互斥

**风险**：训练偏动漫/JPEG，对监控真实纹理可能不理想。**必须实测对比 bilateral**，否则不替换。
