# 解码后 NV12 直取（全平台）—— 新会话交接

> 目标：所有原生平台（Windows/Android/iOS/macOS）都能从播放器**直接取到解码后的 NV12 CPU 帧**，
> 统一走 `setOffSurface(YuvType::nv12)` + `ISurfaceRenderOb::onFrame(IImageBuffer*, YuvType)`
> 的既有契约（IImageBuffer 恒 packed，带 rowPitch）。本文是 2026-09-10 会话的现场交接。

## 1. 已有的积木（大部分已存在，别重造）

- **契约（c95c441，09-10 立的）**：`IImageBuffer` 恒 packed（rowPitch≥width）；`YUVFrame` 恒 split；
  GPU padded 帧转 split 用 `image2SplitYUVFrame(buf, yuvType, frame, tmp)`；
  `unpackGpuYUV`（原地改写 U 行）已禁止外部直接调用——现仅 `image2SplitYUVFrame`
  内部对副本使用（Video.cpp:310），外部直接调会破坏 packed 契约。
- **取帧入口**：`player->getSurfaceRender()->setOffSurface(YuvType::nv12)` + `addSurfaceRenderOb`，
  观察者 `onFrame(IImageBuffer*, YuvType)` 收 packed 帧。`getCpuFrameBuffer` 直取（d78c35f 新增）。
- **现成回归探针**：`samples/functest/latprobe.cpp`（新增，可当模板）：
  `latprobe <url> [秒] [前缀]`，onFrame→RGBA→存 PNG，末尾 `case=latprobe PASS/FAIL`。
- **测量工具**：`script/testenv/glass_latency.py`（源端烙墙钟 + 四协议采样），
  配套 `samples/vulkantest/webrtcplaytest.cpp` 已支持存图参数。

## 2. 各平台硬解→CPU 现状

| 平台 | 硬解 | 解码输出 | CPU 直取现状 |
|------|------|----------|--------------|
| Windows | dx11va（FFDx11Decoder） | D3D11 纹理数组帧（onDecodeGpu） | ⚠️ 见 §5 重大发现：当前 ffmpeg 没编 d3d11va hwaccel，硬解实际逐帧软解回退。GpuFrame 已带稳定取数坐标（buffer=copyTexture, queueIndex=切片号，FFDx11Decoder.cpp:128-150），车道B staging 直取的输入齐了 |
| Android | MediaCodec（AndVDecoder） | surface 模式走 onDecodeGpu；buffer 模式直出 CPU YUVFrame | 双路已存在：bOpenglRender 由 eglGetCurrentContext() 决定（AndVDecoder.cpp:164-178），离屏时 configure 不传 window 即 buffer 模式；实际色彩格式 andYuvType(localColorFMT) 已上报 |
| iOS/macOS | VideoToolbox（IOSVDecoder.mm） | CVPixelBuffer（已锁 NV12 格式，IOSVDecoder.mm:173）/Metal 系 | 解码器有 bMetalRender 开关与 CPU 锁定路径（IOSVDecoder.mm:299-326，现为死代码，且先 Unlock 后 dispatch 有指针隐患）；缺的是 renderer 侧锁定拷贝（见§5） |

## 3. 建议的设计方向（供新会话讨论）

1. **不要新开 API**：`setOffSurface(nv12)` + `onFrame(IImageBuffer*, YuvType)` 就是统一入口，
   缺的是各平台硬解帧"到 CPU packed NV12"的可靠落地（copy/staging 或平台映射）。
2. rowPitch 必须显式带出（硬解纹理行宽≠width），观察者按 packed+rowPitch 消费；
   禁止任何原地改写输入 buffer 的 helper（unpackGpuYUV 的教训）。
3. 每平台用 latprobe 同款探针做回归（解码→NV12→存 PNG + 判定行），进 collect_verdicts。
4. 补 `-hard`/软解双口径的延迟数字进矩阵（注意 -hard 当前实际是软解，见 §5）。
5. 【09-10 晚补】现有 vk CPU 输出是"RGBA→YUV"回程货：Windows 上 `getGpuContext()` 返回
   outSharedTex（NV12→RGBA 后的共享纹理，Dx11CSVideoRender.hpp:42），vk 从 RGBA 再转 YUV
   （rgba2YUV）——过两次色彩矩阵，拿不到解码器原生 NV12。"解码后 NV12"只有下节车道 B
   能真正达成；这也是车道 B 的最强论据（更便宜且无损）。

## 4. 车道B方案：各平台原生 NV12 直取（!bVulkan && enableYuvOut 时）

统一骨架（09-10 晚定稿：不加 readCpuYuv、不挂渲染尾部，回读在 getCpuFrameBuffer 里按需惰性做）：
- 依据：onRenderOut→getCpuFrameBuffer 本来就在渲染线程内、紧跟渲染发生（SurfaceRenderVk.cpp:349），
  首次 pull 触发回读即可。原生路径的 DX11 Map 自带同步、Metal Lock 随时可做，不像 vk 那样
  必须把下载嵌进图运行（vk 的下载在 graph->run() 里、nvBuffer 是图产物——该路径不动）。
- `VideoRender` 基类：把 VkVideoRender::getCpuFrame 的"packed 源→image2SplitYUVFrame"逻辑
  下沉为基类默认实现——getCpuFrame(frame) = getCpuFrameBuffer(&buf,...) + image2SplitYUVFrame
  （VkVideoRender::getCpuFrame 可随之删掉）；cpuIn 分支透传本次 SwVideoBuffer
  （Android buffer 模式走这条，零改动）；pts/dts/keyFrame 沿用 gpuFrame/yuvFrame。
- 各平台渲染器只重载 `getCpuFrameBuffer`：内部带"本帧已回读"缓存（按 pts/帧号判定），
  一帧最多一次 Map/Lock——同一帧会被取多次（onFrame 透传 + muxer pushFrame，yuvouttest
  测的双路场景），不能每次 pull 都回读；非渲染线程的 pull 只读缓存、绝不触发 GPU 操作
  （DX11 Map 必须在持有 context 的线程）。
- `SurfaceRenderNative`：重载 enableYuvOut/disableYuvOut（bVulkan→vkVideoRender 原样，
  !bVulkan→pVideoRender）；重载 getCpuFrame/getCpuFrameBuffer/getOutYuv 按 bVulkan 二选一
  （getOutYuv 非 vulkan 现返回 other，SurfaceRenderVk.cpp:296，会让 MediaPlayer/SourcePlayer
  误判软硬编，必修）。
- 门控收口两处：enableYuvOut 路由一处（!bVulkan→pVideoRender）+ 重载内部一处
  （bOutCpuYuv && !cpuIn && 本帧未回读）。vulkan 在场时行为零变化。

各平台 readCpuYuv：

| 平台 | 落点 | 做法 | 成本 |
|------|------|------|------|
| Windows Dx11CSVideoRender | getCpuFrameBuffer 重载（本帧缓存+顺延 Unmap） | 复用 staging 纹理（DXGI_FORMAT_NV12 + USAGE_STAGING + CPU_READ + ArraySize=1），ArraySize>1 时按 `gpuFrame.queueIndex` CopySubresourceRegion 取切片、否则 CopyResource→Map→**映射指针零拷包进 IImageBuffer**（rowPitch=Map.rowPitch，UV 起始=rowPitch×height）发布；Unmap 顺延到下一帧回读开头（单 staging 即可） | Map 同步 ≈1-3ms 是大头；嫌 stall 用双 staging"拷 N 读 N-1"错位 |
| Apple MetalRender | getCpuFrameBuffer 重载（本帧缓存+CFRetain 到下帧） | `gpuFrame.buffer` 即 CVPixelBuffer（NV12 420v/420f，biplanar 连续、UV 紧跟 Y）：LockBaseAddress(ReadOnly) 后**零拷包进 IImageBuffer**（rowPitch=bytesPerRow），CFRetain+保持锁定，下一帧再 Unlock/Release | 锁定+引用 ≈0，每帧省一次 3MB memcpy |
| Android | 无需重载 | 走解码器 buffer 模式：离屏纯取帧时跳过 surfaceTexture 创建，configure 传 null window，AMediaCodec_getOutputBuffer 直出 CPU YUVFrame；基类 cpuIn 透传即可收口（实际格式 nv12/420P planar 由 andYuvType 已上报，观察者按 YuvType 收） | 零 GPU 回读；codec 缓冲当帧回收，透传仅在回调窗口内有效 |

注意点：
- 【零拷的前提】Windows/Apple 的"映射指针直发"要求消费者在当帧窗口内消费（下一次回读、
  即下一帧渲染之前）：现有 onFrame 观察者（回调内同步转换/拷贝）与 pushFrame（渲染线程内）
  都满足；新增消费方要跨帧持有必须自行拷贝。行拷方案不是错，只是把生命周期解耦换成 ~0.3ms
  memcpy@1080p，二选一即可，别两套都做。
- Android buffer 模式没有预览；"预览+取帧并存"时才需要 GL OES 双 FBO 回读（Y→R8、UV→RG8），
  放二期，别进首期。
- 别复用 IOSVDecoder bMetalRender=false 那条死路径（先 Unlock 再 dispatch，指针出回调即悬空
  风险），renderer 侧锁定拷贝更稳。
- 顺序：基类骨架 → Windows staging → Apple 锁定零拷 → Android buffer 模式；每平台配 latprobe
  同款探针（解码→NV12→存 PNG+判定行），进 collect_verdicts。
- Windows 车道 B 的价值调整：车道 B (staging 直取) 从「解套手段」降级为「性能优化」
  (省一次 Vulkan 图转换), 优先级可后置。
