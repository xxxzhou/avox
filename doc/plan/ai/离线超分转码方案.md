## 1. 定位

实时超分上限已明(见[实时增强方案调研](实时增强方案调研.md)): Real-ESRGAN iGPU 540P 才 ~15fps,
1080P 实时无望。**画质要求高的场景改走离线**: 用 `createRecorder(true)` 转码链路
解码→GPU 图像处理→编码, 提前出增强片源, 播放时直接放增强后的文件, 不再赶帧。

**决策 (2026-09-17): 离线只走 Real-ESRGAN** (`realesr-general-x4v3`)。
理由: 盲退化训练覆盖压缩+模糊+噪点, 离线三档里效果上限最高; BSD-3-Clause 可商用(见 §2);
`skipFrames=0` 逐帧路径天然适配离线。FSR/Anime4K 保持实时轨使用, 不进离线链路。
超分产品化总盘见 [a11-superres-frc](../backlog/a11-superres-frc.md), 本方案是其离线支线。

### 9.5 G11 机制源码研判 (为下轮复现准备)

- `OVEngine::infer` 用**同步** `request.infer()` (`OVEngine.cpp:108`), 无超时、不可取消。

- `CpuQEnhancer::process` 无取消点: 进 infer 前不检查任何停止标志, 队列语义是"排空"
- 因此**修法明确**: ① `infer` 走 `start_async()`/`wait_for(timeout)` 或独立 watchdog
  线程 + `request.cancel()`; ② `stopTask` 增加带超时重载, 超时后放弃 join、
  把 qenhancer/OVEngine 的释放挪到 `close` 里 join **之前**或改为泄漏式隔离
  (宁可泄漏一个 OV 上下文也不能卡死产品)

### 10.7 **U/V 色差公式缺陷 + 修复 (本轮真正的产品级 bug)**

> **发现路径值得记下**: 这个 bug 是**因为用户问「产物在哪, 我看下」才暴露的**。
> 上一轮的验证只对了 ONNX 模型输入输出(max abs diff 8.3e-7)就下了"增强正确"的结论,
> **完全没验颜色编码**。教训: 图像链路的验收必须**看图**, 不能只验数值。

**症状**: 增强产物中**纯绿、品红整段变成灰色**, 黄/青/蓝严重失色; 同一源的
**纯缩放假分支颜色正常** ⇒ 缺陷牢牢锁在 `CpuQEnhancer`。

**实测症状**(Pillow 取色带中位数, 与真值对比):

| 段 | 真值 RGB | plain(2x) | enh(2x+ESRGAN) |
|---|---|---|---|
| 红 | (254,0,0) | (232,0,1) | (255,0,0) ✅ |
| **绿** | (0,254,0) | (17,255,8) | **(179,164,155) ❌ 变灰** |
| 蓝 | (0,0,254) | (0,0,242) | (0,74,255) ⚠️ |
| 青 | (0,253,254) | (21,255,251) | (0,255,255) ✅ |
| **品红** | (253,0,253) | (233,0,245) | **(77,89,95) ❌ 变灰** |
| **黄** | (253,253,0) | (251,255,10) | **(255,181,0) ❌ 失色** |

**根因** —— `CpuQEnhancer.cpp` `unpackToYuv` 第二遍算 2x2 块 UV 时, **漏减亮度**:

```cpp
// 错(修复前):
uint8_t u = clamp255((b - r) / 1.772f + 128.0f);
uint8_t v = clamp255((r - b) / 1.402f + 128.0f);
```

BT.601 full-range 的定义是 `U ∝ (B−Y)`、`V ∝ (R−Y)`, 而这里写成了 `(B−R)` / `(R−B)`。
**当 `R == B` 时两者恒为 0 ⇒ U=V=128 ⇒ 强制中性灰** —— 这就是纯绿/品红被打成灰的
全部原因(红也一起丢, 只是红恰好 R≠B 侥幸)。灰/白/黑本就 R=B 故"看不出问题",
所以小规模抽检极易漏掉。

数值对照(经 `ColorSpace.cpp:51-54` 真实矩阵往返):

| 色 | 正确 UV | 旧代码 UV | 旧公式还原 RGB | 新公式还原 RGB |
|---|---|---|---|---|
| 绿 | (43.9, 21.7) | **(128, 128)** ← 恒灰 | (149,149,149) | **(0,254,0)** ✅ |
| 品红 | (211.8, 233.9) | **(128, 128)** ← 恒灰 | (104,104,104) | **(253,0,253)** ✅ |
| 黄 | (2.3, 148.9) | (−14.8, 308.5) | (477,144,−29) | **(253,253,0)** ✅ |
| 蓝 | (255, 107) | (271, −53) | (−225,109,283) | **(0,0,254)** ✅ |
| 青 | (171, 1.4) | (271, −53) | (−77,258,431) | **(0,253,254)** ✅ |
| 红 | (85, 255) | (−15, 309) | (330,−4,−178) | **(254,0,0)** ✅ |

**最大还原误差: 旧 225.0 → 新 0.0**(10 色全部归零, 含橙/灰/白/黑)。

**修复**(`CpuQEnhancer.cpp:213-218`, 已落地):

```cpp
// BT601 full-range 色差(U/V)必须以亮度为基准: U∝(B-Y), V∝(R-Y)。
// 曾误用 (B-R)/(R-B) —— 当 R==B 时恒等 128(纯灰), 于是纯绿/品红这类
// R==B 的色被整段打成灰(RED 也一起丢), 黄/青/蓝则严重失色。
int32_t yy = (299 * r + 587 * g + 114 * b) / 1000;
uint8_t u = clamp255((b - yy) / 1.772f + 128.0f);
uint8_t v = clamp255((r - yy) / 1.402f + 128.0f);
```

另注意 Y 平面用的是 `clamp255(0.299f*r + 0.587f*g + 0.114f*b)`(逐像素 float),
而 UV 这里用整数 `(299*r+587*g+114*b)/1000` —— **两者系数一致, Y/UV 互为一致**,
不会出现"Y 用新色、UV 用旧色"的错配。

**调用链已核实 (2026-09-17 23:3x, 读源码确认, 收窄了怀疑面)**:
`TranscodeRecorder::onRunTask()` 的 `:422 muxer->close()` 里 `muxer` 的类型是
**`std::unique_ptr<RawMuxer>`** (`TranscodeRecorder.hpp:36`) —— 而 `RawMuxer::close()`
是**继承自 `MediaMuxer::close()`** (`MediaMuxer.cpp:202`), 不是 `IOMuxer::close()`。
所以真实链路是:

```
TranscodeRecorder::onRunTask() :422
  └─ RawMuxer::close()  == MediaMuxer::close()      MediaMuxer.cpp:202
       ├─ :207  if (state == completed) return;     ← 早退守卫
       ├─ :210  onClose()          → RawMuxer::onClose() = bReAudio=false (平凡)
       ├─ :212  ioMuxer->close()   → IOMuxer::close()   IOMuxer.cpp:111
       │            ├─ stopTask()  → thread.join() (裸 join, 无超时)
       │            └─ onClose()   → FFMuxer::onClose() → av_write_trailer
       └─ :219  setRecState(completed)
```

**关键澄清: 早退守卫不会命中。** 仓库里存在**两个互相独立的 `state` 成员**:
`TranscodeRecorder::state` (`TranscodeRecorder.hpp:40`, 由自己的 `setRecState` 写,
`TranscodeRecorder.cpp:36`) 与 `MediaMuxer::state` (`MediaMuxer.hpp:24`, 由
`MediaMuxer::setRecState` 写, `MediaMuxer.cpp:12`)。`TranscodeRecorder::setRecState`
**不转发**给 `MediaMuxer`, 因此 `TranscodeRecorder` 置 `completed` 不影响
`MediaMuxer::state`。实测日志也印证 —— 全程只有三次 muxer 状态迁移:

```
muxer state change:none -> opening      (MediaMuxer.cpp:61 open)
muxer state change:opening -> recording (MediaMuxer.cpp:89 ready)
（再没有第 4 条 ⇒ 到 close 时 MediaMuxer::state 仍是 recording）
```

⇒ `MediaMuxer::close():207` 守卫**不成立**, `onClose()`(平凡) 必然执行,
卡点**必定在 `ioMuxer->close()` 之内**。这把怀疑面从「三个候选」压到「两个」:
**`IOMuxer::stopTask()` 的 `join` 出不来**, 或 **`FFMuxer::onClose()` 的
`av_write_trailer` 本身阻塞**。新探针 (`TRACE muxclose: begin/after stopTask/after onClose`
+ `TRACE muxloop: exit loop/flushPendingAu done`) 正是为二分这两者插入的。

墙钟 309s ⇒ **1.72s/帧, 跑满 12s 源需 ~620s**。400s 根本不够, **不是挂死**。
(旧记录里 "1.95s/帧" 是 640x360 源 4x 的实测; 本次 960x540 源 4x 实测
`CpuQEnhancer frame #180:1+1911+8ms` = **1911ms/帧**, pack 1ms / unpack 8ms
⇒ **瓶颈 100% 在 infer**。)

另: `updateProgress` 的 `media` 值在小幅震荡(如 `5000→5133→5067→5033→5100`),
属解码在队列反压下的正常抖动, **不要当成"倒退"故障**。

**⚠️ 判据修正 (本轮踩到)**: 判「卡死 vs 干活」不能只看 CPU 占用率 —— **要看核数形态**:

| 形态 | `cores_busy` | 含义 |
|---|---|---|
| **单核自旋** | **≈0.99** (其余核闲置) | G13 收尾卡死特征(§10.8) |
| 多核满载 | **≈8.8** (本机 9 核) | **正常**: ORT CPU 并行推理在干活 |

本轮一度以为"产物 37s 不涨 = 又卡了", 实测 `cores_busy=8.834` ⇒ **是 9 核全速推理**,
产物随后继续增长。**判据: 单核自旋才是病态; 多核满载是正常吞吐。**
另可辅以 `wmic path Win32_Process where ProcessId=<pid> get KernelModeTime,UserModeTime`
取全进程 CPU 秒(比 PowerShell 的逐线程表格可靠, 后者 `Out-File` 有编码坑)。

#### pts 量纲谜题解决 (G7 时基链的最后一个未知量)

`TRACE pts` 实测(源 tb `1/15360`, 30fps):

```
#0   inPts=0     inDts=0
#30  inPts=1000  inDts=1000    Δ=1000
#60  inPts=2000  inDts=2000    Δ=1000
#180 inPts=6000  inDts=6000    Δ=1000
```

**步进 = 1000, 即「毫秒」** —— 既不是源 tb 原样的 512, 也不是 1/90000 的 2970。
⇒ **进编码器前 pts 已被折算成毫秒**, 因此 `FFVEncoder.cpp:99` 硬编码
`codecCtx->time_base = {1,1000}` **是正确的、不是 bug**。
G7 时基链**确认自洽**, 之前的"定时炸弹"判断**撤销** —— 不必再动 `FFVEncoder.cpp:99`,
也不必在 `processVideo` 前找折算点(它就在 `yframe.pts` 这一层, 已经是 ms)。

#### 新缺陷 A: 所有 avox 转码产物开头有两个「无图像访问单元」

`ffprobe` 对**每一个** avox 转码产物(含改动前的 `out_nomodel.mp4`)都报:

```
[h264] missing picture in access unit with size 28
[h264] no frame!
[h264] missing picture in access unit with size 8
[h264] no frame!
```

28B / 8B 的裸包 = 只有 AUD/SEI 没有 slice 的访问单元。`IOMuxer.cpp:66` 的
`naluDropAble` 只丢弃 **AUD**, 未覆盖这类纯 SEI 包 ⇒ 它们被当独立帧写进码流,
解码器在文件开头就要报错(`Missing key frame while searching for timestamp: 0`)。
**这是存量缺陷, 非本轮引入**。影响: 容错差的播放器可能开播失败。

#### 新缺陷 B: 关增强 + `auto` 时输出分辨率不生效

关增强产物 `out_blur_plain.mp4` **声明 960x540**(源尺寸), 而日志明确
`source 960x540 duration=12000ms mode=auto -> output 3840x2160`、summary 也写
`960x540 -> 3840x2160` ⇒ **实际出图仍是 960x540, 与声明的 3840x2160 不符**。
可疑点: `TranscodeRecorder.cpp:254` 的输出尺寸覆盖被 `!qenhancer` 挡住:

```cpp
if (bSetOutVideo && !qenhancer) {     // ← 关增强才走这条路
  ... surfaceRender->enableSizeChange(outVideoDesc.width, outVideoDesc.height);
}
```

对照: **开增强**产物 `out_model.mp4` 声明 **2560x1440**(640x360 源 4x)是**正确**的
—— 因为它走 `vdesc.desc.width = qenhancer->outWidth()`(`:232`)。所以问题特定于
**关增强 + 显式输出尺寸**这条组合, 需查 `bSetOutVideo`/`outVideoDesc` 由谁填、
`auto` 的倍率是否根本没传下来。

**产物几何错乱**: `out_blur_plain.mp4` 用 ffmpeg 强解出的首帧**上下错位/横向撕裂**
(彩条与正文块位置都不对), 符合"按 3840 宽读 960 宽数据"的 stride 错配特征
—— 与缺陷 B 同源。

### 10.10 糊源验收集 (2026-09-17 深夜, 用户要求「找一个糊的视频来验证」)

**为什么必须自造糊源**: 增强效果只能在**本身丢过信息**的源上体现。先扫全仓现有素材
(`avox-test/assets/video`、`avox/assets/video`、`samples`), 实测边缘强度:

| 素材 | edge strength | 判定 |
|---|---|---|
| `selfcheck_h264_320x240` | 7.47 | 太锐 |
| `test_h264_aac_320x240` | 4.94 | 太锐 |
| `selfcheck_h264_640x360_12s` | 4.02 | 太锐 |
| `482x362` | 3.29 | 仍偏锐 |
| `1080p` | 1.83 | 低但分辨率不同, 不利对照 |

⇒ **现有素材没有真正"糊"的**, 故自造。

**糊源做法**(`make_sources.py`, ffmpeg): 先**降采样丢高频**, 再升回目标分辨率, 最后低码率编码
(模拟真实"糊+压缩"源):

```
scale=480:270:flags=bilinear, scale=960:540:flags=bicubic
-c:v libx264 -preset veryfast -crf 45 -maxrate 250k -bufsize 500k
```

**素材清单** (均 12s @30fps, 源图为 `c_mix.png`):

| 文件 | 分辨率 | 大小 | edge | 用途 |
|---|---|---|---|---|
| `blur_960x540_12s.mp4` | 960x540 | 47,999 B | **3.78** | 主糊源(验收集主角) |
| `sharp_960x540_12s.mp4` | 960x540 | 674,909 B | **12.14** | 同分辨率锐源对照 |
| `blur_1920x1080_12s.mp4` | 1920x1080 | 109,941 B | 2.35 | 触发 `auto`=2x 分支 |

**关键对照原则**: 锐源对照**必须同分辨率**(960x540), 否则"糊"与"小"两因素混淆 ——
糊源 edge 3.78 是锐源 12.14 的 **31%**, 差异来自**信息丢失**而非分辨率。
