## 2. 实测证据链（每条都可复测）

| # | 事实 | 怎么测出来的 |
|---|---|---|
| 1 | 容器与解码帧都是 **720x406**（`avih`/`strf` 均 `0x2d0 x 0x196`） | Python 解 RIFF 头 |
| 2 | 解码帧 `stride[0]=768, stride[1]=384, stride[2]=384`（**带 padding**） | 在 `copyPlaneYUV2TightlyBuffer` 里临时 fprintf |
| 3 | 因此走 `Video.cpp:266` 的 **else 分支**（`halfWidth 360 != stride[1] 384`） | 同上 |
| 4 | 打包后缓冲区 609 行里**只有第 608 行整行为零**，尾部 816 字节从未被写 | 在 `SwVideoBuffer::form` 里把 `bdata` 原样 `fwrite` 落盘，Python 逐行查零 |
| 5 | 用真实打包缓冲 + 复刻 `yuv2rgbaV1` 的寻址做纯 Python 着色，**只出 404/405 两行绿** | 见本文 §6 |
| 6 | `-hard` 对本片**无效**，回落到软解（日志 `FFVDecoder.cpp:350 onFrame` 即 CPU 解码器） | `avox_cli play -hard` |

### 关键算术

色度行高 `uvH = 406/2 = 203`（**奇数**）。else 分支 `physRows = uvHeight / 2 = 101`，
一个物理行塞两条逻辑色度行 → 每平面只装得下 `2*101 = 202` 条，**第 203 条无处安放**，
尾部 `720` 字节留零。着色器按行寻址 V 基址 = `size.y*5/4 = 507`，读到未写区 → `V=0`。
YUV 全零不是黑，是**绿**（`V=0 → R` 钳到 0）。

**空间其实是够的**：色度区 `720 × 203 = 146160` 字节，两平面各需 `360 × 203 = 73080`，
合计正好 `146160`。装不下只是因为打包把 V 对齐到了**整行**，白扔 360 字节。

## 3. 根因：仓库里有两套 packed 420P 布局定义

| 位深 | 着色器 | V 平面基址 | 奇数色度行 |
|---|---|---|---|
| 8bit | `glsl/source/yuv2rgbaV1.comp:63` | `nuv + ivec2(0, size.y*5/4)` —— **按行** | 表达不了 ← 本 bug |
| 8bit 编码侧 | `glsl/source/rgba2yuvV1.comp:70` | `ivec2(0, size.y*5/4) + nuv` —— **按行** | 同上 |
| 10bit | `glsl/source/yuv2rgbaV5.comp:124-136` | `yPlaneSize + uvPlaneSize + uvIndex` 再 `%(width), /(width)` —— **按字节线性** | 天然 OK |
| 10bit 编码侧 | `glsl/source/rgba2yuvV4.comp:36-44` | 同上，线性 | 天然 OK |

按行寻址要求每个色度平面从**整行**开始；`uvH` 为奇数时 V 的真实落点在半行上，按行永远差半行。
按字节线性寻址不受行边界约束，且 `nuv` 那套 `%width / /width` 本来就是线性寻址——
**V1 的 U 寻址已经是对的，只有 V 基址用了行对齐。**

结论：**V5/V4 的线性式才是通式**，V1/rgba2yuvV1 是只在偶数色度行时字节重合的特例。
修 = 把 8bit 两侧对齐到线性式，**406 不改、画面不丢**。

## 4. 改动清单（5 处，约 20 行）

| # | 位置 | 改什么 |
|---|---|---|
| 1 | `src/avox/video/Video.cpp:266-280`（`copyPlaneYUV2TightlyBuffer` 420P/422P else 分支） | `physRows = uvHeight / 2` 丢掉落单末行 → 循环按 `uvHeight` 全量走，目标地址按**纹理线性**算：`L = p*uvSize + r*halfWidth`，`dst = (y_logic_size + L)/width*yrowpitch + (y_logic_size + L)%width`。V 基址随之从 `p*physRows*yrowpitch` 变成 `p*uvSize` 的线性映射（本片 = `uvDst + 77928`，比现在多 360） |
| 2 | `glsl/source/yuv2rgbaV1.comp:63` | `vindex = nuv + ivec2(0, size.y*5/4)` → 抄 V5 的线性式：`int vPos = size.y*size.x + (size.x/2)*(size.y/2) + uv.y*(size.x/2) + uv.x;` 再 `%(size.x), /(size.x)`。U 侧已是线性，不动 |
| 3 | `glsl/source/rgba2yuvV1.comp:70` | 反方向同一处 `size.y*5/4`，一起换成线性式 |
| 4 | `src/avox/video/Video.cpp:316-319`（`image2YUVFrame` 420P/422P 分支）+ `src/avox/video/ImageBuffer.cpp:117`（`unpackGpuYUV`） | CPU 回读侧要按同一线性式还原 split：V 基址不能再写 `uvPitch*uvHeight`（buffer 空间），得按纹理线性映射；`uvPhysRows = yHeight/2` 同样漏末行。这条覆盖录制与 `setOffSurface(yuv420P)` |
| 5 | `tests/test_videobuffer.cpp` | 加**奇数色度行** case。现有 6 个 case 全用 `h=4`（色度行 2，偶数），正好躲开本 bug——这就是它没被拦住的原因 |

着色器改完要重编 GLSL：`glsl/` 下的 `.comp` 由构建自动编成 `.spv`（见 AGENTS.md「GLSL」条）。

### 不用动（已核过）

- **DX11 / GLES / Metal**：`src/avox_windows/WinCommon.cpp` 等没有 planar 420P 的按行寻址，它们收 **NV12**——色度一物理行=一逻辑行，无配对约束，奇数 `uvH` 天然免疫。
- **硬解**：`FFDx11Decoder` / `FFVkDecoder` 出 `GpuFrame`，不经 `SwVideoBuffer::form`，压根不产生 packed planar 帧。实测 `-hard` 对 mpeg4 直接回落软解。
- **`yuv422P`**：`uvHeight == height`，V 基址 `size.y*3/2` 对偶数高本就整除，不受此限。
- **`nv12` 分支**：同上免疫。
- 帧高 406、`imageFormat.height = 609`、`getYuvFrameSize`、`AVOX_MAP_YUV` 的 group/groupsize —— **全都不用改**，这是本方案相对「裁剪到 404」和「扩缓冲区到 610 行」两个备选的核心优势。

### 已否决的两个备选（别再走回头路）

- **裁剪 `height &= ~3`（406→404）**：闸只能下在 `SwVideoBuffer::form`（`src/avox/video/VideoBuffer.cpp:16`，packed 布局唯一生产者，仅 `VInputLayer.cpp:44` 与 `VideoFrame.cpp:27` 两个调用点），约 6 行。但丢 2 行画面、`setAspect` 从 720/406 变 720/404（+0.5% 拉伸）、容器 desc 仍报 406 与实际帧 404 不一致。
- **把未写尾部填成 `U=V=128` 让它显示黑/中性**：一处 `memset` 最省，但只是把「装不下」藏起来——第 4 项的 CPU 回读错位没修，录制还是花的；而且要注意**填 0 恰恰是绿**，得填 128。

## 5. 动手前必须先做：钉死那多出来的 2 行

证据 5 说明**当前模型只能解释 2 行绿（404/405），实测是 4 行（402~405）**。
按 V1 的寻址手算，`cy=201` 的 U/V 都落在已写区，不该绿。也就是 `form` 之外还有一处缺陷。

**不改完这一处就动手，绿条很可能只掉一半，等于白改一轮。**

建议的查法（沿用本会话的探针手法）：
1. 在 `SwVideoBuffer::form` 打包后把 `bdata` 落盘（挑 `tempFormat.height == 609 && frame.pts > 4000` 的帧，前两帧即可）；
2. 纯 Python 按 V1 寻址把它转成 RGBA，逐行取色，和同一时刻的 `-screenshot` 输出对比；
3. 两者行数不一致 → 分歧在着色器之后（`VkOutputLayer` 回读 / `bufferToImage` 的 `bufferRowLength` / 中间层重采样），逐段缩小。

重点怀疑 `bufferToImage(cmd, inBuffer.get(), outTexs[0].get(), inFormats[0].rowPitch)`
（`src/avox_vulkan/layer/VkInputLayer.cpp:199`）——纹理宽 720 而 buffer 行距 768，
若 `bufferRowLength` 没设成 768，色度会逐行累积 48 字节斜偏，表现正是「越往下越不对」。

## 6. 复刻着色器寻址的验证脚本（本会话用它得出证据 5）

```python
import numpy as np
S0, W, H = 768, 720, 406          # rowPitch, width, 帧高
buf = np.fromfile('_dbg_pack1.bin', np.uint8)
tex = np.stack([buf[r*S0:r*S0+W] for r in range(609)])   # 每 768 字节行取前 720 = 纹理
halfW = W // 2
cy, cx = np.mgrid[0:H//2, 0:halfW]
lin = cy*halfW + cx
nr, nc = lin // W, lin % W        # V1 的 u12u2(u22u1(...))
u = tex[nr + H, nc].astype(int)         # uindex = nuv + (0, size.y)
v = tex[nr + H*5//4, nc].astype(int)    # vindex = nuv + (0, size.y*5/4)
y = tex[0:H:2, 0:W:2].astype(int)
yn = 1.164*(y-16)/255.0; un = (u-128)/255.0; vn = (v-128)/255.0
r = np.clip((yn + 1.596*vn)*255, 0, 255)
g = np.clip((yn - 0.391*un - 0.813*vn)*255, 0, 255)
b = np.clip((yn + 2.029*un)*255, 0, 255)
for yy in range(398, H):
    print(yy, r[yy//2, 0], g[yy//2, 0], b[yy//2, 0])
```

跑出来只有 404/405 绿（`[25 255 229]`），实测 402~405 都绿 —— 差 2 行，即 §5。
