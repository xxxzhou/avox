## 一、目标与非目标

**目标**

1. 平面式 4:2:2 10bit(FFmpeg `AV_PIX_FMT_YUV422P10LE`)在**三腿全通**: Windows D3D11 CS / Apple Metal / Vulkan。
2. ProRes(Matroska `V_PRORES`, 含 PQ/HDR10 母版)正常出画, 且**复用既有 HDR 链**(直通 / tone map / 呈现面实态翻转 / DV 整形全部零改动)。
3. 全链**不引入 CPU 像素格式转换**(无 swscale, 无逐像素重采样)。

**非目标**

| 项 | 处置 |
|---|---|
| 打包式 4:2:2 10bit(`uyvy422_10B`) | 不动, 见 §2.3(采集向遗留, 解码链不可达) |
| ProRes 4444 / 4444 XQ(12bit 4:4:4) | **暂时不做**(2026-10-03 拍板), 挂账见 §八 第 1 条 |
| Apple VT 硬解 ProRes(`x422`) | **已并入范围**(2026-10-03 追加) —— 见 §4.7 / T8b(可行, 直通不经 VK) |
| Android/EGL 原生腿 4:2:2 | 不做 —— Android 恒走 VK 腿, 由 VK 覆盖(§4.6) |
| Linux 原生腿 | 同上(Linux 唯一窗口是 `VkWindow`) |

## 二、事实基线(核码 2026-10-03)

### 2.1 断点链(两条, 叠加)

| # | 断点 | 位置 | 证据 |
|---|---|---|---|
| ① | 编码白名单无 prores → `VCodecId::none` | `FFHelper.cpp:109 ffVCodec()` 的 switch 无 `AV_CODEC_ID_PRORES` → `default: return VCodecId::none`; `AvoxCodec.h:34 AVOX_MAP_VCODEC` 无该项 | 实播日志 `add video track: invalid-3840*2160@23.976-unknow` + `VideoTrack.cpp:37 setTrackDesc unsupported codec -1`; 该段 `video decode create` 计数 **0** |
| ② | 像素格式枚举无**平面式** 4:2:2 10bit | `AvoxVideo.h:15 AVOX_MAP_YUV` 的 422 只有 8bit 平面 `yuv422P` 与 10bit **打包** `uyvy422_10B`; `ffYuvType()`(`FFHelper.cpp:314`)无 `AV_PIX_FMT_YUV422P10LE` 条目 | 即使补①, 解码帧仍落 `YuvType::other` |

**两条都要修** —— 只修①仍不出画。

### 2.2 各腿支持面(实测, 均为源码守卫)

| 渲染腿 | 420P 8b | 420P 10b | 422 8b | 422 10b | 守卫位置 |
|---|---|---|---|---|---|
| Vulkan | ✓ | ✓ | ✓ | △ **仅打包式** | `VkYUV2RGBALayer.cpp:89 onInitLayer`(分支表) |
| Windows D3D11 CS | ✓ | ✓ | ✗ | ✗ | `Dx11CSVideoRender.cpp:532` `if ((yuvType != yuv420P && !b10) ...) return false;` |
| Apple Metal | ✓ | ✓ | ✗ | ✗ | `MetalRender.mm:560` 同形守卫 |
| CPU 兜底 `yuvframe2Rgba` | ✓ | ✗ | ✗ | ✗ | `ImageBuffer.cpp:80` 只放 `yuv420P`/`nv12` |

VK 那格是 `uyvy422_10B → glsl/yuv2rgbaV3.comp.spv`, 而 V3 是**打包式**着色器(shader 内 `uv.x*5 + 0..4` 连读 5 字节拆 4 个 10bit, 2 像素/5 字节)—— 与 ProRes 的**平面式**输出布局不兼容。

### 2.3 `uyvy422_10B` 的真相(为什么不能复用)

- 它是**打包式** 4:2:2 10bit, 属**上古采集/编码向**遗留(首见 `82e429a 添加视频渲染接口`), 配套 `rgba2yuvV3`/`yuv2rgbaV3` 一对 shader。
- **`ffYuvType()` 从不产出它** ⇒ 在「解码→出图」链上**不可达**; 仅 `getFFVideoFormat()` 反向表有它(`FFHelper.cpp:458 → AV_PIX_FMT_YUV422P10LE`)。
- ⚠️ 顺带发现一处**不对称待核**: 反向表把 `uyvy422_10B`(打包)映到 `AV_PIX_FMT_YUV422P10LE`(**平面**), 与 V3 期望的打包布局对不上, 且正向表无对应项。独立小账, 见 §八 第 3 条。

### 2.4 无 CPU 兜底(为什么必须走 GPU 路径)

- 全仓 `sws_scale` / `sws_getContext` **零命中**。
- `FFVDecoder.cpp:437` 直接把解码帧的 `AVPixelFormat` 经 `ffYuvType()` 映射, **不在表即 `other`**, 无转换腿。
- 硬解面(**引擎现状**): 三平台**都没接 ProRes 硬解** —— `VkDecoder.cpp:67`(VK 只 h264/h265/av1)、DXVA 无 ProRes、
  `IOSVDecoder.mm:111` 只认 420(`p010`/`nv12`)。
  ⚠️ **但「平台没有」≠「引擎没接」**: Apple 的 VideoToolbox **本身能解 ProRes**(FFmpeg 有 `prores_videotoolbox` hwaccel 佐证),
  只是引擎没接 ⇒ 见 §4.7 / T8b(已并入范围)。
  ⇒ **Windows/Linux/Android 上 ProRes 恒软解**, 帧必走 CPU 帧腿(`initGraphCpu` / `renderCpuFrame` / VK `cpuIn`),
  正是 §2.2 里那三条**最窄的守卫**; **mac 上可由 VT 硬解直通**(§4.7), 软解仅作兜底。

- **Windows 侧为什么没有 ProRes 硬解(已核, 勿重复调研)**: 不是驱动/显卡档次问题, 是**根本没有这个解码器**。
  ① **DXVA2/D3D11VA 的 profile 表**(`libavcodec/dxva2.c:62-78`)只有: mpeg2 simple/main、h264 constrained
  baseline/main/high(**无 High 4:2:2**)、hevc main/main10(**都是 4:2:0**)、vp9 p0/p2、av1 p0
  ⇒ **整个 DXVA 不存在任何 4:2:2 解码模式**, 故不只 ProRes, 一切 4:2:2 内容在 Windows 上都没有 DXVA 路径。
  ② 厂商 SDK(NVDEC / QSV / AMF)亦不提供 ProRes 解码。
  ③ FFmpeg 全仓的 ProRes 硬解**只有两个** hwaccel(`libavcodec/hwaccels.h:71-74` / `proresdec.c:883,886`):
  `videotoolbox`(Apple 专属)与 `vulkan`。
  ⚠️ `vulkan` 那个**不是固定功能硬解** —— `vulkan_prores.c:31` 的 descriptor 只有 `codec_id` +
  `queue_flags = VK_QUEUE_COMPUTE_BIT`, 配 `FFVulkanShader vld`/`idct` 两个 compute shader, 即
  **把 VLD 熵解码 + IDCT 放到 GPU 通用算力上跑**; 理论上 Windows 也能跑, 但见 §八 第 5 条(未采用, 已评估)。
  ⇒ **Windows 的 4:2:2 10bit 只能软解** —— 所以 T7(D3D11 CS 422 上传与呈现)是 Windows 的**唯一路径, 不是可选优化**,
  也正因如此 §7 把「上传带宽/CPU」列为 Windows 侧头号风险。**两平台处境不对称: mac 有 VT 硬解(T8b), Windows 没有。**

## 三、方案总览

**核心观察: 4:2:2 与 4:2:0 的差别只有一个数 —— 色度平面高度。**
位深(10bit)、平面紧排、色彩处理(矩阵 / tone map / DV)、HDR 直通与呈现面实态翻转, 与既有 `yuv420P10` **完全同构**。

⇒ 三腿改法统一为一句话: **照抄各自已有的 `yuv420P10` 那条路, 把色度高度 `h/2` 改成 `h`**。

| 腿 | 既有 420P10 路径(模板) | 新 422P10 路径 | 改动量 |
|---|---|---|---|
| VK | `VkInputLayer` r16→rgba8 字节视图 → `yuv2rgbaV5.comp` | 同左, 换 `yuv2rgbaV6.comp`(仅入口函数) | 新 shader 一个 + `onInitLayer` 一分支 |
| D3D11 | CPU 帧 → DYNAMIC P010 纹理(双平面视图) → CS `p010Point` | 双纹理(Y R16 / UV R16G16, UV 高 = h) → CS 新分支 `p422Point` | 新纹理槽 + CS 一分支 + 上传循环一行 |
| Metal | CPU 帧 → P010 CVPixelBuffer → fragment shader | 双 `MTLTexture`(Y r16Unorm / UV rg16Unorm, UV 高 = h) → **同一 fragment shader** | 新纹理对 + 新绘制入口 |
| **Apple VT 硬解**(§4.7) | VT 硬解 420 → `x420` pb → fragment shader | VT 硬解 ProRes → **`x422` pb**(色度全高)→ **同一 fragment shader** | 解码器注册 + profile 来源 + Metal **四处**格式判定(含 UV 平面高度); **零纹理/零上传** |

**上传契约按腿各自镜像既有路径**(不强行统一, 理由见 §4.4 注):

| 腿 | 位对齐 | 布局 | 与既有路径的关系 |
|---|---|---|---|
| VK | **低对齐**(原样, 无移位) | 平面紧排**字流**(Y/U/V 按 width 连排, `copyPlaneYUV2TightlyBuffer` 产出) | = `yuv420P10` ✓ |
| D3D11 / Metal | **高对齐**(`<<6`, P010 语义) | 双平面(Y R16 + UV 交错 R16G16) | = `yuv420P10`/P010 ✓ |

## 四、逐腿设计

### 4.1 格式语义层(全平台共编, 零行为变更) — T1

`src/avox/AvoxVideo.h:15`:

```c
XX(yuv422P10, 12, 2, 4, "yuv422P10")   // 平面式 4:2:2 10bit(4B/像素)
```

> 取值 12 = 现最大值 11(`p010`)之后; 比率 (2,4) 与 8bit `yuv422P` 同形(= 2 samples/pixel),
> 使 `getYuvFrameSize = rowPitch(2w) × h × 2 = 4wh` 正确。

**必须逐个消费点核对**(`AVOX_MAP_YUV` 全仓消费点仅 4 处, 全在 `Video.cpp`):

| 消费点 | 420P10 现状 | 422P10 需要 |
|---|---|---|
| `getYuvTypeStr`(:51) | 宏自动 | 宏自动 ✓ |
| `getYuvFrameSize`(:55) | 宏比率自动 | 宏比率自动(4wh)✓ |
| `bVPlaneFormat`(:69) | 显式列 `yuv420P10`/`p010` | **加 `yuv422P10`** |
| `yuv2ImageFormat`(:76) | 420P10/p010 → r16, `height = h*3/2` | **加分支 → r16, `height = 2h`**(Y h 行 + U/V 各 h/2 行, 按 width 连排) |
| `image2YUVFormat`(:125) | 420P10/p010 → `height = imH*2/3` | **加分支 → `height = imH/2`**(2h → h) |
| `bTightlyPacked`(:158) | 列 `yuv420P` | **加 `yuv422P10`**(uvWidthDiv=2, uvHeightDiv=**1**) |
| `copyPlaneYUV2TightlyBuffer`(:194) | 420P10: Y 行距 `2w`, UV `uv_pitch=w, uv_height=h/2` | **加分支**: 同左但 `uv_height = h`(VK 腿用) |
| `image2YUVFrame`(:307) | 420P10: `uvPitch=rowPitch/2, uvHeight=h/2` | **加分支**: `uvHeight = h` |

`src/avox_ffmpeg/FFHelper.cpp`:

```c
// ffYuvType(:314)

// getFFVideoFormat(:452)
case YuvType::yuv422P10:     return AV_PIX_FMT_YUV422P10LE;
```

**影响面四件套**(沿用 HDR 稿 §6.1 纪律): ①枚举 ②上表消费点 ③**SWIG 重生成**(`swig/csharp/files/YuvType.cs`
与 `swig/nodejs/files/commonJAVASCRIPT_wrap.cxx` 逐值枚举, 随构建重生成) ④文档(`AvoxVideo.h` 注释 + 本稿)。

**必配单测**: `tests/test_videobuffer.cpp` 已有 P010 装箱契约用例, 照此加 422P10 用例 —— 断言
`getYuvFrameSize == 4wh`、`yuv2ImageFormat.height == 2h`、`image2YUVFormat` 往返一致、
`copyPlaneYUV2TightlyBuffer` 出口字流按 `[Y|U|V]` 紧排。

> ⚠️ **陷阱**: `AVOX_MAP_YUV` 的 group/groupsize 语义在各消费点**不自洽**(注释写「每像素字节系数」,
> 而 `getYuvFrameSize` 实际按 `rowPitch(字节) × height × 比率` 算; 对 8bit 恰好等价, 对 10bit 靠
> 「样本数/像素」值兜住)。**加新类型前必须逐个消费点实算并用单测钉死**, 别照抄 8bit 422 的直觉值 ——
> 该注释记着一次「误写 3 → 高估 2 倍 → 黑屏」的历史。

### 4.3 Vulkan 腿 — T4+T5

**新 shader `glsl/source/yuv2rgbaV6.comp`**: 以 V5 为底, **只换入口函数**(V5 已把「读函数/色彩尾段」分离,
注释原话「接入新格式只加读函数, 色彩尾段共用」):

```
void yuv422p10(){
  每线程处理 2x2 四个输出点(与 V5 同 dispatch 形状)
  Y : read10bit(ivec2(x*2+{0,1}, y*2+{0,1}))          // 与 V5 完全一致
  UV: uvHeight    = height          ← 唯一改动(420 是 height/2)
      uvPlaneSize = (width/2)*height
      uLinearPos  = width*height + uv.y*uvWidth + uv.x
      vLinearPos  = uLinearPos + uvPlaneSize
      上下两行各取一组 (u,v), 共 4 次 read10bitUV
  dvProcess / processColor 原样复用
}
```

`read10bit` / `read10bitUV` / `processColor` / DV 全链**零改动**(字行宽恒 = 帧宽, 与 422 无关)。

> **⚠️ 还要一个 HDR 变体(实施时补的设计点)**: `forceHDR` 时 420P10 走的是 `yuv2rgbaHDR.comp`
> (outTex **rgba16f**、forceHDR 分支线性化到 1.0=SDR 白 80nit), 422 也得有 —— 否则 422 片在
> `forceHDR`/`vkHDR` 下会落回 V6 的 rgba8「PQ 码原样」路径, 与 420 行为不一致。
> 做法**不复制第二份源码**(250 行重复必然漂移), 而是**一份源码出两变体**: 源码里 `#if YUV2RGBA_HDR`
> 只包住两处差异(`outTex` 绑定 `rgba8`/`rgba16f` + forceHDR 分支), 索引里写两行 ——
> `yuv2rgbaV6.comp` 与 `yuv2rgbaV6.comp yuv2rgbaV6HDR.comp YUV2RGBA_HDR=1`,
> 与 `input.comp`/`morph1.comp` 的既有宏做法同款(⚠️ 是 `#if MACRO`, 不是 `#ifdef`)。

**`VkYUV2RGBALayer::onInitLayer`(:89)** 加分支(仿 420P10 段 :119):

```cpp
else if (paramet == YuvType::yuv422P10) {
  path = "glsl/yuv2rgbaV6.comp.spv";
  inFormats[0].imageType = ImageType::rgba8;   // 字节视图, 与 V5 同
  // outFormats[0].height 无需改: 字节视图高 = 字行数 2h / 2 = h = 输出高
  sizeX = divUp(outFormats[0].width,  2 * groupX);
  sizeY = divUp(outFormats[0].height, 2 * groupY);
}
```

**`VkInputLayer` 零改动**: `onInitLayer`(:61)的 r16→rgba8 字节视图逻辑对字行数 `2h` 天然成立
(`wordRows = 4wh/(2w) = 2h` → 图高 `(2h+1)/2 = h`), 并会打 `10bit byte-view: words wx2h -> rgba8 wxh` 日志供验收。

**格式传播零接线**: `VkVideoRender.cpp:812` 每帧 `if (yuv2RGBA->getParamet() != frame.format.type) updateParamet(...)`
—— 帧侧 `YuvType` 自动下发。

**编译纪律**: 改 `.comp` 后**必须手动** `python glsl/compileglsl.py`(cmake 不含此步), 并在 `glslindexcurrent.txt` 登记
(同 HDR 稿 §6.3 G10 口径)。

> **收益面**: 这一条落完, **Win/mac/Linux/Android 只要走 VK 腿就能出画**(Android/Linux 恒 VK),
> 是投入产出比最高的一步。

### 4.4 Windows D3D11 CS — T7

**纹理**: 现 `inTexture`(单纹理双平面视图)在 P010 下 UV 面高恒 `h/2`, **表达不了 422** ⇒ 新增第二张纹理:

- `inTexture`(Y): `DXGI_FORMAT_R16_UNORM`, `w × h`
- `inTextureUV`(UV): `DXGI_FORMAT_R16G16_UNORM`, `w/2 × h`

**上传**(`uploadCpuPlanes` :624): 新增 `b422` 分支 —— Y 逐行 `<<6`(与 P010 同款高对齐),
UV 逐行交错 `<<6`, 唯一差别是 **UV 循环跑 h 行(不是 h/2)**。

**CS**(`kShaderBody` :132): `constData.yuvType` 加值 `2`, `main` 加分支:

```
} else if (yuvType == 2) {          // 4:2:2 10bit
  o1..o4 = p422Point(...)           // 与 p010Point 逐字相同
}
```

`p422Point` = `p010Point` 的**唯一改动**: `uvTex.Load(int3(pix.x / 2, pix.y, 0))` —— UV 行号**不除 2**。

**建图守卫**(:532)放开 `yuv422P10`; `cpuInFormat`(:62)需能表达「双纹理」, 建议改为记录 `YuvType`
(或加 `bCpu422` 标志), 别再用单一 `DXGI_FORMAT` 承载。

**HDR 零新增**: `processColor` / DV / 直通分支与输出格式翻转(R1 既有机制)全部照旧。

### 4.5 Apple Metal — T8

> **定位**: 本腿是 **软解兜底腿**。mac 的**首选**是 §4.7 的 VT 硬解直通腿(T8b) —— VT 可用时根本不走 CPU 帧;
> 但 VT 不可用/失败时选型链会回软解, CPU 帧仍需本腿的 422 上屏路径。两条都要做。

**关键有利事实**: 既有 `fragmentShader`(`MetalRender.mm:245`)对 Y/UV **用同一个归一化 `texCoord` 采样**。
4:2:2 与 4:2:0 的差别只体现在**纹理尺寸**上 —— UV 纹理高取 `h` 时, 同一 `texCoord` 自动落在正确的色度行。
⇒ **片元着色器零改动**(`params.tenBit` 那套 P010 数学照用)。**§4.7 的 VT 硬解腿靠的是同一机制。**

**做法(实施时定的更省路子, 已落 `71ae311`)**: **不自建 MTLTexture 对**, 而是**直接建 x422 的
CVPixelBuffer**(`kCVPixelFormatType_422YpCbCr10BiPlanarVideoRange`)—— 填好 Y(`<<6`)+ UV 交错
(`<<6`, **h 行**)后整条复用既有 `renderCVPixelBuffer`: 既不用新绘制入口, 也不用管纹理生命周期。
而且这一组格式判定**与 §4.7 的 VT 硬解腿完全共用**(VT 输出的就是 x422 pb)⇒ 两条腿的 Metal 改动
是同一份(即 §4.7 那个「四处」清单)。

- ⚠️ **一处未验证假设**: `CVPixelBufferCreate` 是否接受 x422(Apple 文档视其为可用 biplanar 格式,
  但未实测)。**若实际不支持**, 退回原方案: 自建 `MTLTexture` 对(Y `r16Unorm` w×h / UV `rg16Unorm`
  w/2×h, IOSurface-backed)+ 新绘制入口绑两纹理(那时才需要复刻 `renderCVPixelBuffer` 的绘制段)。
- `publishCpuFrame` 的 CPU 读回面**已落地**(`afe777f`): 交付低对齐 `yuv422P10`, packed 按 `height*2` 而非
  `height*3/2`, 且交付类型尚无对应 `YuvType`)—— 别静默按 4:2:0 约定打包出错图。归 §八 第 4 条挂账。
- `fragmentShader` **零改动**(同一归一化 `texCoord`, UV 纹理高取 `h` 时自动落对色度行)。

**HDR/EDR 零新增**: 输出域与层翻转(`applyLayerHdrConfig` / `vaildAndInitGraph` 过界)照旧。

### 4.6 Android / Linux — 不做, 由 VK 覆盖

- **Android**: `EglVideoRender` 恒 VK 车道(HDR 稿 §1.3), CPU 帧由 VK 全接 ⇒ **VK 腿落完即覆盖**, 无需 EGL 原生 422 路径。
- **Linux**: 唯一窗口是 `VkWindow`(HDR 稿 §6.3 表)⇒ 同上。
- 若将来出现「原生腿强制」的 Android 场景, 兜底 = 在 **GPU 内**做一次 4:2:2→4:2:0 10bit 垂直降采样
  (两行平均, 在输入层 CS 内, **不是 CPU**), 复用全部既有 420P10 路径 —— 代价是色度垂直分辨率减半。
  **本稿不实施, 只记账**(见 §八 第 2 条)。

### 4.7 Apple VT 硬解 ProRes(直通腿, 不经 VK) — T8b

**可行性(已核码)**: FFmpeg 有 `prores_videotoolbox` hwaccel(`videotoolbox.c:1474`)⇒ 这条 API 路是通的;
Apple Silicon 有**专用 ProRes 解码硬件**(Intel Mac 走系统软解, 仍可用, 只是没加速)。

**VT 输出格式**: `kCVPixelFormatType_422YpCbCr10BiPlanarVideoRange`(`'x422'`)—— 双向佐证:
`libavutil/hwcontext_videotoolbox.c:69`(`x422 ↔ AV_PIX_FMT_P210`)与 `libavcodec/videotoolbox.c:1259`
(10bit 4:2:2 → `AV_PIX_FMT_P210`)。

**为什么与既有 Metal 链天然兼容 —— 这就是「和 420 10 一样直通、不经 VK」的依据**:

| 事实 | 后果 |
|---|---|
| `x422` 是 **16bit 字装 10bit、双平面、色度全高** | 既有 `fragmentShader` 用**同一个归一化 `texCoord`** 采 Y/UV ⇒ UV 平面高 = h 时自动落对色度行 ⇒ **着色器零改动**(与 §4.5 同一机制) |
| `x422` 是 **VideoRange** | 既有 `params.tenBit` 分支正是 limited-range 展开(`(y·k − 64/1023)/(876/1023)`)⇒ 数值口径直接对上(ProRes 本就 video-range 编码) |
| 走既有 `renderCVPixelBuffer` 硬解链 + EDR 层翻转 | 与 420P10 硬解**同一条路**, HDR 直通/tone map/呈现面翻转全部照旧 |

⇒ **比 T8 更省**: 不用自建纹理对、不用 CPU 上传(省掉 4K 422P10 的 ~795 MB/s CPU 解码 + 上传)。

**⚠️ 卡点: profile 四字节 —— 2026-10-03 下午上 mac 实测后推翻了上午的推断**

VT 建会话必须知道 ProRes profile 才能定 `kCMVideoCodecType_AppleProRes*`(`apch`/`apcn`/`apcs`/`apco`/`ap4h`/`ap4x`)。
FFmpeg 自己的做法是取容器 `codec_tag`(`videotoolbox.c:940`), `default` 分支只告警不兜底 ⇒ `cm_codec_type = bswap32(0) = 0` ⇒ 失败;
而**本片 MKV 的视频轨无 CodecPrivate**(偏移 641 那个是 **Vorbis 音轨**的), 六个 fourcc 全文件不存在 ⇒ 照搬必失败。

**❌ 上午的推断(已证伪)**: 曾据源码认为「读 `st->codecpar->profile` 即可」—— 依据是
`proresdec.c:141-161` 的 switch 会写 `avctx->profile`, 再由 `parameters_from_context()`
(`avcodec_parameters_from_context`, `codec_par.c:152`)拷回 `codecpar->profile`。
**下午 mac 实测打脸**: 引擎日志打出 `[FF][prores] Unknown prores profile 0`。回查 `proresdec.c:162`
—— 那个 switch 的条件是 **`avctx->codec_tag`**(容器 fourcc), **不是帧头**;
告警里打印的 `%d` 也正是 `avctx->codec_tag`。

⇒ **`codecpar->profile` 与 `codec_tag` 是同一个死路**(本片 codec_tag=0 ⇒ profile=UNKNOWN), 上午那条路**作废**。

**✅ 修正后的取值顺序**(MP4/MOV 有 fourcc ⇒ ①; 本片这类无 CodecPrivate 的 MKV ⇒ 只能 ②):
1. `codecpar->codec_tag`(有则用, = 精确 fourcc);
2. **默认 `apch`(422 HQ)** —— 并按解出的像素格式收紧: `YUV422P10LE` → 422 家族(`apch`),
   `YUV444P12LE` → 4444(`ap4h`)。因为 VT 本身会读帧头, 声明值主要用来定 `kCMVideoCodecType`,
   实际 profile 以码流为准 —— **但这一点须在 mac 上实测确认**(声明与实际不符时 VT 是否仍解)。

> ⚠️ 教训: 源码推演 ≠ 实测。上 mac 后第一条引擎日志就把这条推翻了 —— 凡是「引擎会怎样」的判断,
> 优先写几十行小程序实测(本次即靠 `x422probe` + `engine_play_test` 一次验掉两个假设)。

**其余改动点**:

- `bMustVcc = false`(ProRes 无 avcc/hvcc, 同 VP9 口径);
- 格式描述走 `CMVideoFormatDescriptionCreate`(`IOSVDecoder.mm:331/348` 既有 VP9/AV1 路线);
- `streamBitDepth = 10`; `dstFmt = kCVPixelFormatType_422YpCbCr10BiPlanarVideoRange`(`:377/389` 按 codec 分支);
- **Metal 侧共四处改动(⚠️ 不是三处, `:1159` 那处最易漏)**:
  1. `:665` —— `publishCpuFrame` 算 `bTenBit`(决定 CPU 读回交付类型 `p010`/`nv12`);
  2. `:672` —— 同函数的**拒绝闸**, 不在白名单就 `warn "cpu yuv out not support pixel format"` 并丢帧;
  3. `:1141` —— 硬解腿真正设 `params.tenBit`(shader 选 8bit 还是 10bit 分支);
  4. **`:1159` —— UV 平面纹理创建的高度 `height / 2`**(当前硬编码 4:2:0 的半高色度)。
     **`x422` 的色度平面是全高 `height`**, 必须按格式取。
  ⚠️ **为什么第 4 处最危险**: 前三处漏改的症状是**被拒/全黑**(一眼看出); 第 4 处漏改会建出一张**半高**色度纹理
  ⇒ 色度被垂直压缩/错行 ⇒ **画面颜色错乱但仍出画**, 极易被误判成"色彩空间/矩阵配错"而往错方向查。
  四处的改动都只是把判定条件加上 `kCVPixelFormatType_422YpCbCr10BiPlanarVideoRange` /
  `...FullRange`(`xf22`), 外加第 4 处的高度改按格式取;**`fragmentShader` 本身零改动**。
- **CPU 读回面的 packed 约定要同步**: `:693` 的「`r8/r16 + height*3/2`」是 4:2:0 约定, `x422` 应为
  **`height*2`**(Y h 行 + UV h 行); 归 §八 第 4 条(读回面挂账)。
- 会话未要求硬解(`decoderSpecification = nullptr`, `:399`)—— Apple Silicon 上 VT 通常仍选硬件 ProRes 引擎;
  若实测落软解, 再加 `kVTVideoDecoderSpecification_EnableHardwareAcceleratedVideoDecoder`。

**CPU 读回面**: 呈现不需要新 `YuvType`(pb 直进 Metal); 但截图/缩略图/`getCpuFrameBuffer` 需要交付类型
⇒ 复用 `yuv422P10`, 归一化时把 x422 高位对齐 `>>6` 成低对齐(与 `p010→yuv420P10` 同款)。
**✅ 已落地(`afe777f`)**: 按上面这条建议实现 —— `publishCpuFrame` 交付低对齐 `yuv422P10`,
packed `[Y(w*2×h)][UV(w*2×h)]`(行距 `w*2`, 总高 `2h`), 逐样 `>>6`(10bit 无损)。
**没有新增 `YuvType::x422`**: `yuv422P10` 是既有类型, 全仓布局助手/消费者都认它, 不必再教每个
switch 一个新值。实测 `hard=1` 得 207 帧 / 34.5fps / 零卡顿(输出 3840x4320 = `2h`, 与新约定一致)。

#### T7 验证受阻 → 已解: Dx11Window 从不派发 onRenderWindow(既有缺口, 已修)

T7 代码落完后用**带窗口的探针**(建真窗口 + `setSurface(hwnd)` + `setVulkan(false)` + 周期
`screenShot`)验证, 首轮 **15 次截图全失败**, 日志每帧刷:

```
warn: Dx11CSVideoRender.cpp:593 initGraphCpu dx11 cs cpu frame no window device, skip
```

**根因(已核码, 结构性)**: `Dx11CSVideoRender::initGraphCpu` 的 D3D11 设备取自
`targetWindow->getRenderContext()`, 而 `targetWindow` 只由 `VideoRender::renderWindow(Window*)` 写入,
其唯一调用点是 `WindowRender::onRenderWindow()`(WindowRender.cpp:436-437)。而 `onRenderWindow` 由
**窗口自己 dispatch**(`IWindowOb::onRenderWindow`):

| 窗口 | 是否派发 |
|---|---|
| `VkWindow` | ✅ `VkWindow.cpp:251` |
| `Dx12Window` | ✅ `Dx12Window.cpp:193` |
| **`Dx11Window`** | ❌ **全文件无 `IWindowOb`/`onRenderWindow`/`dispatch`** |

⇒ **D3D11 原生腿上 `targetWindow` 恒为 null ⇒ CPU 帧腿(软解)恒失败**。只影响 CPU 帧路径
(硬解 GPU 帧走 `renderToTexture`, 设备来自解码上下文, 不需要窗口)—— 而 **ProRes 恰恰恒是 CPU 帧**。
这也解释了 HDR 稿 G9 为何一直停在**「代码就绪但未验」**: 它从未真正跑通过。

**修复(已落, `888c156`)**: `Dx11Window::onTickWin()` 里补 `dispatch(&IWindowOb::onRenderWindow);`
(`Window : public Observer<IWindowOb>`, 方法现成), 位置在 `if (!sharedTexture) return;` **之前**
—— 首帧正是靠它把窗口交给渲染器, 渲染器才能建图产出共享纹理(否则先有鸡, 永远到不了下面)。
**无死锁**: 观察者侧(`renderWindow` → `setTargetWindow`)只写指针 + 读 `hdrPassthroughActive()`
原子位, 不取 `mtx`, 与同处调用的 `applyPendingHdr` 同理。
**副作用(正向)**: 顺带激活该腿此前恒空跑的 `checkTargetPassthrough()` 统一检查点(HDR §4.2),
即 R1 的直通重建逻辑在 D3D11 腿上**首次真正生效**。

**T7 验证结果(修复后, 带窗口探针)**:

#### 「没硬解 ⇒ 一定走 VK」是个常见误判(2026-10-03 澄清)

**误判**: "ProRes 在 Windows 没有硬解 ⇒ 产出的是 CPU 帧 ⇒ 那 Dx11CSVideoRender 的 422 处理就用不到, 交给 Vulkan 就行"。
**正解**: "CPU 帧"只说明**解码侧**没走硬解, **不决定渲染侧走哪条腿**。CPU 帧会喂给**当前 lane 的渲染器**:

- **lane 由宿主 panvox 定档**(HDR 稿注释列: "开播定道 **`trc∈{pq,hlg}` + HDR 屏闸 → lane=1**"), 与解码成败解耦
  (HDR 稿 §推论: 硬解失败时 lane=1 **就地落软解**, 不再换道)。
- 本片 `trc = PQ`: **HDR 屏 → lane=1 → 原生 D3D11 吃 CPU 帧 = T7**; **SDR 屏 → lane=0 → VK = T6**(HDR 稿场景 2/4)。
- ⇒ **T6 与 T7 各管一种呈现面, 缺任一个都会在对应屏况下黑屏**。两条今日均实测出画。

**同理, macOS 侧也不是"只有 VT 硬解才用 Metal 422"**: 本机 mac 实测 `canVulkan: vulkan loader not available` ⇒ 走 Metal(探针态)。
⚠️ **订正(2026-10-03 晚, 二次核对)**: 探针那两次 `loader not available` 是**免窗探针自身搜索路径缺 MoltenVK** ——
`ept_mac` 无 rpath, `DYLD_LIBRARY_PATH` 只给了 `<install>/Release`, 而 MoltenVK 在上一层 `<install>`(同一 exe 补路径即通)。
**这不等于 mac 无 Vulkan**: 部署版 panvox.app 走的就是 VK 腿(`use vulkan:1` + `VkWindow initVkSurface` +
swapchain 2560x1440, `volkInitialize failed` 0 次); iOS 真机同样在跑(2a15230 构建, `attach window lane=vulkan`)。
`VkContext.cpp` 的 MoltenVK 引导块是 **iOS 专用**(mac 不需要 —— 包内 dylib 走 volk 裸名候选), 原守卫写的
`IOS` 宏全仓未定义 ⇒ 死代码, 已修(`b91ecb8`: 守卫改 `TARGET_OS_IPHONE`, 同批 `LinkVulkan.cmake` 拷库前解软链)。
⇒ mac 探针要验 VK 腿, 运行时须把 `<install>` 一并加入 `DYLD_LIBRARY_PATH`;
而 Metal 的 422 改动分两块 —— **T8 = 软解兜底**(`renderCpuFrame` 自建 x422 pb, **当前生效, 今日实测在跑**),
**T8b = VT 硬解**(VT 直接吐 x422 pb, 跳过建 pb, 但**共用同一组格式判定**)。

**读回面(2026-10-03 晚补, `afe777f`)**: 原先 x422 的 CPU 读回面是**明确拒绝 + 落日志**
(§八 第 4 条挂账), 导致硬解路径的离屏读回(screenShot / enableYuvOut / 离屏哨兵)拿不到帧。
本次落地: `publishCpuFrame` 交付**低对齐 `yuv422P10`**, packed 布局 `[Y(w*2×h)][UV(w*2×h)]`
(行距 `w*2`, 总高 `2h`, 与 `yuv2ImageFormat(422P10)` 的 r16 视图一致); pb 里是 `<<6` 的高位对齐,
故逐样 `>>6`(10bit 无损), 不能像 x420 那样零拷贝。
**选低对齐而非新增 `YuvType::x422`**: `yuv422P10` 是既有类型, 全仓布局助手/消费者(含 T2 布局单测)
都认它, 不必再教每个 switch 一个新值。

**端到端实测(读回面落地后, `hard=1` 请求硬解, Metal 原生腿)**:

```

         pos=17643/74866ms stalls=0 maxFrozen=0ms state=3(playing)
```

输出 `3840x4320` = packed `yuv422P10` 的 r16 视图高(`2h`)⇒ 读回按新约定交付 ✓;
**207 帧 / 34.5fps / 零卡顿** ⇒ **VT 硬解全链路(会话→解码→Metal 渲染→读回)打通**。
（软解腿 `hard=0` 同口径对照: 202 帧 / 33.7fps —— 两者相当, 硬解的价值在 CPU 占用, 不在帧率。）

## 七、风险与陷阱

| 风险 | 说明 | 缓解 |
|---|---|---|
| **`AVOX_MAP_YUV` 语义不自洽** | group/groupsize 在 `getYuvFrameSize` 与 `yuv2ImageFormat` 两处口径不同, 历史上已因此「高估 2 倍 → 黑屏」一次 | §4.1 逐点实算 + 单测钉死 |
| **上传带宽 / CPU** | 4K 422P10 = **31.6 MiB/帧**, 23.976fps ≈ **795 MB/s**; D3D11/Metal 的 UV 交错 + `<<6` 是逐样本循环(4K 每帧 ~16.6M 次)。⚠️ **Windows 侧没有硬解退路**(§2.4: DXVA 无 4:2:2 模式、无 ProRes 解码器), 该风险**只在 Windows 成立**; mac 有 VT 硬解(T8b)不背这个 | 既有 420P10 已跑同款循环(1.5wh 样本)证明可接受; 若剖析成瓶颈 → 改**低对齐**(Y 退化为纯 memcpy)+ 着色器常数分支, 或 UV 拆双纹理免交错 |
| **`uyvy422_10B` 与新类型混淆** | 同名「422 10bit」, 一个打包一个平面, 布局完全不兼容; 误映射 = 花屏/绿屏(`AndCommon.cpp:45` 已有同类教训注释) | 类型名 `yuv422P10` 与打包式 `uyvy422_10B` 显式区分; 上传/读取两处注释互指 |
| **Metal 无 CVPixelBuffer 4:2:2 类型** | 必须自建 `MTLTexture` 对, 偏离既有 `renderCVPixelBuffer` 单一路径 | 复用既有管线与 shader, 只替换纹理来源; 纹理必须 IOSurface-backed |
| **枚举新增的连带面** | SWIG 两处逐值枚举文件需重生成; 老宿主读到未知值 12 的行为 | 值只增不改不删; 未知值宿主按 `other` 处理 |
| **DV 链与 422 叠加** | 422P10 + DV(ProRes 不带 DV, 但理论上可 mux) | V6 复用 V5 的 `doviEnable` 分支, 天然覆盖 |
| **VT 拿不到 ProRes profile**(T8b) | VT 建会话要 fourcc, 而 MKV 封装的 ProRes 容器**不给**(视频轨无 CodecPrivate); 照搬 FFmpeg 取 `codec_tag` 会得 0 ⇒ 会话失败 | §4.7 方案 1: 用 FFmpeg prores 软解解一帧读 `avctx->profile` → 映射 fourcc; 兜底方案 3(默认 `apch`) |
| **VT 输出 x422 但 Metal 只认 420**(T8b) | Metal 侧**四处**格式判定只列 `420YpCbCr10BiPlanar*`: `:665`/`:672`(CPU 读回判定与拒绝闸)、`:1141`(`params.tenBit`)、**`:1159`(UV 平面纹理高 `height/2`)** | 四处一并加 `x422`/`xf22`, 第 4 处高度改按格式取(`x422` 取 `height`)。**漏前两处 = 丢帧; 漏第三处 = 按 8bit 数学解 10bit 数据 = 错色; 漏第四处 = 色度垂直错行 = 颜色错乱但仍出画(最隐蔽)** |
| ~~**`Dx11Window` 不派发 `onRenderWindow`**~~(既有缺口) | ~~D3D11 原生腿上 `targetWindow` 恒 null ⇒ CPU 帧腿(软解)恒失败~~ | ✅ **已修 `888c156`**(一行补 `dispatch`, 见 §5.7); 顺带激活该腿此前恒空跑的 `checkTargetPassthrough` |
| **12bit 4444 未覆盖** | `ap4h`/`ap4x` 是 12bit 4:4:4, 会落 `YuvType::other` → 同样「没画面」 | **用户决定暂时不做**(§八 第 1 条); 复发时照 §4.1 同法加 `yuv444P12` |

## 八、拍板结论与挂账

**已拍板(用户 2026-10-03)**: ①ProRes 4444/4444 XQ **暂时不做** ②**Metal 原生腿要做**(三腿一起)
③**真 4:2:2**(不做 GPU 降采样兜底) ④**Apple VT 硬解 ProRes 要做**, 且**直通不经 VK**(同 420P10 硬解路)。
⇒ 施工范围与顺序见 §五。

**挂账(未做, 记录在案)**

1. **ProRes 4444 / 4444 XQ(12bit 4:4:4)**: 同一族的「没画面」(`ap4h`/`ap4x` → `AV_PIX_FMT_YUV444P12LE` 落 `YuvType::other`)。
   用户决定**暂时不做**。⚠️ 复发提示: 用户拿到 4444 母版会再报一次**一模一样**的 bug —— 届时照 §4.1 同法加 `yuv444P12`
   即可(布局助手与三腿路径同构, 增量很小)。**恢复本项前先回读本节。**
2. **GPU 内 4:2:2→4:2:0 降采样兜底**(§4.6): 用户选了真 4:2:2 ⇒ 不实施。仅在将来出现「原生腿强制」的
   Android/EGL 场景时作为备选(代价: 色度垂直分辨率减半)。
3. **`getFFVideoFormat(uyvy422_10B)` 不对称**(§2.3): 反向表映到 `AV_PIX_FMT_YUV422P10LE`(**平面**),
   与 V3 期望的打包布局对不上, 且正向表无对应项。**独立小提交** —— 动手前先确认全仓无消费方。
4. **VT 硬解腿的 CPU 读回面**(§4.7 末): 呈现不需要新 `YuvType`(pb 直进 Metal), 但截图/缩略图/
   `getCpuFrameBuffer` 需要交付类型 ⇒ 建议复用 `yuv422P10` + 归一化 `>>6`(同 `p010→yuv420P10` 款);
   ⚠️ 且 `publishCpuFrame` 的 packed 视图约定(`MetalRender.mm:693`)当前是 4:2:0 的 **`height*3/2`**,
   `x422` 须改 **`height*2`**(Y h 行 + UV h 行)。**本次先只做呈现, 读回面另账。**
5. **Windows 侧 GPU 解码备选: FFmpeg `prores_vulkan`(compute 路线)—— 已评估, 未采用**: 它是把 ProRes 的
   VLD 熵解码 + IDCT 做成 Vulkan compute shader 在 GPU 通用算力上跑(§2.4 ③), **不是专用解码硅块**。
   未采用的四条理由: ① 当前 FFmpeg 构建**没编它**(`build_ffmpeg.py:149` 的 `MINIMUM_HWACCELS` 只有
   h264/hevc/vp9/av1 的 `d3d11va` 与 `vulkan`), 要动就得改白名单 + 重编 FFmpeg(四平台脚本同步);
   ② 引擎需把 `AV_PIX_FMT_VULKAN` 帧接进自有渲染链, 与现有 `VkDecoder`(Vulkan Video 固定功能)是**两套**;
   ③ 省 CPU 但吃 GPU 通用算力, **功耗/延迟不等同专用硬解**;
   ④ **只解 ProRes**, 解决不了「Windows 上一切 4:2:2 10bit 都得软解」这件事。
   ⇒ 若将来 Windows 4K 422 软解确实成瓶颈, 再回来评估本条(先看 §7 的性能实测数据)。
6. **上传路径性能优化**(§7): 若 4K 剖析显示 D3D11/Metal 的 UV 交错 + `<<6` 成瓶颈 → 改**低对齐**
   (Y 退化为纯 memcpy)+ 着色器常数分支, 或 UV 拆双纹理免交错。**先测再改, 不做预防性优化。**
