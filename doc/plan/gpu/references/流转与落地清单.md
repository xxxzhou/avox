## 三、超 RGBA8 HDR 流转

### 3.1 格式与域字典

| 格式/域 | 语义 | 出现位置 |
|---|---|---|
| P010 / NV12 | 硬解输出纹理, PQ 码值 0-1 归一化 | 解码器→平台渲染器 |
| yuv420P10 | 软解 CPU 10bit 平面, PQ 码值 | 解码器→VK yuv2rgba 层 / Metal renderCpuFrame |
| R10G10B10A2_UNORM + G2084 | **Win 直通域**: PQ 码原样 | Win CS 输出(R1 新增)与 Win 交换链(已有) |
| RGBA16Float 扩展线性 | **Apple 直通域**: 线性, 1.0=SDR 白; EDR extended linear ITUR-2020 | Metal 层/管线(MetalRender.mm:310/737) |
| VK_FORMAT_R16G16B16A16_SFLOAT + VK_EXTENDED_SRGB_LINEAR | **VK 直通域**: 同 Apple 语义 | VkWindow::setHdrPassthrough(VkWindow.cpp:498); **永不启用 VK_EXT_swapchain_colorspace**(AMD 崩 0xC0000374) |
| R8G8B8A8 / BGRA8 | SDR 域 | tone map 终点/SDR 呈现 |

- PQ 是非线性 HDR 编码, 动态范围全在 0-1 码值里——**8bit 中转不破坏「能播」**(9/30 a/b+10/1 发灰修复后肉眼确认「和系统对上了」), 代价=梯度精度(暗部/高光可 banding)。R1 去 8bit 中转是为画质, 非可行性。
- Win=PQ 码域 / Apple·VK=线性域(1.0=SDR 白): 域不同是呈现面差异不是处理差异, 「值原样呈现」语义三平台一致。

### 3.2 现状流转(逐平台逐腿)

**Win lane=1(直通链)——已转, =G3**: P010 → Dx11CSVideoRender CS(processColor: forceHDR=PQ 码原样 / follow=tone map 锚线性+Reinhard) → **R8G8B8A8 共享纹理**(createProgram 唯一输出创建点写死, Dx11CSVideoRender.cpp:440, 无 HDR 分支) → Dx11Window blit(像素着色器纯采样直出, 无色彩处理) → 交换链 R10G10B10A2+G2084 / SDR=BGRA8。`setHdrMode` 只刷 UBO 不重建图——输出格式无从跟随 HDR 态(重构动因)。

**Mac lane=1(直通链)——未转, 16F 全程=统一语义样板**: CVPixelBuffer → CVMetalTextureCache 直进 shader(无中间 rgba8) → 管线色附随直通态翻转(RGBA16Float/RGBA8Unorm, MetalRender.mm:737) → CAMetalLayer(applyLayerHdrConfig :310 层翻转+EDR)。翻转检测在 vaildAndInitGraph 每帧过界(wantF16 != bF16Pipeline → 层+管线同帧切+releaseGraph, :354; bResetFlag 原子读清消费是基类契约范例 :356)。软解 CPU 帧经 renderCpuFrame(:417)包装 P010 pb 进同一管线。iOS: `MetalWindow::setHdrPassthrough` 恒不受理(无 NSScreen)。

**进 VK 的硬解帧(三平台 lane=0)——已转, 一律 rgba8**: 平台渲染器先转 rgba8 → VkInputLayer import(VkInputLayer.cpp:297; Win=DX11 共享纹理按 GetDesc **格式自适应重建** / Android=GLES texture id+EGLContext 判重 / mac=Metal IOSurface) → VK 合成 → VkWindow。→ **VK 的 HDR 处理对硬解帧不生效的根因**: 输入早被平台渲染器转成 8bit。

**NT 共享通路的边界(2026-10-01 核代码)**: `Dx11SharedTex` 这条通路**生产端与消费端都在 dx11 目录内, 外面拿不到**(类型系统保证, 不需新增隔离接口):
- **生产端唯一出口**: `Dx11CSVideoRender::getGpuContext()` 返回私有成员 `outSharedTex.get()`(Dx11CSVideoRender.hpp:73)——`unique_ptr` 私有成员, 构造参数不外露;
- **消费端天然闸**: `Dx11Window::renderContext` 先 `dynamic_cast<IDx11Context*>`, 再按 `bInteropTexture()` 分流(Dx11Window.cpp:150-160)——`Dx11SharedTex` 返 **true**(Dx11SharedTex.hpp:79)被收进 `sharedTexture`; 普通 `IDx11Context` 返 **false**(Dx11Context.hpp:23)被静默忽略。**既有设计, 非新加**;
- **唯一外部接触面**: `VkWinImage::updateInputContext`(VkWinImage.cpp:177)在 context 是 `Dx11SharedTex` 时置 `interopType = inputNt`(直读不拷贝), 只在 `bVulkan` 时被喂入(WindowRender.cpp:193)。**这条路正是链F 自己**; lane=1 时该接触面不存在。
⇒ 「把 10bit NT 共享限定在 dx11 内部」的诉求**现状已满足**; 要做的不是加锁, 而是**把格式描述补全**(§6.1 三处映射), 见 §6.3 通用性三层。

**VK 软解腿——16F 被盖回=G4**: CPU yuv420P10 → VkYUV2RGBALayer(onInitLayer forceHDR 分支设 rgba16f 选 yuv2rgbaHDR.comp, 但**共用归一化段无条件 `outFormats[0]=rgba8` 盖回**——HDR 变体写出的 >1 线性值进 8bit 被钳 1.0, 高光全丢) → 合成 → 窗。SDR=V5.comp tone map(V5 通吃 p010 上传归一化)。CPU 读回按输出纹理格式走, 输出变 10bit/16F 后需防护(§3.4)。

**Android / Linux**: Android 恒 VK 车道: EglVideoRender NV12→rgba8(:435)+自有 uHdrMode tone map 分支(:95) → VK → VkWindow(Flutter 纹理桥); EGL 无 HDR 呈现面口=G8。Linux: CPU 帧→VK(inputCpuData), 无平台 GPU 导入腿, HDR 不做。

### 3.3 目标流转(六条链)

- **链A 硬解直通(情况1)**: Win `P010→CS(PQ原样)→R10G10B10A2(R1)→交换链 R10G10B10A2+G2084→屏`, 全链 10bit 无 8bit 中转; Mac `P010→shader→RGBA16Float→CAMetalLayer+EDR`(已达标)。
- **链B 软解直通(情况2, 两路等价)**: 原生腿(v2 主路) `yuv420P10→平台渲染器 CPU 腿(mac 已有/G9 补 Win)→RGBA超10→原生窗口超 RGBA8`(与硬解帧同一链); VK 腿(lane=0) `yuv420P10→VK upload→yuv2rgba 16F(修 G4)→16F 域合成→VK FP16 交换链`。
- **链C tone map(情况3/4, =「原来 vulkan 路径」)**: `YUV10→SDR rgba8`(硬解帧=平台渲染器 follow 分支; 软解帧=V5.comp)→VK 合成→SDR 呈现。现状达标, 本重构不动。
- **链D SDR(情况5)**: 常规 lane=0, 零变化。
- **链E 硬解帧×图像处理(降 SDR)**: 硬解帧(HDR 片)→原生 tone map 降 SDR→rgba8 对接面(VkInputLayer)→VK 图像处理→呈现; SDR 片硬解帧直接 rgba8 对接(现状即此)。软解帧×图像处理不走对接面, 直接 YUV 进 yuv2rgba。
- **链F 硬解 HDR 保真进 VK(v2 补, 用户定稿)**: `YUV10→原生 forceHDR 分支把 PQ 码原样写进 rgba8(不做 tone map)→rgba8 对接面→VK 升样层(PQ EOTF→16F 线性)→图像处理/字幕(16F 域)→VK FP16 交换链→HDR 呈现`。
  - 依据: PQ 是非线性压缩, 动态范围全在 0-1 码值里——8bit 载体保住完整动态范围只损梯度精度; Win 链A 就是同一原理在 8bit 中转上成立(9/30 a/b+10/1 发灰修复实证);
  - 定位: 「又要硬解、又要 HDR、又要 VK 图像处理/字幕」的唯一组合路径, 全平台可用(对接面即现有 rgba8 通道);
  - 实现要点: VK 呈现域恒 FP16 扩展线性(HDR10 色空间被禁, §3.1), 升样=显式 PQ EOTF(与 yuv2rgbaHDR.comp 同源); 链A 的「升样」由交换链 G2084 免费完成, VK 必须显式做;
  - **模式映射(v2)**: 链A 用 `forceHDR`(原生直通), 链F 用新增 `vkHDR(3)`(「转 VK 的 HDR 处理」)。vkHDR 是**宿主意图值**——引擎在 `WindowRender::setHdrMode` 入口**按 lane 分岔归一化**(lane=0→折 forceHDR 行为; lane=1→折 follow 并告警, 见 §4.3), UBO/shader 协议仍只见 2, 零协议改动; SWIG 三端随枚举重生成。加值依据: ①枚举本就是宿主意图语言(forceSDR 在引擎无独立分支, 意图值有先例); ②「lane=0+forceHDR」组合无名字正是旧禁令 bug 根源, 命名即防复发; ③升样层键控不依赖新值(按 forceHDR 行为态+输入类型分流)。
  - 代价与缓解: 一次 8bit 量化(PQ 域)——画质仍以链A 为首选; banding 可选 dither 缓解, 另批评估。
- **域交接**: mac lane 往返(Metal↔VK)交接面恒 rgba8 IOSurface。⚠️ 「恒 rgba8」只说载体格式, 没说载荷语义——mac forceHDR 出的是**已 EOTF 的线性**(非 PQ 码), 且 lane=0 时 Metal 画 drawable 而非 IOSurface, 该交接面在 mac 结构上不成立(§6.3「交接面语义核对」)。

### 3.4 过界与过渡(翻转时序 + 竞态 A + 读回防护)

- **翻转时序差(风险等级: 中)**: 交换链由 `applyPendingHdr()` 在渲染线程翻(Dx11Window.cpp:318, 由 `onTickWin` :107 调用; D3 前是宿主线程同步翻), 输出纹理由 `bResetFlag` 在**渲染线程**消费后重建(VideoRender.hpp:46 契约)——中间必然有过若干帧「交换链已 10bit+PQ、输出仍 rgba8」或反向。此时 `Dx11Window` blit 是**像素着色器纯采样直出、无色彩处理**(§3.2), 若输出是 SDR 码而交换链已挂 G2084, 就是把 SDR 码当 PQ 码呈现 → **这几帧必发灰/过曝**(与 §4.3 lane=1 误折 forceHDR 同一病根)。
  - 原稿「UNORM→UNORM 值域同 0-1, 只损位深不花屏」的论证**只在两端同为 PQ 码或同为 SDR 码时成立**; 值域不同时位深论证失效。**位深与值域是两件事**。
  - **同帧对齐手段(用户拍板 2026-10-01): 方案②「过渡帧按 SDR 口径」+ 标志位驱动, 不数帧**。口径: 宿主下发翻转只**挂意愿**(不当场改交换链), 渲染线程在**持 `mtx` 的临界区内**先重建输出端、再翻交换链, 两端同一帧生效; 中间帧双端**天然都停在旧(SDR)口径**——不存在错配窗口。用户约束: **过渡帧花一下可接受(人眼看不出 1~2 帧), 但绝不能 crash**。候选①(交换链推迟到输出重建后)与③(中间格式只切 colorSpace)弃用: ①无法保证两动作落在同一帧可见点; ③需双端同时支持 10bit 中间格式而 Apple/VK 腿是 16F, 不成同构。
  - **⚠️ 竞态 A(crash, 与花屏同级)**: `WindowRender::run()` **持 `mtx`** 跑 `onTickWin`(WindowRender.cpp:323), 其中 `DrawIndexed`+`Present` 用 `renderView`/`backTex`/`sharedTexture`(Dx11Window.cpp:118-136); 而(落地前)`setHdrMode`→`setHdrPassthrough`→`initBuffers`(Dx11Window.cpp:290/468-493)在宿主线程执行且**不持 `mtx`** ⇒ 渲染线程可能正 `Present` 时被宿主线程拆掉交换链资源 = **释放后使用**。方案②正是把这步挪进渲染线程 `mtx` 临界区(D3 已落: `applyPendingHdr()` 在 `onTickWin` 首段, Dx11Window.cpp:107/318), **竞态 A 与花屏一并消除**。
  - **`hdrPassthroughActive()` 语义约束(实现要害)**: 方案②下翻转期间「意愿≠实态」, 本查询口**必须返回实态(旧值)**——若返意愿位, `checkTargetPassthrough()` 会在交换链尚未翻时就置 `bResetFlag` 重建输出端, 反把两端拉开成错帧。三平台现口径(§4.1)正好都取实态, **勿改**。
- **CPU 读回防护**: fetchFrame/mapStagingFrame 按输出纹理格式, 遇直通格式(rgba10/16F)拒绝并日志; 截图走 SDR 口径(临时 follow 抽帧), 防脏图。
- **3s 自愈重发节流(da27cbf)必须保留**(宿主侧, §6.6)。

**方案② 落地清单(逐平台, 范围=Win+Metal+EGL+VK 一起收)**: 共性只有两条——①意愿与实态分离 ②翻转动作落在「与输出重建同一临界区」内; 其余各自本地实现, 不强行统一代码。

| 腿 | 方案②落点 | 改动性质 |
|---|---|---|
| **Win** `Dx11Window` | `setHdrPassthrough` 只落意愿位(`bHdrPending`)立即返回; 实翻移入 `onTickWin` **首段**(渲染线程持 `mtx`, Dx11Window.cpp:318), 检 `bHdrPending != bHdrActive` 才 `initBuffers`+`applyHdrSwapchainState`+提交 `bHdrActive` | **结构调整**(唯一真正动的) |
| **Metal** `MetalWindow`/`MetalRender` | 意愿位 `metalHdrPassthrough` 是原子写、翻转已在渲染线程 `MetalRender::vaildAndInitGraph:364-370`(`wantF16 != bF16Pipeline`→`applyLayerHdrConfig`+`releaseGraph`) ⇒ **已符合方案②, 零改动**; `hdrPassthroughActive()` 保留「意愿位即实态」既有口径(金属腿无宿主侧同步资源可竞态) | 核对项 |
| **EGL** `EglWindow`/`EglVideoRender` | Android 腿**无 HDR 呈现面**(`setHdrMode` 仅 `hdrMode = mode` 纯数据), 无直通可翻, **本批不改**; 仅接 D2 检查点令三平台检查路径同源 | 仅接检查点 |
| **VK** `VkWindow` | `setHdrPassthrough` 只落意愿位(`bHdrPassthrough`)返回; 实翻移入 `onTickWin`(`vkGetFenceStatus` 通过后、`vkAcquireNextImageKHR` 前), 与 `lockCommand()` 同护 | **结构调整**(与 Win 同形) |

**判据(与花屏同级, 必过)**: ①播中开关 HDR/跨屏拖动/窗口缩放往返全程无 crash(重点验 Win, 竞态 A 唯一现场); ②过渡帧**不出现两端值域错配**(不出现整屏发灰/过曝的稳定中间态; 1~2 帧闪动可接受); ③SDR 片零变化; ④VK 腿自窗直渲不变(`outputGpuData` 仍格式无关 blit)。

## 六、平台落地清单

### 6.1 Windows: 输出翻转(G3, R1 主体)

`src/avox_windows/dx11/Dx11CSVideoRender.cpp`:
- `createProgram` 输出格式按**两轴**定(§6.1 R2 修订): ①给 VK(`bVkOutput`)恒 rgba8——`VkInputLayer` 对接面全平台统一; ②直呈原生窗口跟直通实态——直通=`R10G10B10A2_UNORM`(PQ 码原样写), 否则 `R8G8B8A8_UNORM`。两端必须同翻, 错配即发灰。**已落**。
- `ImageType` 增 `rgba10`(src/avox/AvoxImage.h:28) + Dx11Helper **三处**映射同时补: `getImageDXFormt`(Dx11Helper.cpp:21)、`getImageType`(:62)、`getVkFormat`(VkHelper.cpp:354)——**三处少补一处即断链**;**纯追加零行为变更**(三处现有分支无一处被改动, 且全仓无 `rgba10` 产出点 ⇒ 生效面=0)。**影响面四件套**: ①枚举 ②三处映射 ③**SWIG 三端重生成**(X-Macro 枚举值进绑定层) ④`code-wiki/03-核心类与关键接口.md:245` 的 ImageType 清单。
- SRV 已按实际 texDesc 建(Dx11SharedTex.cpp:166)。
- **共享纹理格式支持面**: R10G10B10A2_UNORM 的 NT 共享**无代码障碍**(`Dx11Resource.cpp:89-99` 建纹理不校验 Format, D3D10 起该格式即标准 RT); 真正障碍是消费端映射表缺 10bit(即三处映射), 非驱动兼容性; **D3D11↔Vulkan 互操作**才需真机验。
- `fetchFrame`/`mapStagingFrame`: 输出为 rgba10 时拒绝并日志(截图走 SDR 口径); shader 无需改。
- **格式选型注记**: Win 输出跟 HDR10 呈现面(R10G10B10A2+G2084)走, 不用 mac 的 RGBA16Float——PQ 码值恒在 0-1, FP16 的 >1.0 余量只在线性呈现域才有意义; 与 mac 真正同域需换 scRGB FP16 交换链整链改版, 记为未来选项不列入本稿。
- CPU 帧腿补齐(G9, 已落): `renderCpuFrame` 上传 yuv420P/yuv420P10 平面(自建 DYNAMIC NV12/P010 纹理, 10bit `<<6` 对齐 MetalRender.mm:417)→进既有 CS→超 RGBA8 输出; 设备取自**呈现窗口**(同设备免跨设备句柄), `WindowRender::render(YUVFrame)` 同步补 `window->renderContext()` 下发。

### 6.2 macOS: 对齐(基本不动)

Metal 腿已有完整翻转(§3.2), 只把 `MetalWindow::hdrPassthroughActive` 接上供基类统一检查/日志; 渲染器侧行为不变。

### 6.3 VK: HDR 内容链(G4+G10, R2 主体)

**前置**: §6.1 的 `ImageType::rgba10`+三处映射必须先落——链F 输入侧(VkInputLayer 导入硬解共享纹理)要靠 `getVkFormat` 认出 10bit, 否则建 image 得 `VK_FORMAT_UNDEFINED`。

- **G4**(`VkYUV2RGBALayer.cpp` onInitLayer): 16F 赋值移到格式归一化段**之后** ✅ **已落**(条件化为「10bit + forceHDR」); `VkTexture` ✅ **经核无需改**(`VkHelper.cpp:151` `formatTable` 已有 `{VK_FORMAT_R16G16B16A16_SFLOAT, {8,4}}`)。
- **G10 升样层**(链F): 新增「rgba8 PQ 码→16F 线性」compute 层 ✅ **已落**: `VkPqUpsampleLayer` + `glsl/source/pqUpsample.comp`(源在 `source/`, 产物落 `target/`), 拓扑条件 = `hdrMode==forceHDR && !cpuIn && !bRgbaInput`, 插在 `inputLayer`(或 `yuv2RGBA`)之后; `glslindexcurrent.txt` 已登记, 12 shader 编译全绿。⚠️ 改 `.comp` 后**必须手动** `python glsl/compileglsl.py`(cmake 不含此步)。
- graph 下游格式协商(canvas→output→交换链)跟 16F; Blend/VR/font 层 16F 域兼容先保主链, 余项跟进批。
- 真验: 软解 HDR 片×HDR 屏, FP16 交换链+16F 内容链端到端(Win); 链F 用硬解 HDR 片同屏验(高光顶出+图像处理/字幕可用)。

**链F 的真实定位(核平台结构后修正)** — 链F 不是「给已有直通的平台再添一项」, 而是**无原生 HDR 腿平台的唯一 HDR 出路**:

| 平台 | 原生直通腿 | 事实依据 | 链F 的意义 |
|---|---|---|---|
| Win | ✅ 有(Dx11Window 10bit+G2084) | 已验收 | 冗余(链A 画质更好) |
| Mac | ✅ 有(Metal EDR) | 已验收 | 冗余 |
| **Linux** | ❌ **无** | `src/avox_linux/` 只有 `X11Surface`/`WaylandSurface`(非 `Window` 派生)+PulseAudio; 唯一 Linux 窗口是 `VkWindow`(自己 `__ONLY_LINUX__` 直接吃 X11/Wayland, VkWindow.cpp:348/376) ⇒ Linux 今天就只走 VK 呈现 | **唯一 HDR 路径**: 无链F 则 Linux HDR 片只能降 SDR, 永远出不了 HDR |
| Android | ❌ 无 HDR 口 | `EglWindow` **零 HDR 代码**; `EglVideoRender` 的 `uHdrMode` 是 **tone map 分支**, 非 HDR 交换链 | 同 Linux(若 EGL HDR 口不补) |

⇒ 链F 的优先级应由「跨平台 HDR 覆盖」驱动, 不由 Win 画质驱动。Linux 落地前提: `VkWindow::setHdrPassthrough` 平台无关(VkWindow.cpp:498, 已禁 `VK_EXT_swapchain_colorspace`——AMD 崩 0xC0000374), 缺的只是「X11/Wayland WSI 上 FP16 交换链能否跑通」= **真机验项, 非代码缺失**。

**交接面语义核对(G10 跨平台半场)** — 升样层假定输入是「**PQ 码原样**(未做 EOTF)」的 rgba8:

| 平台 | forceHDR 分支产出 | 交接面载体/格式 | 与链F 契约 |
|---|---|---|---|
| **Win** | `Dx11CSVideoRender` CS: **PQ 码原样**(不做 tone map) | `outSharedTex`(rgba8, VK 腿时恒 rgba8) | ✅ 一致 |
| **Android** | `EglVideoRender` `uHdrMode==2` → **`return rgb;`**(PQ 码原样) | FBO `GL_RGBA`/`GL_UNSIGNED_BYTE`(rgba8, :305) | ✅ 一致 |
| **Mac** | `MetalRender` `hdrMode==2` → **`pqToLinear(rgb)*100.0`(已 EOTF, 出线性)** | IOSurface `32RGBA`(rgba8, :768/775) | ❌ **不一致**(会二次解码) |

⚠️ **Mac 两点事实(颠覆「mac 交接面照旧」原判)**: ① mac forceHDR 出**已 EOTF 的线性**, 与 Win/Android 的「PQ 码原样」**语义相反**——走链F 会二次 `pqToLinear` ⇒ 画面严重错暗/错色; ② **mac lane=0 交接面结构上也不成立**: `MetalRender.mm:933-938` 渲染目标是「`metalLayer` 存在就画 drawable(直呈屏), 否则才画 `outputTexture`(IOSurface)」, 即 mac 有窗口时 Metal **自己直接上屏**, IOSurface 只在离屏时才是渲染目标——与 Win(CS 恒产 `outSharedTex`)结构不同。
⇒ **G10 跨平台结论**: Android 就绪(Win 亦就绪); **mac 需独立批次**(Metal 侧 PQ 直通变体+切 IOSurface 为 VK 腿目标, 与 G7 叠加后收益不足); **Linux 无 GPU 导入腿(`VkInputLayer.hpp:5-9` 三段条件编译不命中), 走 CPU 上传, 不涉本条**。

**通用性三层结构** — 链F 按「通用程度」分三层:

| 层 | 通用性 | 事实依据 | 本次 |
|---|---|---|---|
| **格式语义层**(`ImageType::rgba10`+三处映射) | ✅ **全平台共编, 完全通用** | `AvoxImage.h`/`Dx11Helper.cpp`/`VkHelper.cpp` 都是跨平台编译单元, 无 `#ifdef` 平台分支 | 补枚举+三处映射——**给 Linux/鸿蒙铺路** |
| **导入机制层**(`VkWinImage`/`VkAndImage`/`VkIosImage`) | ❌ **逐平台各一套** | `VkInputLayer.hpp:5-9` 条件编译: `#ifdef WIN32`→VkWinImage / `__ANDROID__`→VkAndImage / `__APPLE__`→VkIosImage; **Linux 三段都不命中, 无 GPU 导入腿**, 只能 CPU 上传 | **不做**(属 Linux 批次) |
| **跨 VkDevice 层**(`VkSharedImage`) | ⚠️ **声明通用, 实现仅 Win32** | 声明层已平台无关(`VkShareHandle` 含 `opaqueFd`/`androidHwBuffer`); 但 `importFromHandle` 硬编码 `OPAQUE_WIN32_BIT`(VkSharedImage.cpp:239-240), 导入整段在 `#ifdef _WIN32` 内(:266-311) | **不做, 只记缺口**(§九) |

⇒ 「接口通用」在**格式语义层已满足**; 缺的是 Linux/鸿蒙各自的 handle 导入实现, 属各自批次。**现在补映射=给未来铺路, 不是给 Windows 打补丁**。

### 6.4 硬解状态上报(G6, R5) — **结论: 引擎内部已自洽, 无需新增接口(2026-10-01 定案)**

R5 原稿要「冒宿主事件/状态位+shim 加查询口」的设想**作废**: 「不加 shim 查询口 / 不加 `IMediaPlayerOb` 事件 / 不加 `IMediaPlayer` 查询方法」。宿主徽章维持但改口径——「下发成功」即点亮(现状), 文档/注释写明「徽章=宿主意图, 非引擎实态」。若未来确有分诊需求, 走既有 MPPingback 埋点(异步批量, 不占调用栈)而非同步回调。

#### 6.4.1 R5 撤销依据(用户定稿)

**原设计(已废)**: 曾拟新增 `IMediaPlayer::isHardwareDecoding()`+`getVideoCodecTh()` 查询口与 `IMediaPlayerOb::onDecoderStateChange()` 事件口, 让宿主徽章吃引擎实态。**已实现一版, 后按用户判定全部撤回**(源码零改动)。

**撤回理由**: ① **回落软解不需要宿主做任何事——引擎已自治**: 硬解失败→`VDecoderTask::openFallbacks` 自动降级→**原生渲染腿就地吃 CPU 帧**(Win G9/mac 既有), 播放与画面全程不断; ② **软解帧原生腿能接, 接不了还有 VK 腿兜底**(lane=1 原生/lane=0 VK 的 `renderCpuFrame`), **不用换 lane 就能继续放** ⇒ 无「宿主必须介入」场景; ③ **告诉上面反而添乱**: 宿主收到事件要么无事可做、要么被诱导换道(v2 下换道已非恢复必需), 徒增卡顿与状态机复杂化; ④ **同步回调时序风险**: 事件从解码/命令线程打到宿主, 宿主若在回调里调 player API 即跨线程重入(既有 `onDecodeError` 注释已警示); ⑤ **信息公开面成本**: 新增虚函数=ABI+SWIG 三端重生成+文档同步+`VCodecTh` 多曝光一个枚举, 成本远超收益; ⑥ **既有埋点已覆盖「可查」**: `LOGFLF(warn, "video decoder fallback to:", name)` + `pushPB<MPPBType::MediaAction>(msg="video decoder fallback from X to Y")`——「异步、批量、不占调用栈」的内部上报形态。

**逐平台判定源(现状, 不动)**: Win `FFDx11Decoder::onVaild:125-140` / Android `AndVDecoder::onVaild:132` / Apple `IOSVDecoder::onVaild` / Linux `FFVADecoder::onVaild:46`——各自探测返回 false 即被选型链跳过, **由 `VDecoderTask::openFallbacks` 统一兜底**, 无需新增任何跨层出口。⇒ **本项无代码缺口**。

#### 6.6.1 宿主待办: 「源HDR × 显示器HDR」三态呈现切换(2026-10-01 晚, 用户定需求)

**需求**: panvox 现口径是「HDR 片+HDR 屏→恒直通 lane=1」。用户要在此组合上再加**可切换的三态呈现档**(目的**比对效果**), 界面由 panvox 做(**档位定位与业界先例见 §2.1**):

| 档位 | 宿主下发 | 引擎实际行为 | 链路 | 画质定位 |
|---|---|---|---|---|
| **A. 原生直通**(默认) | lane=1 + `forceHDR` | 原生 forceHDR 分支: PQ 码原样写 10bit 交换链 | 链A | **画质首选**, 无 8bit 中间量 |
| **B. vkHDR** | **lane=0** + `vkHDR` | lane=0 折 forceHDR: 原生渲染器出 PQ 码 rgba8 → `VkPqUpsampleLayer` 升样回 16F → 图像处理/字幕 → FP16 窗 | 链F | 保动态范围, **损梯度精度**(一次 8bit 量化, 暗部/高光可能 banding); 换来 **VK 图像处理能力** |
| **C. HDR→SDR** | lane=0 + `follow` | V5.comp tone map → rgba8 → SDR 呈现 | 链E | 压成 SDR, 丢 HDR 高光 |

**引擎侧: 零改动。** `HdrMode::vkHDR=3`(AvoxVideo.h:72)+lane 分岔归一化(WindowRender.cpp:70-77)+`VkPqUpsampleLayer`(VkVideoRender.cpp:551)全部就绪。**缺的只是宿主入口**。

**⚠️ 两条硬约束(否则档位 B 不生效)**:
1. **必须走「换道重开」, 不能热切**。`WindowRender::setVulkan`(WindowRender.cpp:49-58)对**已有 window 直接 `return`**, 故「播中直接 setVulkan(true)+发 vkHDR」**无效**——`bVulkan` 不变, vkHDR 仍落 lane=1 被折 follow(§4.3)。**唯一可行路径 = `switchNvvLane` 那套「拆面复挂」**: `window.reset()`→按新 `bVulkan` 建 `VkWindow`/`Dx11Window`(WindowRender.cpp:115-133)。切档 B = 触发一次到 lane=0 的换道+下发 vkHDR; 用户会看到一次短暂重开闪动(换道固有代价)。
2. **lane 必须真的在 0**。lane 分岔是**防呆**: lane=1 收 vkHDR 折 follow 并告警, 为的是拦「宿主嘴上要 VK 处理、窗口却还是原生窗」的矛盾态。**只要窗口真换成 `VkWindow`, vkHDR 必走链F**。宿主切档时须确保 lane 已落 0 再发 vkHDR(或同一次换道里带着下发)。

**实施建议(最小改法)**: 设置里加三态项「HDR 呈现模式: 原生直通 / VK 升样(保HDR) / 降SDR」; `applyNvvLaneForRef` 开播定道支持「HDR 片+HDR 屏」时按该设置决定 lane=1 还是 lane=0; 档位值映射 `forceHDR`/`vkHDR`/`follow` 经 `setHdrMode` 下发; 播中切档走既有 `switchNvvLane`。默认仍 A。
**验收提示**: 档 B vs A 对照重点是**暗部/高光的 banding**(链F 已知的 8bit 量化代价, §八); 档 C 应明显暗/压平。**HDR 屏验收一律肉眼, 截图对照作废**。
