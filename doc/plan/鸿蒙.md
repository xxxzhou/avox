# 鸿蒙播放器适配计划

> 状态: 进行中 · 上次核对: 2026-10-05 · 权威源: -

**目标：** 在鸿蒙手机上跑通视频播放（打开视频、解码、画面显示、声音播放）+ 视频硬编（录制/转码），硬解/硬编帧**走 Vulkan 管线，对齐方式与其余平台同构**。本期口径 = **本地播放**；ZLMediaKit 直播链路移出本期（仅编译探路），WebRTC 更后。

**周期：** 1 人约 9 周。壳路线（ArkTS Demo vs Flutter-OHOS/panvox）**不晚于第 4 周拍板**（见第八节）。

---

## 一、技术对位与总体路线

鸿蒙图形/媒体栈与 Android 高度同构，SDK 的对齐方式是：**在现有每个平台分叉点加一个 ohos 分支，复用全部 VK 管线，不另起炉灶**。

| 概念 | Android 现状（仓内位置） | 鸿蒙对应 |
|------|--------------------------|----------|
| 窗口句柄 | `ANativeWindow*`（`Window.hpp:26` AvoxSurfaceType 宏） | `OHNativeWindow*` |
| 硬解 | `AndVDecoder`（NDK AMediaCodec，`src/avox_android/AndVDecoder.cpp`） | `OhosDecoder`（OH_AVCodec，同为 NDK C API） |
| 零拷贝导入 | `VkAndImage`（AHardwareBuffer→VkImage，`src/avox_vulkan/android/VkAndImage.cpp:31`） | `VkOhosImage`（OH_NativeBuffer→VkImage，官方扩展 `VK_OHOS_external_memory`，芯片支持待探针） |
| 硬编 | `AndVEncoder`（AMediaCodec，`src/avox_android/AndVEncoder.cpp`） | `OhosEncoder`（`OH_VideoEncoder_*`，OH_AVCodec 体系——没有 OH_AVEncoder 这个符号） |
| 音频 | `AndAudioRender`（AudioTrack，经 JNI） | `OhosAudioRender`（OH_AudioRenderer，NDK C API） |
| VkSurface | `vkCreateAndroidSurfaceKHR`（`VkWindow.cpp:408`） | `VK_OHOS_surface` / `vkCreateSurfaceOHOS`（`vulkan/vulkan_ohos.h`，@since API 10） |

**对齐的核心是帧通路而非渲染本身**：硬解输出的图形缓冲（OH_NativeBuffer）导入成 VkImage 后挂进 `VkInputLayer`，后面 Vulkan 的 100+ 图像处理、输出层、跨设备共享输出全部白得。Android 上这条腿是 `VkInputLayer.cpp:36` / `VkOutputLayer.cpp:42` 挂 `VkAndImage`（外部内存 + dedicated allocation 导入）；鸿蒙镜像同构实现。帧的 buffer 类型直接用现有 `VBufferType::vulkan`（`AvoxSource.h:73`，消费侧按「已是 VkImage」处理，`VideoRender.cpp:169` / `VkInputLayer.cpp:342`），无需新增枚举值。

三大支柱已经官方源码/文档核实成立：零拷贝链（`OH_AVBuffer_GetNativeBuffer` @11 → OH_NativeBuffer → `VK_OHOS_external_memory` 导入）、上屏链（`VK_OHOS_surface` + XComponent 回调拿 window）、音频（`OH_AudioStreamBuilder` → `OH_AudioRenderer` @10）。

相关：backlog [A-14 avox_ohos 鸿蒙后端](backlog/a14-a19-platforms-reserve.md)。

## 二、先手探针（第 0 周起步，可跑时点随第三节工具链就绪）

两个探针直接决定零拷贝腿的生死，**先探后写主工程**。宿主形态：**最小 ArkTS 原生 ability 壳**（几百行，与第八节壳工程解耦）——探针要枚举 GPU/建 VkSurface，hdc shell 下裸二进制不保证 GPU 设备权限，不能照抄 Android 的 `/data/local/tmp` console 跑法；探针逻辑按仓惯例落 `samples/`，ArkTS 承载壳落 `platform/ohos/`。版本口径：**minPlatform = API 12**；API 23 相关（AV1 mime、外部内存 handle type 改名）走运行时版本探测。

1. **Vulkan 探针**：枚举 device extensions（`VK_OHOS_surface` / `VK_OHOS_external_memory` 是否在场）；NV12 的 `OH_NativeBuffer` 导入 round-trip：`vkGetNativeBufferPropertiesOHOS` 查属性 → 带外部内存标记建 VkImage → `VkImportNativeBufferInfoOHOS` + dedicated allocation → 绑定 → **采样验证（NV12 大概率返回 `VK_FORMAT_UNDEFINED` + `VkExternalFormatOHOS`，必须配 `vkCreateSamplerYcbcrConversion` 挂 ImageView/Sampler 才能采）**；顺带验 CPU 侧 `OH_NativeBuffer_Map` 可行性（拷贝腿前提，全线失败则 surface 预案腿上位，见第四节）。handle type 注意 API 23 改名（`…OHOS_NATIVE_BUFFER_BIT_OHOS` → `…OH_NATIVE_BUFFER_BIT_OHOS`）。
2. **OH_AVCodec 探针**：h264/hevc buffer 模式输出像素格式与 stride/sliceHeight 对齐。**注意 `OH_AVPixelFormat` 枚举只有 I420/NV12/NV21/SURFACE_FORMAT/RGBA8888/RGBA1010102——没有 P010、没有 DMA**：buffer 模式 10bit 预期拿不到，10bit 验 RGBA1010102 或 surface 模式的 NativeBuffer（关系 HDR 二期路线，见风险 7）。另加 **编码器输入 round-trip：含非对齐宽高（如 1366x768）的 NV12 入编 → 解码回读比对**——编码器对输入 stride/宽高对齐的语义与解码侧不保证同构。能力查询走 `OH_AVCapability_*`（IsHardware/GetVideoWidthAlignment 等），不盲试。

## 三、构建系统与第三方库适配（1 周）

现有构建体系按平台各有一个 `build_<platform>.py` + 公共 `build_common.py`，鸿蒙照此新增。第三方库交叉编译：**FFmpeg**（解封装+软解兜底，白名单裁剪）、**fdk-aac**、**Vulkan/volk**。

- **FFmpeg**：上游 n6.1~n9.0 的 configure 均无 `--target-os=ohos`（已核实），走 `--target-os=linux` + clang `--target=aarch64-linux-ohos`（与 SDK toolchain 三元组一致）。
- **ZLMediaKit**：本期只编译探路不接线（直播已移出本期）；**WebRTC** 后置（需 OHOS GN 归档进库仓 `build/ohos/release/`，社区有先例，放最后）。
- **toolchain**：SDK 自带 `ohos.toolchain.cmake` 自设 `CMAKE_SYSTEM_NAME=OHOS`（全大写）并强制 `UNIX=TRUE`；上游 CMake 自 3.30 才有 `Platform/OHOS.cmake` → `build_ohos.py` 钉 CMake ≥ 3.30，模块分发的 `if(OHOS)` 依赖 toolchain 变量而非内建平台判断。
- **GLSL spv 资产**：`assets/glsl` 的 spv 必须打进 HAP 资源且运行时按 OHOS 路径解析——漏了会「黑屏且无日志」（同理 AGENTS.md 的 spv 重编规矩）。
- **volk / Vulkan 宏**：`VK_USE_PLATFORM_OHOS` 必须定义否则 `vulkan_ohos.h` 结构体不完整；volk dlopen 命中 `libvulkan.so` 的第二 fallback 可工作，建议钉死；官方警告 dlopen 与 CMake 链接二选一，勿并存。
- **HAP 打包**：so 落模块 `libs/arm64-v8a`（ABI 目录命名与 Android 同名）。

**新增**：

| 文件 | 说明 |
|------|------|
| `build_ohos.py` | 仿 `build_android.py`；CMake ≥ 3.30 + SDK `ohos.toolchain.cmake`，arch 先只 arm64 |
| `script/ffmpeg/build_ffmpeg_ohos.sh` | 仿 `build_ffmpeg_android.sh`；`--target-os=linux` + `--target=aarch64-linux-ohos` |

| `src/avox_ohos/` | 平台后端模块（解码/编码/音频/窗口，命名与 avox_windows/avox_android 一致） |

**修改**（精确到位置）：

## 四、视频硬解 + VK 管线对齐（1.5 周，核心）

新建 `src/avox_ohos/OhosDecoder.{hpp,cpp}`，**镜像 `AndVDecoder` 的结构**：

- `OH_VideoDecoder_CreateByMime("video/avc"|"video/hevc")` → `OH_AVCodecCallback` 四回调（OnError / OnStreamChanged / OnNeedInputBuffer / OnNewOutputBuffer，Create 后 Configure 前注册）→ Configure（宽高/像素格式）→ Prepare → Start
- 输入侧照抄 AndVDecoder 的 **pendingPackets 深拷贝待喂队列**（9/25 真机教训：input buffer 耗尽时直接丢包 = 缺 slice 宏块花屏）
- SPS/PPS extradata 处理用现有 `H26XHelper` 工具（annexb/length-prefixed 转换已有，`H26XHelper.hpp:132-152`）

**输出侧两腿 + 一预案，按探针结果择主：**

1. **零拷贝腿（目标形态）**：buffer 模式拿 `OH_AVBuffer` → `OH_AVBuffer_GetNativeBuffer`（@11）取 `OH_NativeBuffer` → 新建 `VkOhosImage`（镜像 `VkAndImage::bindVK` 的结构）：`VK_OHOS_external_memory` 官方路径——`vkGetNativeBufferPropertiesOHOS` → 带外部内存标记建 VkImage → `VkImportNativeBufferInfoOHOS` + dedicated allocation → 绑定。**两个必踩点**：NV12 大概率 `VK_FORMAT_UNDEFINED` + `VkExternalFormatOHOS`，须建 YCbCr 采样转换挂 ImageView/Sampler；GetNativeBuffer 的 buffer 有 `OH_NativeBuffer_Unreference` 生命周期义务，渲染管线滞后深度受队列约束（跨帧持有须 Reference 计数）。
2. **CPU 拷贝兜底腿**：`OH_NativeBuffer_Map` 读出 YUV（记 stride/sliceHeight 重排）→ `SwVideoBuffer` → 走现有 CPU→VK 上传路径。**设计约束**：映射后持有到 buffer 归还（勿逐帧 Map，免 cache 同步开销）；`FreeOutputBuffer` 时序 = 拿住即拷、拷完即还；Map 失败（usage/protected buffer）→ 腿 3 预案。
3. **surface 直上屏（预案，不排期）**：仅当 buffer 模式全线不可用（含 Map 全灭）时启用，`OH_VideoDecoder_SetSurface(OHNativeWindow)` 直渲，能播但不进后处理。备注：executing 态可动态 SetSurface 换窗（对 surface 销毁恢复有用，见第五节）。

**接入选型/车道体系（这是「像别的平台」的关键动作）**：把 OhosDecoder 注册进解码器注册表（`AvoxManager::vDecoders` 的 initFuncs，`AvoxManager.hpp:129`）即白得「openFailed / 首帧看门狗超时 ⇒ 自动回退软解」链（`VDecoderTask.cpp:427` / `:444-469`，按名字匹配注册表）；但「成为硬解**首选** + `bHardDecode` 状态正确」还须三处小改，漏了则硬解永远只是回退候选、seek 也走不了硬解专属路径：

- `getDefaultDecoderName` 平台分支加 ohos（`AVTrack.cpp:269-300`，现为四平台分）
- `VCodecTh` 枚举加 ohos 值（`AvoxCodec.h:97-107`）
- `bHardDecode` 判定的三平台硬编码加值（`VDecoderTask.cpp:164-167` / `:260-261`）

（用词注意：`decodeLaneDead` 是 AVError 枚举，语义是停喂报错/置 failed，不是回退触发词——日志判读别混淆。）

AV1：mime `OH_AVCODEC_MIMETYPE_VIDEO_AV1` @since 23，低版本设备条件编译；芯片无硬解时直接复用已落地的 libdav1d 软解车道。

**验收门（独立离屏，不依赖上屏——如此四、五两节才真并行）：** 硬解出帧 → VkOhosImage / SwVideoBuffer → VK 回读 → CPU 像素校验。

**HDR/10bit** 放二期：探针 2 已实锤 buffer 模式无 P010，10bit/HDR 预期走 surface 模式 NativeBuffer + `OH_NativeWindow_SetMetaData`（HDR Vivid 元数据），路线届时重估。先把 8bit NV12 链路打穿。

## 五、画面渲染上屏（1 周，与第四节真并行）

鸿蒙支持 Vulkan，XComponent 的 `OH_NativeWindow*` 可直接创建 VkSurfaceKHR，与 Android `ANativeWindow*` 模式一致，**直接复用现有 Vulkan 渲染管线**（VkWindow + VkVideoRender + 各类 Layer）。分叉点共四处：

- `Window.hpp:11-39`：`AvoxSurfaceType` 宏加 `OHNativeWindow*`
- `WindowRender.cpp:120-140`：窗口分支加 ohos（Vulkan 路线一律 VkWindow）
- `VkWindow.cpp:372-441 initVkSurface`：加 `VK_OHOS_surface` 分支（`vkCreateSurfaceOHOS`，入口在官方 vulkan-guidelines 即「XComponent OnSurfaceCreated → 拿 window → 建 surface」这条链）
- XComponent OnSurfaceCreated/Destroyed/Changed → `setSurface` 窗口语义对齐

**前后台切换是常态场景，不是边界情况**：后台挂起 → surface 销毁 → 回前台重建，VkWindow 必须支持 surface/swapchain 重建链；销毁回调先停渲染消费、再停喂解码，回前台利用 executing 态动态 SetSurface 切新窗；析构旧窗必须同锁清指针（历史 UAF 教训，`WindowRender.cpp:100-110`）。另注意 `OH_NativeWindow` 是 buffer-queue 模型（RequestBuffer/FlushBuffer），与 ANativeWindow 的 lock/post 不同；直上屏预案里队列由解码器驱动，应用侧不插手。

**验收门：** 接窗上屏 + 同一素材与 Android 逐帧比对（判据挂 playmatrix，不发明新口径）。

## 六、视频硬编（1 周）

新建 `src/avox_ohos/OhosEncoder.{hpp,cpp}`，**镜像 `AndVEncoder` 的结构**：

- `OH_VideoEncoder_CreateByMime` + Configure（`OH_MD_KEY_BITRATE` / `OH_MD_KEY_FRAME_RATE` / `OH_MD_KEY_I_FRAME_INTERVAL` / `OH_MD_KEY_PROFILE`，以探针 2 核对为准）
- **首版走 buffer 模式喂 NV12**。「零改动」的准确口径：TranscodeRecorder 层零改动（stride 在离屏回读 `getCpuFrame` → `SwVideoBuffer` 时已归一为 packed，`VideoRender.cpp:327-348` + `VideoBuffer.cpp:16-62`；`bHardEncode=true` 本就按 NV12 出帧，`TranscodeRecorder.cpp:326-333`）——但 **OhosEncoder 封装层必须照抄 `AndVEncoder.cpp:186-196` 的按行 stride 归一拷贝**，输入宽高对齐要求以探针 2b 的 round-trip 结论为准。qenhancer 增强开启时走增强输出分支、不落 NV12（`TranscodeRecorder.cpp:313-325`）
- 零拷贝编码输入（VK→OHNativeWindow 桥 + SetSurface）是最不成熟的方向，Android 侧同方向也没做，**不进本期**
- 接入编码车道注册表 `AvoxManager::vEncoders`（`AvoxManager.hpp:133`），名字进 `getDefaultEncoderName` 映射（`Muxer.cpp:36-64`）；commercial flavor 宏（`AVOXOptions.cmake:51-63`）加 OHOS 硬编名。`rec.hard.encode=0` 回 FFmpeg 软编兜底，既有逻辑自动生效

**验收门：** 录制 mp4 可播（常规宽高 + 非对齐宽高各一）；`rec.hard.encode=0` 软编对照零回归。

## 八、平台壳工程（2 周）——路线 ≤ 第 4 周拍板

两条路线工作量与风险完全不同，按拍板结果走条件分支：

### 路线 A：ArkTS 独立 Demo（现稿）

需要有鸿蒙应用项目来承载 SDK，类似 Android 的 Studio 工程、iOS 的 Xcode 工程。

**NAPI 桥接层（关键工作）**：鸿蒙 C++ ↔ ArkTS 互调走 NAPI，和项目 Electron 端用的 Node-API 是同一套接口体系。项目已有 SWIG 生成的 `commonJAVASCRIPT_wrap.cxx`，它依赖 `Napi::` 封装类（node-addon-api 头文件库），底层全是 `napi_*` C 接口；鸿蒙自带 `napi_*` 但没有 `Napi::` 层。策略：**移植 node-addon-api 到鸿蒙**——一次性投入后 SWIG 代码直接可用，后续全功能接口零桥接成本；node-addon-api 只是头文件库，需逐个验证鸿蒙 NAPI 兼容性。

**ArkTS 壳工程**：DevEco Studio 项目 + XComponent 播放器页 + NAPI 调 SDK；`module.json5` 声明 `ohos.permission.INTERNET`（漏了网络播放第一手就失败）。

### 路线 B：Flutter-OHOS（panvox 主线候选）

砍掉 NAPI/SWIG 桥（那 2 周省掉）：panvox 走自家 `panvox_c_api` shim（libpanvox_native，纯 C++ 平台无关）+ **Dart FFI**（`plugin_ffi` 模板已支持 ohos 平台）；视频窗 = XComponent PlatformView（与 Android/iOS/mac 腿同构）；ISourceInfo ready 快照等 shim 成果直接带过。**成本实锤**：Flutter-OHOS 主线 3.7.12-ohos（另有 3.22.1 分支，未见 release 标注），明显落后 Flutter 主线——与 panvox 现用 Flutter 版本的对齐是第一风险；SIG 仓已迁 gitcode。要求 API 12 / DevEco 5.0 / JDK17。若胜出，本节 2 周 → 约 1~1.5 周，但版本对齐探针须提前到第 0-2 周。

### 共同项

- **引擎 so 分发模型**：HAP native lib 随包签名分发，版本管理天然解决——**别照搬 Windows 运行时下发 so 的启动闸模式**（SELinux 加载限制）；commercial（LGPL）license 断言脚本须覆盖 OHOS 打包形态
- 拍板前置探针：Flutter-OHOS 现用版本可行性 + XComponent 与 Flutter 视图堆叠表现（社区有黑块/闪烁报告、推外接纹理绕行——外接纹理是 panvox 已判死的纹理路，先按 PlatformView 直渲验，不成立再议）

## 九、全链路联调（1.5 周）

## 主要风险

1. **`VK_OHOS_external_memory` 的芯片实现** — 官方扩展与指南俱在，目标真机是否实现仍只能探针定；失败走拷贝腿，结构不塌
2. **buffer 模式格式面**（已核实枚举无 P010/DMA）— 8bit NV12 预期稳；10bit 只能 RGBA1010102 或 surface 模式，探针 2 定；最坏 surface 预案腿
3. **XComponent surface 时序** — 官方指南即此用法，风险较先前评估下调；真机验证保留，重点盯销毁/重建风暴
4. **musl/FFmpeg 编译期探测** — ohos target 已定论走 linux 变体；残余风险集中在 musl 差异的 configure 探测
5. **壳路线** — 拍板前置（≤ 第 4 周）；ArkTS 路线的 node-addon-api 移植是最大单笔可报废投入，Flutter 路线的版本落后是第一风险
6. **HEVC/AV1 芯片支持面** — 按能力探测动态注册车道，不可用自动落软解（AV1 有 libdav1d 先例；AV1 mime @23 需条件编译）
7. **HDR Vivid** — buffer 模式无 P010 的前提下，预期走 surface 模式 NativeBuffer + SetMetaData，路线待重估
8. **音频中断/焦点恢复** — AudioSession 处理不当则游标错位（来电、切后台类场景）
