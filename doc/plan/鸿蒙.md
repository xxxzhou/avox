# 鸿蒙播放器适配计划

**目标：** 在鸿蒙手机上跑通视频播放（打开视频、解码、画面显示、声音播放），与播放无关的功能暂不涉及。

**周期：** 1 人 7-8 周（约 2 个月）

---

## 一、构建系统与第三方库适配（1 周）

现有项目是为 Windows/Android/iOS/Linux 设计的编译体系，鸿蒙是全新平台，需要：

- 编写鸿蒙专用的编译配置，告诉 CMake 用什么编译器、链接哪些系统库
- 把项目已有的公共宏（如导出符号 `AVOX_EXPORT`）扩展到鸿蒙
- 写自动化构建脚本，一键编译出鸿蒙可用的 SDK

同时需要适配项目依赖的第三方库，这些库大多没有官方鸿蒙支持，需用鸿蒙工具链重新交叉编译：

- **FFmpeg** — 音视频解封装（把 mp4/flv 拆成音频流和视频流）和软解回退，没有它连视频文件都打不开
- **ZLMediaKit** — 直播协议支持（RTSP/RTMP 等），用于网络流播放
- **fdk-aac** — AAC 音频编解码库，部分音频格式依赖它
- **Vulkan / volk** — Vulkan 图形 API 加载器，渲染模块依赖它

不做这些，代码根本编译不过，后续所有工作都无法开始。

---

## 二、视频硬解（1 周）

视频文件是压缩数据，需要芯片内的专用硬件（编解码器）实时解压成画面。每个平台的调用方式不同：

- Android 用 MediaCodec，iOS 用 VideoToolbox，Windows 用 DX11 硬解
- 鸿蒙有自己的 `OH_VideoDecoder` 接口，需要重新对接

主要工作：把压缩的视频数据喂给鸿蒙解码器，再把解码后的画面取出来交给渲染模块。需要处理 H264 和 H265 两种主流编码格式，以及配置帧（SPS/PPS）的特殊处理。

---

## 三、画面渲染（1 周）

解码出来的原始画面数据需要画到屏幕上。鸿蒙支持 Vulkan，XComponent 拿到的 `OH_NativeWindow*` 可直接创建 `VkSurfaceKHR`，与 Android 上 `ANativeWindow*` 的模式完全一致，因此可以**直接复用项目现有的 Vulkan 渲染管线**（VkWindow + VkVideoRender + 各类 Layer），无需另写 CPU 上屏逻辑。

主要工作：
- 在 `VkWindow` 新增 `initVkSurface(OH_NativeWindow*)` 分支，创建 Vulkan Surface
- 在 `VkOutputLayer` 新增鸿蒙平台输出分支（Vulkan 处理结果直接上屏，暂不涉及 GPU 零拷贝互操作）
- 扩展 `AvoxSurfaceType`、`RenderType`、`VBufferType` 等枚举定义，让框架识别鸿蒙平台

暂不做的：硬解输出到 Vulkan Image 的零拷贝路径（GPU 互操作），先走 CPU 回读 YUV → Vulkan 渲染上屏，后续再优化。

---

## 四、音频播放（1 周）

视频有画面还得有声音。各平台音频 API 不同：

- Windows 用 WASAPI，Android 用 AudioTrack，iOS 用 AudioUnit
- 鸿蒙使用 `OH_AudioRenderer`

主要工作：把fdk-aac解码后的 PCM 音频数据写入鸿蒙的音频播放器，实现音量调节、暂停/恢复、播放速度控制。音频模块相对独立，接口简单，工作量较小。

---

## 五、平台壳工程与接口桥接（2 周）

需要有鸿蒙应用项目来承载 SDK，类似 Android 的 Studio 工程、iOS 的 Xcode 工程。

### NAPI 桥接层（关键工作）

鸿蒙 C++ ↔ ArkTS 互调走 NAPI，和项目 Electron 端用的 Node-API 是同一套接口体系。项目已有 SWIG 生成的 `commonJAVASCRIPT_wrap.cxx`，它依赖 `Napi::` C++ 封装类（来自 node-addon-api 头文件库），底层调的全是 `napi_*` C 接口。鸿蒙自带 `napi_*` C 接口但没有 `Napi::` 封装层。

策略：**移植 node-addon-api 到鸿蒙**，而非手写少量 `napi_*` 接口。理由：

- 一次性投入，之后 SWIG 生成的代码直接可用，所有 struct/class/enum/回调自动暴露
- 后续扩展全功能接口（STT、翻译、去水印、WebRTC 等）无需再写任何 NAPI 桥接代码
- node-addon-api 本身只是头文件库，底层全调 `napi_*`，需逐个验证鸿蒙 NAPI 兼容性并适配缺失函数

### ArkTS 壳工程

- 创建 DevEco Studio 项目，搭建 ArkTS 播放器页面（XComponent + 播放控制按钮）
- 通过 NAPI 调用 C++ 播放器 SDK
- 这是让 SDK 真正"跑在鸿蒙手机上"的最后一环

---

## 六、全链路联调（1.5 周）

各模块单独能跑不等于整体能跑，需要：

- 验证"打开视频 → 解封装 → 硬解/软解 → 画面上屏 + 声音播放"完整链路
- 调试音视频同步（画面和声音对不上是最常见的问题）
- 处理各种视频格式的兼容性（不同分辨率、帧率、编码）

联调往往是最耗时的阶段，模块间接口对不上、时序问题、线程冲突都在这里暴露。

## 主要风险

1. ffmpeg/zlmediakit/fdk-aac这些播放需要的第三方库在鸿蒙上的兼容性.
2. **OH_VideoDecoder 输出格式** — 能否直接拿到 YUV 数据，还是只输出到 NativeWindow（如果是后者，渲染路径需调整为解码直接上屏，不走后处理）
3. **XComponent C++ 回调** — 鸿蒙 XComponent 的 `OnSurfaceCreated` 能否稳定拿到 `OH_NativeWindow*`，这是 Vulkan Surface 创建的入口
4. **Vulkan ICD 扩展完整度** — 鸿蒙 Vulkan 驱动是否支持创建 Surface 所需的 platform extension（`VK_KHR_surface` + 对应的鸿蒙扩展）
5. **node-addon-api 鸿蒙适配** — 鸿蒙 NAPI 基于 Node.js 12.x，部分 `napi_*` 函数可能未实现或行为有差异，需要逐个验证和绕过
