# 显示矩阵旋转实施方案（播放/预览/录制）

> 状态: 进行中 · 上次核对: 2026-10-29 · 权威源: -

手机竖拍的编码画面通常是横的，播放方向由容器的 display matrix 声明。avox 目前
完全不读它，所以窗口预览把竖拍内容横着放；Windows 自带播放器/VLC/mpv 会自动转，
用户对比后确认是引擎缺口（1029 截图：左侧 avox 系播放器横躺，右侧系统播放器
正常）。本文定旋转归属、落点、逐腿改法与验收；**P1（VK 车道 + VTrackDesc）
已落地，P2/P3 原生腿未动**，见 §8 施工记录。

---

## 0. 结论

1. **旋转在渲染层入口做一次**：YUV→RGBA 之后、缩放/画质/字幕/OSD/输出之前。
   这样窗口预览、`screenShot`、`enableImage`、录制 YUV 全都是显示方向，字幕按
   显示方向合成，且只转一次。
2. **不在 `ak_frames` 里转**（用户 1029 拍板）：shim 只做 JSON/JPEG/FFI；旋转是
   引擎能力，reader 迁移后也不在 reader 里 CPU 转。
3. **不在窗口 blit 转**：VK 车道字幕/OSD 已经合进纹理，到 blit 再转会把字幕也
   转歪；截图和录制仍然横躺。
4. **VK 是当前主车道**：Windows panvox `create` 即 `setVulkan(true)`，avoxkit
   预览也走默认 Vulkan。P1 先落 VK，直接修好用户截图里的预览；DX11 CS、EGL、
   Metal 是同一模式的机械重复，P2/P3 补齐。
5. 方向语义对齐 ffmpeg 自动旋转；本机两向 fixture 已用 `ffmpeg` 自动旋转结果
   对照过（§7），不是重新推导的一套角度。

- 本机 536 个视频抽样：530 个无旋转，5 个 `rotation=-90`（显示角 90°），1 个

- 生成 fixture `D:\tmp\portrait_test\rotated.mp4`（1920×1080 + display matrix，

## 2. 为什么必须是“入口一次”

| 做法 | 后果 |
|---|---|
| **渲染入口转（本方案）** | 预览/截图/`enableImage`/录制/YUV 输出全对；字幕在旋转后的显示域合成，保持水平；只转一次 |
| 窗口 blit 转 | VK 的字幕/OSD 已合进同一张纹理，会跟着转 90°；`screenShot`/录制仍横躺 |
| `ak_frames` 里转 | 缩略图对，播放窗口仍横躺；用户已明确不要 shim 承担 |
| Flutter/UI 每张图转 | 预览、缩略图、系统截图、录制各转各的，容易出现转两次/方向不一致 |
| reader 里 CPU 转 | 与播放层重复；reader 迁移后同一文件会出现两种方向定义 |

旋转必须在 `VkResizeLayer`、画质层、`VkFontLayer`/`VkCanvasLayer`、几何层之前；
否则超分/字幕/OSD 的坐标系仍是编码方向。

## 3. 数据链路

### 3.1 IO 取 display matrix

`IOParseFF` 建 `VTrackDesc` 时（`src/avox_ffmpeg/IOParseFF.cpp:1172-1185`）读
`st->codecpar->coded_side_data` 里的 `AV_PKT_DATA_DISPLAYMATRIX`（FFmpeg 9 已把
流侧数据收进 `codecpar`，与 DOVI conf 同一处）：

```cpp
const AVPacketSideData* sd = av_packet_side_data_get(
    st->codecpar->coded_side_data, st->codecpar->nb_coded_side_data,
    AV_PKT_DATA_DISPLAYMATRIX);
if (sd && sd->size >= 9 * sizeof(int32_t)) {
  double theta = -av_display_rotation_get((const int32_t*)sd->data);
  // 归一化到 [0,360)，四舍五入到 90° 的倍数；偏离 >1° 视为无效
}
```

`theta` 的语义与 ffmpeg 自动旋转一致：90=顺时针 90°，270=逆时针 90°。只有
0/90/180/270 生效；非 90° 倍数（极少）按 0 处理并打一条 warn；矩阵含镜像
（行列式为负）v1 不支持，同样 warn 后按纯旋转处理/忽略。

### 3.2 FFmpeg 能替我们做到哪一步（1029 核实）

- **libavformat/libavcodec 不会应用矩阵**。`ffmpeg` 命令行的 autorotate 是
  `fftools/ffmpeg_filter.c` 在滤镜图里插 `transpose/hflip/vflip`，属于 CLI
  行为；libav API 没有对应开关，`avcodec_receive_frame` 返回的
  `AVFrame::width/height` 仍是编码宽高，像素仍是编码方向。
- FFmpeg 9 会把矩阵从 packet side data 挂到解码帧
  `AV_FRAME_DATA_DISPLAYMATRIX`（`libavcodec/decode.c` 的 packet→frame 映射；
  手机样本 `ffprobe -show_frames` 实测有 `3x3 displaymatrix`/`rotation=-90`）。
  角度有现成来源，可作为 stream side data 缺失时的回退，但**应用仍要我们做**。
- 想用 FFmpeg 内部滤镜转：随包五平台 FFmpeg 都**没编 avfilter**（只有
  avcodec/avformat/avutil/swresample）；软件 transpose 是 CPU 拷贝/转置，硬解帧
  还要 `hwdownload`（GPU→CPU），违背零拷贝；硬件 transpose 滤镜
  （vulkan/vt/cuda/vaapi）需要另建 hwframes+filter graph，且没有
  `transpose_d3d11va` 覆盖 Windows DX11 腿。接入成本不低于在现有渲染图里插
  一个转置层，因此不采用。
- 结论：FFmpeg 负责“告诉我们角度”，像素旋转由 avox 渲染层负责；这也是
  10 月 29 日“在底层处理、`ak_frames` 不转”的落点。

### 3.3 归属：`VTrackDesc` 加字段，引擎内部消费（1029 用户口径）

用户要求“全在内部做”，不要 `ISourceInfo`/`ISurfaceRender` 上再加一层需要宿主
调用的接口。落法：

- `VTrackDesc`（`src/avox/AvoxCodec.h:131`）末尾加
  `int32_t rotation = 0;`（顺时针 0/90/180/270，来自 display matrix）。`IOParseFF`
  填；播放器、录制、reader 都从 `trackDesc` 直接取。
- **不加** `ISourceInfo::getVideoRotation`，**不加** `ISurfaceRender::setVideoRotation`。
  `VideoTrack::setTrackDesc` 存 rotation；`VideoTrack::onVideoDesc()` 内部调用
  `windowRender->setVideoRotation(rotation)`；`WindowRender` 再转发给
  `VkVideoRender`/平台渲染器。这些都是内部具体类的方法，不经公共虚接口，宿主无需
  调用、也无法漏调。
- 代价：`VTrackDesc` 变大，`ISourceInfo::getVideoDesc` 按值跨库 → 旧宿主/插件
  必须重建（panvox/avoxkit/playtest runner/SWIG 绑定）。这是“全部内部做”的
  交换条件；本仓发布本来统一重建。`ATrackDesc`/`VideoDesc` 不动。
- 宿主若要用角度做 UI 提示，读 `VTrackDesc.rotation` 即可；不读也不影响
  播放，引擎会自己旋正。**`VTrackDesc` 不提供 displayWidth/displayHeight**：
  输出尺寸会被 resize/画质/VR/录制改尺寸等处理改变，track desc 阶段拿不到；
  实际输出宽高只以帧回调里那一帧的 `ImageFormat`/`YUVFrame` 为准（见 §5.4）。
  `ak_probe` 最多输出 `rotation`，不承诺输出尺寸。
- 内部消费点要齐：`VideoTrack`（播放/录制共用同一个 `WindowRender`）、
  `IMediaReader`（自建 `VTrackDesc` + `SurfaceRenderVk` 内部 setter）、
  `TranscodeRecorder`（自带 `WindowRender`，`vTracks` 里有 `VTrackDesc`）也要
  传 rotation，否则转码导出仍横躺。纯封装的 `StreamRecorder` 不渲染，包保持
  编码方向，靠 muxer 复制 display matrix（见 §5.4）。

## 4. 方向映射

以 `theta` 为顺时针显示角：

| theta | VK 节点 | 参数 |
|---|---|---|
| 0 | 无 | - |
| 90（顺时针） | `VkTransposeLayer` | `bFlipX=1, bFlipY=0` |
| 180 | `VkFlipLayer` | `bFlipX=1, bFlipY=1` |
| 270（逆时针） | `VkTransposeLayer` | `bFlipX=0, bFlipY=1` |

`transpose.comp` 的默认映射是 `out(x,y)=in(y,x)`；`bFlipX` 把输入列翻成
`outW-1-x`，`bFlipY` 把输入行翻成 `outH-1-y`。上表按该实现推导，落地前用
§7 的两向 fixture 各跑一遍（参考图 = `ffmpeg -i ... -frames:v 1` 自动旋转
输出，不是凭记忆）。

## 5. 逐腿实现

### 5.1 VK 车道（P1，先修用户截图）

落点 `src/avox_vulkan/vulkan/VkVideoRender.cpp:vaildAndInitGraph()`：在
`outNode` 建好之后、`pqUpsampleLayer`/`resizeLayer`/画质层之前插入：

```cpp
outNode = (cpuIn && !bRgbaInput) ? inputLayer->addLine(yuv2RGBA) : inputLayer;
if (videoRotation == 90 || videoRotation == 270) {
  transposeLayer = graph->addNode<VkTransposeLayer>();
  TransposeParamet p = {};
  p.bFlipX = (videoRotation == 90);
  p.bFlipY = (videoRotation == 270);
  transposeLayer->get()->updateParamet(p);
  outNode = outNode->addLine(transposeLayer);
} else if (videoRotation == 180) {
  flipLayer = graph->addNode<VkFlipLayer>();
  flipLayer->get()->updateParamet(FlipParamet{1, 1});
  outNode = outNode->addLine(flipLayer);
}
```

- 层在 **rgba8 域**：`transpose.comp`/`flip.comp` 声明的是 `rgba8` storage image。
  链F（forceHDR 硬解）在 `pqUpsampleLayer` 之前是 rgba8 PQ 码，转完再升 16F，
  正确；不要插到 16F 之后。
- **CPU 软解 + forceHDR** 例外：`VkYUV2RGBALayer` 直通变体输出 rgba16f
  （`VkYUV2RGBALayer.cpp:189-195`），rgba8 转置层接不上。v1 在重建时检测到
  该拓扑就跳过旋转并打 warn（`rotation not applied: cpu+forceHDR`），列为
  已知缺口；reader 固定 `HdrMode::follow`，不受影响。
- 尺寸/比例要跟着转：
  - `VkVideoRender::getOutSize()`（`:484-492`）在无 resize/VR 时返回编码
    `imageFormat`，90/270 要返回 `{h,w}`；
  - `VideoRender::renderFrame()` 的 `setAspect(width/height)` 在 90/270 用
    `h/w`；
  - `bUseNewSize && sizeScale != 1.0f` 的 `newWidth/newHeight` 由编码尺寸乘
    scale（`VkVideoRender.cpp:690-696`），先按显示尺寸算；
  - `VkOutputLayer` 的 `getTextureRect`/`getViewRect` 自动吃新尺寸与 aspect。
- 下游自动正确：`screenShot`/`flushShot` 读 `outputLayer` 纹理；
  `enableImage` 的 `imageResizeLayer` 在转置之后；`bOutCpuYuv` 的
  `rgba2YUV`/`yuvOutLayer` 也在之后。录制的 `getOutSize()` 换成显示尺寸，
  `MediaPlayer.cpp:265` 的 `setInVideoDesc` 即拿到 1080×1920 而不是 1920×1080。
- **字幕/OSD 坐标系**：`VideoTrack::start()`（`:58`）和重挂（`:502`）现在用
  `srcDesc.width/height` 设置 `setStorageSize`；90/270 要改成显示尺寸，否则
  VK 画布仍按 1920×1080 排版，字会按横屏比例缩放。
- `VideoRender::checkShot()` 的 CPU 兜底（`:143-146`）仍会用未旋转的
  `yuvFrame` 转 RGBA；rotation!=0 时该兜底要么跳过（优先走 GPU fetch），要么
  在兜底里做一次 CPU 旋转，不能让截图偶尔横躺。
- 旋转变化/换片：`setVideoRotation` 置 `bResetFlag`，下次 `vaildAndInitGraph`
  重建图；`VideoTrack` 每次 open 都下发，0 会清掉上一场。

### 5.2 Windows 原生 DX11 CS（P2）

`Dx11CSVideoRender` 的 YUV→RGBA 计算着色器直接按输出像素采样 YUV。旋转在
CS 里做：

- 常量区在 `doviEnable` 后有一组预留/填充 int（`Dx11CSVideoRender.cpp:42-46`），
  可借一个存 `rotation`；C++/HLSL 两侧按声明序同步，改完用
  `static_assert(sizeof(ColorYuvUBO)==2848)` 和 DV P5 用例回归（该区 DV 偏移
  敏感，不能只看非 DV 画面）；
- `main` 里输出像素 `DTid` 先按逆旋转映射成源像素 `srcPix`，Y/UV 采样和
  tone map/DV 数学用 `srcPix`；画布混合仍用 `DTid`（显示域，字幕保持水平）；
- 输出纹理尺寸与 `Dispatch` 组数用显示尺寸，输入 SRV/源纹理仍是编码尺寸；
  需要把现有 `imageWidth/imageHeight` 拆成 `srcWidth/srcHeight` 与
  `outWidth/outHeight`（`createProgram`、`prepareAndBind`、`Dispatch` 都用到）；
- `Dx11Window` 从共享纹理的 `ImageFormat` 取 aspect，输出纹理换显示尺寸后
  自动正确；`SurfaceRenderNative::getOutSize()` 要按 rotation 返回显示尺寸。

### 5.3 EGL / Metal（P3）

同一原则，但这两条腿的视频绘制本身就是“带 UV 的四边形”，比 DX11 CS 简单：

- YUV→RGB 绘制的顶点/片元 UV 按旋转置换；输出 FBO/纹理尺寸与 viewport 换成
  显示尺寸；`getViewRect` 的 aspect 用显示比例；
- 字幕画布是**第二次独立 draw**（`MetalRender.mm:1509`、
  `EglVideoRender.cpp:775` 一带），它本来就在最终显示域，保持不转；
- `setStorageSize` 同 §5.1 换成显示尺寸；
- 截图/录制的 `getCpuFrame`/`fetchFrame` 从换过尺寸的输出纹理读，自动正确。

### 5.4 共用收尾

- `VideoTrack` 两处 `setStorageSize` 改显示尺寸（`VideoTrack.cpp:58/502`）；
  `SourcePlayer.cpp:122` 是采集源，rotation 恒 0，不改。
- **输出尺寸的唯一真相源是帧回调**：`ISurfaceRenderOb::onFrame(buf, yuvType)` 的
  `buf->getImageFormat()`、`onRender(SurfaceRenderEvent::format)` 或
  `YUVFrame.width/height`。`VTrackDesc`/`getOutSize()` 都只是输入描述或建图前
  预估；resize/画质/VR/录制改尺寸都会改变输出。录制/UI/抓帧要以回调里的实际
  宽高为准，不匹配时在回调里记录并按实际值处理。
- 录制：`MediaPlayer.cpp:265` 的软编/CPU 分支已用 `winRender->getOutSize()`；
  硬编分支直接 `setInVideoDesc(vtracks[0])`（`MediaPlayer.cpp:286`）仍是编码
  尺寸，要改成显示尺寸或显式拒绝竖拍硬编；无论哪条，首帧回调再按实际
  `ImageFormat` 校验一次。
- remux（`video_copy`）不是解码渲染，包仍是编码方向；`IOMuxerFF` 用
  `avcodec_parameters_copy`，需确认 display matrix 被复制（FFmpeg 9 会复制
  coded side data）；不复制就在 muxer 侧补，否则 remux 出来的竖拍文件又横躺。
- `IImageRender`/静态图没有 display matrix，rotation 恒 0，行为不变。

## 6. 与 IMediaReader 的关系

reader **不再 CPU 旋转**（推翻 10 月 29 日早先的“reader 内转一次”口径）：

1. reader 自己从 `VTrackDesc.rotation` 取角度并在内部调用
   `SurfaceRenderVk` 的 setter，`enableImage` 拿到的是显示方向 RGBA；
   `MediaFrameInfo.width/height` 取**实际输出 buffer 的 `ImageFormat`**，
   不是从 track desc 预计算。宿主不参与。
2. `MediaFrameRequest.width` 是请求的显示宽度；320 请求在 9:16 源上实际输出
   一般为 320×569，但以 `onFrame` 的 buffer 格式为准（处理链可能改尺寸）。
3. `ak_frames` 切到 reader 时删除 `DISPLAYMATRIX`/rotation/YUV 采样，shim 只做
   JSON/JPEG；`ak_probe` 只输出 `rotation`，不输出 display_width/display_height
   （输出尺寸只有帧回调知道）。UI 比例用 `MediaFrames.width/height`。
4. 单一真相源 = 渲染层；reader/UI/shim 都不再各读一次矩阵。若某拓扑不能应用
   旋转（§5.1 的 CPU+forceHDR），渲染层打 warn；reader 固定 follow，不会命中。

## 7. 验收

### 7.1 fixture

- `1920×1080 + 顺时针 90°`（本机 `D:\tmp\portrait_test\rotated.mp4` 是
  270°/逆时针，生成时换符号即可）；
- `1920×1080 + 逆时针 90°`（手机样本，或 `-display_rotation -90` 生成）；
- 横拍对照组（无矩阵）、180° 组；
- 带角标（左上角红点/文字）的竖拍样本，方向错一眼可见；
- 用 `ffmpeg -i <fixture> -frames:v 1 ref.png` 自动旋转输出作为参考图。

### 7.2 判据

- 窗口预览：竖拍内容正立，窗口按 9:16 比例留边（不是把 1920×1080 拉伸成
  9:16）；字幕/OSD 水平、不被旋转。
- `screenShot`/`enableImage`：方向与 `ref.png` 一致；宽高**以帧回调实际交付的
  `ImageFormat` 为准**（当前 9:16 链观测为 1080×1920 或请求的显示尺寸，不是
  接口保证）。可做缩略图 SSIM/角标位置断言。
- 录制：软编/硬编输出尺寸与方向按实际帧；muxer 声明的尺寸在首帧回调校验，
  不让 `getOutSize()` 的预估值冒充输出真相；remux 保留 display matrix。
- 横拍文件：像素级零变化（回归基线截图逐字节/SSIM 对比）。
- 播放回归：离线子集 84P+4dav 零新增挂；5 个本机竖拍文件逐个播放/拖 seek。
- 与 reader 一致性：同一 fixture 的 reader `grabFrame` 与窗口 `screenShot`
  方向一致；`ak_frames` 迁移后不再出现 `DISPLAYMATRIX`。
- 无 Vulkan：probe/index 正常；frames 仍 `render_unavailable`；原生腿（P2/P3
  未落时）播放横躺是已知限制，不能静默声称已转。

## 9. 待拍板 / 已知限制

1. **镜像矩阵**（行列式为负）：v1 不转镜像，warn 后按纯旋转/忽略；实际片源
   极少，先不做。

   coded side data；不复制则补 muxer 侧拷贝，不在 P1 阻塞播放。
