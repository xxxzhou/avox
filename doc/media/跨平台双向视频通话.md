# 多平台双向视频通话

现在基本完成了各平台双向视频通话及记录到本地多媒体文件,主要实现点.

1. 支持平台windows/linux/ios/android,包含拉流,解码,编码,推到媒体源(如无特殊说明,媒体源可以是本地文件,也可以是网络流)上,其中每个步骤至少有二种方案,比如拉流与推流都可以分别选择ffmpeg/zlmediakit,解码与编码可以用ffmpeg,也可以用IOS/android原生解码与编码,需要每种组合都考虑到,使用aac/h264/h265时,整个流程可以不用ffmpeg.
2. 支持媒体源直接转发如aac/h264/h265到媒体源,也支持解码后再编码图像处理后到媒体源,解码可以选择硬解/软解,编码可以选择硬编/软编.
3. 低功耗平台如ios/android支持解码到渲染与图像处理到硬编流程全GPU处理.
4. 方便扩展不同SDK,比如从推拉流媒体源,现支持zlmediakit,也支持ffmpeg,也可支持特有的私有协议.
5. 图像处理组合支持,比如加入AI识别,字体渲染,大小变化,旋转,镜像,翻转等.
6. 原始数据源扩展,比如windows下截屏,ios/android下摄像头,不同平台麦克风,方便扩展新的数据源并整合到整个流程中.

## 实现

视频主要以H264/H265为例.一般来说,本地文件/hls每段nalu前4个字节为长度,网络流为0001或是001开头,其中第一种表达方式叫avcc/hvcc,第二种表达为annexb.其中android硬编原生支持的是annexb,而mac平台硬编原生支持默认是avcc/hvcc,包含mac主导的hls流媒体协议也是avcc/hvcc.

当你用ffmpeg拉流,如果媒体源是本地文件/hls,则大概率是avcc/hvcc,如果是网络流,则大概率是annexb,而用zlmediakit拉流,应该会统一为annexb.

ffmpeg编码出的包有可能是多个nalu包组合也可能是单个nalu包拆分到多个包里,用ffmpeg拉流也会保持这种情况,包含如下几种情况,合并可能是配置帧组+I帧,配置帧组+SEI+I帧,拆分可能是大的I/P帧分割成多个包,相反如果是iOS原生编码器输出的是avcc格式的单个NALU,Android原生编码器输出的是annexb格式的单个NALU,用zlmediakit拉流也是单个annexb格式,其zlmediakit内部会自动拆分上面说的合并配置帧组+I帧的情况,以及整合在拉流拆分的I/P包,保证出来的单个nalu包,如果你只用ffmpeg拉流,解码,编码,推流,你可以不用管,但是脱离ffmpeg,则需要知道这些并处理.

如果是nalu包,其annexb与avcc/hvcc如果都是四字节的情况下,其实转换比较简单,但是问题是annexb有001开头,如果这种情况,比如0x000001xx,你并不确定这是annexb头3还是avcc/hvcc,则需要先判定格式,可以从是否avcc/hvcc来处理,从长度直接到下一个nalu头的长宽快速判定是否与整个包长度是否一致,并且只需要判定一次格式就行,至少我暂时还没看到,开始发annexb,然后又发avcc/hvcc的情况.一般为了方便,在把包添加在队列时,如果检查到annexb头3的,直接改为annexb4,后面如果是MAC平台,也方便直接修改成avcc/hvcc格式.

``` C++
bool checkAvccPacket(const uint8_t* data, int32_t size) {  
  // annexb 4肯定不是avcc包，但是ann3可能是avcc包
  if (data[0] == 0 && data[1] == 0 && data[2] == 0 && data[3] == 1) {
    return false;
  } else {
    uint32_t avccSize =
        ((data[0] << 24) | (data[1] << 16) | (data[2] << 8) | data[3]);
    avccSize += 4;
    while (avccSize <= size) {
      // 如果长度对的上，说明是avcc包
      if (avccSize == size) {
        return true;
      }
      if (avccSize > size + 4) {
        break;
      }
      // 下一包的长度
      uint32_t nextSize = ((data[avccSize] << 24) | (data[avccSize + 1] << 16) |
                           (data[avccSize + 2] << 8) | data[avccSize + 3]);
      avccSize += nextSize + 4;
    }
  }
  return false;
}

void PacketBuf::form(const AvoxPacket& packet) {
  frameType = packet.frameType;
  packtype = packet.packtype;
  pts = packet.pts;
  dts = packet.dts;
  const uint8_t* pdata = packet.data.data;
  prefixSize = packet.prefixSize;
  // annexb 3转成成annexb 4,方便后续统一处理
  int32_t bAnnexB3 = 0;
  if (packet.packtype == (int32_t)PackType::video ||
      packet.packtype == (int32_t)PackType::vconfig) {
    prefixSize = 4;
    bool bavcc = checkAvccPacket(pdata, packet.data.size);
    // annexb3 与 avcc可能混淆，所以这里要判断一下
    if (!bavcc) {
      if (pdata[0] == 0x00 && pdata[1] == 0x00 && pdata[2] == 0x01) {
        bAnnexB3 = 1;
      }
    }
  }
  size = packet.data.size + bAnnexB3;
  // 只有在本身少于packet.data.size才可能去调整
  if (buff.size() < size) {
    buff.resize(size);
  }
  memcpy(buff.data() + bAnnexB3, packet.data.data, packet.data.size);
  if (bAnnexB3) {
    buff[0] = 0x00;
  }
}
```

配置帧的情况有些特殊,如ffmpeg拉流及初始化编码器,对应的视频流或是音频流有个类型为AVCodecParameters的参数,除了填充基本信息外,还有一个extradata,这个extradata就是对应流配置帧的信息,包含所有配置帧[AVCC/HVCC 与 Annexb 码流格式相互转换](https://zhuanlan.zhihu.com/p/665881743),这个格式如是annexb格式,则和上面的规则0001/001开头一样的规则,直接分开就是对应的配置帧,如果是avcc/hvcc,则是另外一套规则,相对复杂些,不是简单的四字节头长度头,而是用特定结构解析,也是能分解出vps(只H265有)/sps/pps配置帧的信息,注意配置帧丢给解码器是有顺序的,简单来说,pps里有些信息解析需要sps里的信息,所以pps要在sps之后,而vps则在sps之前.

经过几种平台及媒体源的测试,如果编码后或是转发源媒体文件,如果原始nalu包是avcc格式的,ffmpeg转发到avcc媒体源是可以的,但是转发到annexb媒体源,有些会有问题,zlmediakit则大概率不行,而如果原始nalu包是annexb格式的,ffmpeg转发到avcc/hvcc/annexb媒体源都可以正常工作,应该是内部做了annexb转avcc/hvcc的处理,不知为啥avcc/hvcc到annexb的处理就有些问题,zlmediakit也可以正常工作,所以转发到媒体源时,直接把包变成annexb格式是比较好的选择.

综合考虑上面情况,来的包可能是组合类型(配置帧组+I帧)(配置帧组+SEI+I帧),需拆分类型(多个I帧)(多个P帧),在把包添加在AVSource时,拆分配置帧,合并I/P帧,原则上不对数据改动,保持avcc|hvcc/annexb格式不变,对于apple平台,非avcc,解码时要拆包并把annexb转成avcc/hvcc,对于android,非annexb,解码时要拆包并把avcc/hvcc转成annexb,在推流,非annexb,拆包并把avcc/hvcc转成annexb.

现在假定一台安卓设备与IOS设备双向视频通话,其中IOS,拉流用ffmpeg,使用IOS原生里的解码,编码后做如美化的图像处理,然后用zlmediakit推流,主要流程如下.

1. 用ffmpeg打开媒体源,先得到视频流里编码参数里的extradata,确定是用annexb还是avcc/hvcc,然后把extradata分解出vps/sps/pps,配置帧一般单独保存.
2. IOS硬解根据配置帧初始化解码器,注意这里vps/sps/pps不要带头,简单来说,不要前四个字节,不管是avcc/hvcc头还是annexb头,而ffmpeg需要看流格式,如果是本地媒体源或是hls这种,需要把vps/sps/pps重装成hvcc/avcc对应的extradata(这里的avcc/hvcc对应特定结构,非四字长度),如果是rtsp这种,直接把vps/sps/pps变成annexb格式,然后按顺序vps/sps/pps合并就行.
3. 继续读取媒体源,根据1里的,如果是annexb格式,需要先把包分开,并把annexb格式转成avcc/hvcc格式,送入解码器,MAC平台硬解注意把非数据帧过滤掉,如SEI帧,放入解码器会引起问题.
4. 解出来的图像帧由metal/vulkan渲染并根据配置做图像处理.
5. 读取IOS相机源,根据MAC的AVFoundation框架获取CVImageBufferRef源,和4用同样的渲染类不同对象渲染,根据配置决定做那些图像处理.
6. 编码器根据5里输出图像大小,帧率,码率等参数初始化编码器,在成功初始化编码器后,需要用相应API拿到的vps/pps/sps配置帧等信息,ffmpeg会根据设置,在I帧前一次/每次发送配置帧,而ios里需要自己使用API单独拿取.
7. 根据图像信息,初始化zlmediakit推流对象,并把第5步里的vps/pps/sps配置帧加上annexb头,因为MAC硬编出来的配置帧不带头信息,如果是别的平台或是ffmpeg就不需要了,然后送入zlmediakit推流对象.(ffmpeg推流有些不同,在初始化推流时,就需要把配置帧写入视频流AVCodecParameters对象extradata里).
8. 编码器继续将编码后的图像包压入队列,注意MAC编码后是avcc/hvcc格式的nalu包,需要转成annexb格式,在推流线程取出队列里图像包并送入zlmediakit推流对象.

而android假定用zlmediakit拉流,原生平台解码,编码,再用ffmpeg推流,主要流程如下.

1. 用zlmediakit拉流,一般来说,配置帧通常在第一个I帧之前发送,内部实现中,通道源对象会保存配置帧,并在新配置帧来,检查新配置帧相对老配置帧是否有更新,检测图像大小是否有变化等,是否需要重置解码器.
2. android根据vps/sps/pps初始化解码器,注意不同于IOS,这里需要annexb头的,就是要0001开头的四个字节,如果换成ffmpeg软解,流程和上面IOS一样.
3. 读取媒体源,因为是zlmediakit拉流,所以应该是annexb格式,可以直接送入解码器,但是这里我们不假定是用什么推流,不和媒体源绑定,直接判定一下送入的包是否是annexb格式,如果不是,因为android原生解码器要求annexb格式,则需要转成annexb格式,送入解码器.
4. 解出来的图像帧由opengl/vulkan渲染并根据配置做图像处理.
5. 使用ndk camera2获取数据到JniSurfaceTexture,和4用同样的渲染类不同对象渲染并根据配置做图像处理.
6. 编码器MediaCodec根据5里的图像大小,帧率,码率等参数初始化编码器,在成功初始化编码器后,不同上面IOS需要专门API拿配置帧,和ffmpeg类似,在第一个I帧前自动在编码回调里发出配置帧,根据设置决定是否每个I帧前发送配置帧.这里其实没什么,因为发送到我们维护的源,肯定也是要专门维护配置帧的,在转发源时,也会在I帧前把配置帧发送出去.
7. 根据图像信息,初始化ffmpeg推流对象,不同zlmediakit推流对象,在初始化推流时,就需要把配置帧写入视频流AVCodecParameters对象extradata里,因为android解出来的数据全是annexb格式,所以这里写到extradata也只需要把vps/pps/sps按顺序合成一个大包就行.
8. 编码器继续编码后的图像帧压入队列,android解出来的数据全是annexb格式,直接在推流线程取出队列里压缩的帧数据并送入ffmpeg推流对象.

音频相对来说简单些,一般来说,如G711A这些都没有配置帧概念,而AAC也只需要知道采样率,通道数,码率还有profile level就可手动生成配置帧,和avcc/hvcc与annexb格式一样,acc也有adts与asc格式,adts的话,一般是每帧数据加个adts头,这样可随时拉取并解码,而asc则是类似全局配置+数据,只需要给一次配置.因为拉流的基本信息加个profile level就可以初始化对应编码器与解码器,所以感觉现在asc用的更多些.
