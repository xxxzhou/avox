# 播放引擎排查案例集 ④：帧节奏与上屏停顿

> 状态: 有效 · 上次核对: 2026-10-01 · 权威源: avox 提交 `00ce5dd` + 记忆库(memory/2026-10-01.md)

一句话背景: 4K HDR 片「每秒卡一下、不如 VLC 流畅」，量化后是**上屏内容 1Hz 冻结 115~133ms**。
根因不在 present、不在解码吞吐，而在 **D3D11 → Vulkan 共享纹理的跨队列缺 fence 同步**。
本文记录症状形态、证据链、修法与可复用判据。

## 1. 症状的精确形态（先量化再归因）

- **不是**帧率低、不是丢帧计数异常，而是**上屏内容**每 ~1.000s 停一次，每次吞掉 3~4 帧的上屏时间。
- 周期与时长**跟随内容帧率**（媒体时钟量，非墙钟量）；恢复时刻锁定 **1Hz 墙钟相位 `x.474`**
  （如 `51.475 / 52.474 / … / 03.473`）。
- 与 VLC/系统播放器对比：帧时序量出来**完全一致**（同为 2:3 pulldown），人眼就是不如。
- 复现素材：`hdr_samples/LaLaLand_cafe_4K_HDR.mkv`（原 BluRay 位流、85Mbps、HDR10）。
  同片 SDR 重编、高码率重编 `hires2`（73.8M）均**不冻** ⇒ 码率/音轨/容器/HDR 全被排除。

## 2. 根因：跨 API 零拷贝直读缺同步

- DX11 解码/渲染走**计算着色器**路径 `Dx11CSVideoRender::renderToTexture`（**不是**
  `VideoProcessRender`），它把结果 `Dispatch` 进 NT 共享纹理后**从不 `signalFence()`**。
- Vulkan 侧 `VkWinImage::updateInputContext` 对 `interopType == inputNt`
  （`renderType == D3D11 && bInteropTexture()` 时置位）**早退、不等待**，直接**别名**该纹理。
- 两个 GPU 队列（DX11 写 / Vulkan 读）**互不排序** ⇒ 读方偶发读到**未更新的旧帧**
  ⇒ 图重算出与前一帧**逐字节相同**的画面 ⇒ 窗口以 24/s 均匀 present **同一张内容** ⇒ 屏上冻住。
- 故**引擎侧 present 间隔毫无异常**（`skip:0`、`gapUs 41~42ms`）—— 病在**内容陈旧**，不在 present。
  这也是本战役前期把方向定在 present 侧、白走数小时的原因。
- 旁证：`VideoProcessRender` 本就有 `outSharedTex->signalFence()`（且其 `canWrite()` 门被注释）
  ⇒ 设计里写方**本该** signal，是 CS 渲染器漏了。

## 3. 决定性证据链

- **引擎三重探针全绿**（`AVOX_PROBE_PRESENT=1` 同轮）：`renderWindow` normal 24/s、
  `noGraph/noOutLayer/notReady` 全 0；`graph->run()` 峰值 13~17ms；`vkQueuePresentKHR` 24/s、
  `skip:0`、`outOfDate:0`、present 峰值 1.5ms；`syncResult=none` 24/s、`quick` 恒 0、`noTick` 0。
- **帧身份探针**（`AVOX_PROBE_ID=1`）：`dup:0`、`ptsGapMax:42` ⇒ 引擎交付的帧序列本身没有重复。
- **DWM 侧无丢帧**：`missed+0 dropped+0 late+0 outstanding=1`；停顿期间 DWM 仍持续出新合成帧，
  只是内容与前帧**逐字节相同**（`worstDiff=0`）。
- **A/B 定谳**：`AVOX_PROBE_HASH=1` 的哈希探针在 DX11 立即上下文做 `CopySubresourceRegion` + `Map`，
  `Map` **隐式等待 DX11 GPU 完成** → **意外补上了缺失的同步** → 停顿 **13 → 0**（各 2 轮稳定复现）。
  ⇒ 一个"本为诊断"的探针改变了时序反而成了铁证。
- 同轮屏采与引擎日志用绝对墙钟对齐（`/d/tmp/exp/run_align.sh`）——**跨运行比数据必然得出矛盾结论**。

## 4. 修复（avox `00ce5dd`，4 文件 / +55 -1）

| 文件 | 改动 |
|---|---|
| `avox_windows/dx11/Dx11CSVideoRender.cpp` | `Dispatch` 后补 `outSharedTex->signalFence()`（写方同步点） |
| `avox_vulkan/windows/VkWinImage.cpp` | `inputNt` 早退前补 `exShardTex->waitWriterFrame()`（读方等待） |
| `avox_windows/dx11/Dx11SharedTex.hpp/.cpp` | 新增 `writerSignalVal`（写方提交值）+ `frameWaitEvent`（懒建，`releaseHandles` 关）+ `waitWriterFrame()` |

`waitWriterFrame()` 的设计要点：复用引擎已有的跨设备 `ID3D11Fence`，**已追上则零开销返回**
（`GetCompletedValue() >= target`），否则 `SetEventOnCompletion` + `WaitForSingleObject(100ms)` 兜底，
不引入稳态成本、也不会在设备异常时卡死渲染线程。

## 5. 验收口径

- 修复后原片 **5/5**、其它片源 **3/3**（`Passengers_Breakfast_4K_HDR.mkv` / `lala.mp4` /
  `lala_vonly.mkv`）**上屏停顿 = 0**；内容更新率 21.8 → ~24/s。
- **撤掉全部诊断探针后重建**，再冒烟 2 轮仍 `上屏停顿=0`、`longest below-run: 0 frames, worstDiff=0`。
- 白盒回归：`avox_tests` **96/96 用例、1210/1210 断言全绿**。
- 唯一可信验收 = **同轮屏采**：`>100ms` 空洞消失，**同时 `33/50ms` 交替必须仍在**
  （别把正确的 2:3 pulldown 一起"修"掉）。

## 6. 否证清单（别在这些路上再花时间）

present 模式（FIFO `vsync=true` 与 MAILBOX 同症状）· 音频主时钟 · GOP 结构 · 窗口尺寸 ·
`setHdrMeta` 周期 · 解码队列振荡 · `quickCounter` / `fps` 抬高致 quick 不 tick（该轮 `quick` 恒 0）·
周期性图重建（全程仅 1 次）· GPU 引擎瓶颈 · 跨适配器 · MPO/采集伪影（GDI BitBlt 独立复现）。

## 7. 可复用判据与手法

1. **仪器分层是第一课**：供给侧仪器（`stutterprobe` 离屏 `onFrame`、`avox_cli -log-render`）
   对「上屏冻结」给**假阴性**——问题片在两者下都报"一切正常"。判"卡"必须用**上屏仪器**
   （`/d/tmp/dxgidup2.exe <秒> <窗口类名>`，测 DWM 合成后的光子）。
2. **判据用「内容是否变」，不是「有没有 Present」**：present 节拍干净与上屏内容每秒冻一次
   **可以同时为真**。两种机理的区分：供给卡 ⇒ 渲染回调**本身**出现 >100ms 间隔；
   present 卡（整段跳过）⇒ 渲染回调零间隔、只有上屏有空洞。
3. **采集前必须置顶目标窗口**：`dxgidup2` 抓的是屏幕实际显示的内容，被别的窗口遮挡时
   会抓到**遮挡者**（本机踩过：抓到每秒刷新的 panvox ⇒ `events=10`、STALLS 间隔恰好 1000ms 的伪影）。
   固定动作 `wininfo move <类名> 100 100 1280 720`；判据 `events` 应 ≈ `秒数×24`。
4. **凡在共享 NT 纹理上做跨 API 零拷贝直读，读方必须等写方 fence** —— `inputNt` 那条路原来没有。
   这是本案例最值得记住的一条通用纪律。
5. **对照素材纪律**：判观感不能用静态测试卡（`avox_selfcheck_4K_*` 是 0.75Mbps 静态彩条，
   与真片差 113×）；每份对照只改一个变量，且同轮带一个已知"顺"的样本当哨兵。
