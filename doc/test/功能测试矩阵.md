路径结论 (回应「H264 是否没走 Vulkan」): **不是编码差异**。Windows 硬解 H264/H265 默认
同选 FFDx11Decoder (ff_h264_dx11 / ff_hevc_dx11, 见 AVTrack.cpp getDefaultDecoderName;
FFVkDecoder 注册了但非默认), 离屏取帧同一条混合管线: FFDx11Decoder(d3d11va, D3D11 NV12
纹理) → Dx11CSVideoRender(原生 CS) + VkVideoRender(Vulkan 图 NV12→RGBA→NV12→CPU 输出),
H264 日志可见 vk instance select gpu → create dx11 device → graph nodes 全程。
**硬解不取帧时 GPU 数据直接上屏; 取 CPU 帧必须经 Vulkan 图 (或原生 CS) 转换 —— 这是设计,
不是缺陷。** 窗口渲染 (vkwindowtest) 与 WebRTC 链路全程不受影响。

## 玻璃到玻璃延迟 (2026-09-10 实测, 营销数字)

方法: python 按 30fps 生成帧并把**生成时刻墙钟**烙进画面 (Pillow, 避开 ffmpeg drawtext
在本机必崩), libx265 yuv420p GOP 1s 推 RTMP 进本机 ZLM; 四协议各采 3 个稳态样本,
latency = 截图 mtime − 画面烙印值; latprobe 取解码输出帧 (渲染 ≤1 帧)。
**数字含源端 x265 编码 lookahead (~0.3-0.4s), 真实相机源会更低 → 偏保守**。
播放器口径: 低延迟模式 (AVOX_MP_LOW_LATENCY_BOOL + delay 0 + speed 1.2)。
工具: `script/testenv/glass_latency.py` + `samples/functest/latprobe.cpp`。
源用 H265 是选型时 W0 尚未定界; 现确认已解决 (矩阵 W0, 09-11 复测 RTSP/RTMP H264 -hard 全链 nv12 直出 PASS), 为与既有延迟数字同口径保留 H265 源。

| 协议 | 延迟 (3 样本) | 备注 |
|------|--------------|------|
| **WebRTC (ZLM 信令)** | **0.71 / 0.70 / 0.89 s** | 招牌数字: 亚秒级 |
| RTSP | 1.71 / 1.72 / 1.74 s | |
| RTMP | 5.74 / 5.75 s | ZLM RTMP 出口 + GOP 缓存, 调 ZLM 配置可降 |
| HLS | 8.67 / 8.67 s | 分段协议固有, ZLM 分段时长可调 |

对照 (默认缓冲口径): RTSP ~1.6s / RTMP ~5.9s —— 与低延迟模式差异不大, 大头在 ZLM 出口与
编码端; RTMP/HLS 想压低优先调 ZLM (gopCache/分段时长), 播放器缓冲已非瓶颈。

坑：`open`/双击 .app 启动等于不带参数，默认 URL 是 `rtsp://127.0.0.1:554/live/avox264`，
而 mac 上没有本地 ZLM ⇒ 空窗口无画面，且拉不到流时播放器 tick 仍 yield 自旋吃满一个核
（`swtch_pri` + `MediaPlayer::collectStatus/compateIoTime`，待优化）。要看画面必须带 LAN 地址。

`screenShot` 在 Apple 上原先必失败，两处叠加：`MetalRender::fetchFrame` 拿 `[metalLayer
nextDrawable]`（一张全新未绘制的 drawable，抓到清屏色；且取了不 present 还占空池子），改为
记住上一帧真正画过的目标纹理 + `framebufferOnly=NO`（否则 drawable 纹理不能当 blit 源）；
`getBytes:bytesPerRow:` 传的是 `format.rowPitch`，而 avox 约定 rowPitch=0 即紧凑，
Metal 收到 0 只写第一行 ⇒ 整张全 0（看图器显示成白/透明），这条离屏路径同样中招。

**已知回归（待修）**：定时截图会把渲染压到一半并卡死在低帧率。同一路 `live/test`
对照实测：带截图(每 3 秒一张) fps 30 → **掉到 17.0 钉死**，不带截图**稳定 30~31**，
两者 loss 均为 0、CPU 3%。三个原因叠加 ——
① `VideoRender::screenShot` 同步阻塞调用方(`future.wait_for(1s)`)等渲染线程回填；
② `MetalRender::fetchFrame` 每次新建 MTLTexture + blit + `waitUntilCompleted`，
每次插一个全 GPU 同步点并读回 3.5MB；
③ 为修抓帧引入的 `lastTargetTexture` **常驻持有一张 drawable 纹理**，而 CAMetalLayer
drawable 池默认只 3 个，被长期占掉一个后 `nextDrawable` 更易等待（这最能解释「掉到 17
之后钉死」而非抖动）。拟改为仅在抓帧请求置位时把画面 blit 进一张复用的离屏纹理，
drawable 用完立即放手，并把 PNG 编码挪出热路径。**在此之前定时截图只用于远程无 VNC
