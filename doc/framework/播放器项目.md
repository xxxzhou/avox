# 播放器项目

## 基本架构

播放器项目主要分如下几点：

1. 基础功能模块，如socket封装，线程池封装，日志，SSL解密等。参照ZLToolkit。

2. 网络层解协议模块，包含控制命令与媒体数据，常用解RTSP/RTMP/私有协议.参照[ZLMediakit](Mediakit.md)

3. 解码模块，视频软解如x264,x265,音频软解aac,G711等。

4. 视频渲染模块，包含硬解实现，渲染与硬解方案一般是绑定的，不同平台的实现方案不同。如windows下dx11/dx12,linux下opengl，android下opengles，ios/mac的metal,共同方案有vulkan,但是其硬解方案搜到的信息暂时不支持ios/mac.

5. 音频的渲染模块，不同平台有专有方案，windows平台有WASAPI，liunx下的alsa,mac/ios使用core audio，android使用AudioTrack。

6. 图像处理模块，如常用水印，LUT，AI边框显示，视频特效，去畸变等,可以组合使用。

7. 音频处理模块，可以参考webrtc/speex，如重采样，降噪，自动增益，回声消除等，可以组合使用。

8. 播放器模块，整合上面所有模块，添加音视频同步，缓存延迟平滑播放，多倍速播放，Seek定位，视频状态切换，扩展多路视频同步，每个功能需要对比至少一个项目确定设计方案，确定功能是否多方案实现，能否动态切换。

方便调试的功能，需要在设计接口时就考虑，比如有选项，可以把未解码的数据保存到文件用于后期分析问题。

### 播放器线程交互

其每个播放器对象内部，由本身去创建的线程，主要有如下几个线程。

1. socket线程，去协议头，解析控制命令，解析多媒体数据成H264/H265/AAC数据。

2. 播放器自身轮循线程，控制命令处理，状态切换，收集socket线程处理的数据,音频在当前线程解码并缓存PCM数据队列，视频未解码的H264/H265数据直接转发到视频解码线程中。

3. 音频渲染线程，与2交互缓存的PCM数据，经音频处理模块，然后渲染。

4. 视频解码线程，与2交互未解码的H264/H265数据，并进行解码，缓存解码后的YUV图像队列。

5. 平台界面UI线程，与4交互解码后的YUV图像数据,或是硬解的纹理，经图像处理模块，然后渲染。

音视频同步暂时定为，音频渲染线程校正时间基，视频以时间基为准，检查帧显示是否正常 ，以实现音视频同步。

音频解码需要一个单独线程吗？现在来看音频解码压力也不大，直接放到播放器轮循线程里也可以。

因视频解码相对音频来说，一般比较费时，会堵塞当前线程，所以专门开线程去解码视频，第一个问题，解码线程直接与socket线程交互？还是解码线程与播放器轮循线程交互，暂时决定与播放器轮循线程交互，首先这样socket模块不与播放器模块相对独立，播放器模块本来就要包含所有模块。

因为视频专门开了线程解码，所以H264/H265数据帧需要写入缓冲区，播放器轮循线程在提到socket的回调数据后，H264/H265数据帧直接写入缓冲区，而解码线程则是一直读取缓冲区数据，是用数组模拟的队列缓冲还是环形缓冲？虽然基于数组实现的队列在某些方面与环形缓冲区有相似之处，但环形缓冲区在空间利用效率、数据处理灵活性和效率以及实现复杂度和性能开销等方面具有明显优势，使其在处理视频解码线程和播放器轮循线程之间的 H264/H265 数据交互等场景中表现更为出色。

因其播放器内部缓存，线程的交互，不同播放器如果要同步，几乎是不可能的事，所以如果有多组画面需要同步，只能改为播放器内部拉多路视频流，在同样的图像渲染线程中同步才能完美实现。

## 构建 

CMake为主，多平台windows/linux/mac/ios/android支持，尽可能在CMake中构建,包含常用的安装目录，复制目录等处理，方便多平台统一构建与调试，cmake也可引入python脚本减少平台差异。

主要逻辑主要以C++完成，定好每层导出结构与接口，输出的头文件，输出头文件里不包含任何具体实现，只有结构与抽象类，回调类，以swig自动导出成C#/android接口方便扩展在windows/android界面程序。

第三方库，如果有改动以及不大的库，以引用特定git分支/标签做为子模块，如zlmediakit引入模式，如果没改动，并且项目编译复杂的，要求用户有对应系统下安装相应库，项目以引入库方式导入，如ffmpeg，openssl等。

## 计划

如果以vlc/ijkplayer做基础，其主体框架是C，做为一个通用播放器，一些特殊需求也不好集成，如多路视频同步，还有这些都有对应的UI捆绑，需要对项目去UI，并且vlc/ijkplayer非商业友好，特别是ijkplayer以ffmpeg为核心，这在商业上使用有些问题，当前项目可以在没有ffmpeg上实现，比如软解用x264/x265,硬解用平台自身提供，网络协议用zlmediakit处理，后面可以把ffmpeg当插件集成进来做功能备份。

对图像渲染模块/图像处理模块/网络层解协议模块相对比较熟悉，需要查看更多对于硬解，音视频软解模块，音频渲染，音频处理的实现，最后对播放器各子功能节点的实现以及IOS开发还不太了解，需要尽快熟悉与了解，然后定义结构与接口，填充模块实现。

## 一些细节记录

I帧根据设定一般在1-4秒，解码以I帧为基础，如果想得到当前帧就能显示，必需得到之前帧到I帧所有信息，想秒开一般是服务器缓存前I帧到当前的所有数据，当客户端连接后，服务器会发送缓存的所有数据，在客户端播放时，根据当前时间，以及上一个I帧不停解码到当前帧并显示出来。

zlmediakit里已经把网络包解成单帧数据，包含解包(单个P帧)/拆包(如SPS/PPS一般是组合一起)/组合包(I帧很大,多包发) 。

视频的SPS/PPS/PPS信息，音频如AAC的采样率/通道数(2字节的信息)，都需要在解码前传入解码器，在拉网络包也需要得到这些关键信息后，才能启动解码流程。对应的H264/H265/AAC缓存队列，也需要以这些信息开头，否则也解不出来。

H264/H265的解码器，如在IOS，android，windows硬解出来本来就是在队列中，可以不考虑缓存解出来YUV数据，缓存指针指向对象/PTS,只用来确定是否需要显示，然后在渲染线程根据指针头渲染。其中IOS/android使用的RAM属于统一内存架构，CPU/GPU可以直接访问，而windows平台硬解如果是用独立显卡N/A，出来的应该是GPU显存上的纹理，不建议CPU访问，需要拷贝并且很费时费IO。

变速播放，超过4倍速后的方案设计,变换与缓存，时钟之间的考量。

多Oberver的支持，头文件隐藏多Oberver转发实现。

环形BUFFER，考虑扩充，数据段以头(校检字节，长度字节),数据这样保存，如果音视频属性发生变换，如分辨率，采样率等，能通知BUFFER清空老数据。环形BUFFER以H264/H265/AAC数据为主，在得到解码信息的配置帧后，马上创建解码器，将H264/H265/AAC数据快速压入解码器，保证H264/H265/AAC队列不要压入太多数据，而解码出来的数据，以一定大小的Frame为主，如YUV/PCM，以vector仿队列保存，考虑H264/H265/AAC数据里还有硬解，不同平台数据类型全不同，具体实现可以考虑泛型具化，因为这些细节肯定是项目内各模块处理，不需要考虑给外部项目，所以泛型具化在这倒是可以随便用。

当视频分辨率变化，音频采样变化等，很多对象都要通知，已知需要的对象是环形BUFFER，解码数据队列，解码器，渲染上下文，在这些对象都在通知处理后，如Buffer清空，渲染重新申请相应纹理，在这些处理完成后,这些处理可能在不同线程，这些动作应该都要加锁，保证与正在处理的队列同步，等这些操作完成后，才能继续数据输入/处理/渲染。

锁的粒度要细，所以尽量在各自对象设计的API中，如果有线程交互，相应API实现时，能在里面加锁，就不要放在外面交互，如环形BUFFER中，视频PipeGraph中。锁对应的范围如果有回调，一定要注意，尽量避免锁中出现回调，锁中回调如果避免不了，也要考虑回调在项目内，不要放给外面，并且这个回调尽量简单，别又调用大的API，然后就是回环死锁的问题。

要考虑纯解码无渲染的要求，如音频重采样，视频码率，分辨率变化，就需要先解码再编码，需要的点就要求快，考虑重封装时，视频包与音频包也是时间对齐的，应该还是需要做同步，但是时间轴要能自动变速。

在渲染前，输入数据线程与渲染线程是否在同一线程，不在的话，输入数据要做备份，是否需要自动处理，先假定不在同一线程，复制数据，渲染线程开始运行后，检查与输入数据的线程是否一致，如果一致，就不需要复制。

解码器实现列表，如果解码失败帧过多，自动变换到下一个解码器。IOS/Android有自己的硬解方案，其方案在ViotplayerSDK都另外开线程专门做解码放入对应的队列，切换到硬解，需要预先填充一些数据给解码器，避免解码器因解码时间过长导致的丢帧。

日志记录，如果有多个播放器，当前播放器唯一的标识，如果同播放器有多个同视频流或是音频流，需要记录唯一标示。

## 接口设计

定义成熟的接口需要熟悉多个方案与项目才能给出。

先快速用起来，定义合适的接口，先对接如ffmpeg成熟项目实现接口，然后扩展实现接口，对接特定需求与避免非商业友好开源协议。

一些基本的接口简单设计如下。

1. socket线程与解协议接口参照zlmediakit设计。

2. 软解接口，需要能对接x264/x265/faad/ffmpeg等实现。

``` mermaid
classDiagram
    class IMediaCodec {
        +initCodec(): 初始化解码器，如H264/H265需要的sps/pps信息，音频如AAC是二字节的压缩信息。
        +inData(data): 输入未编码数据
        +closeCodec(): 关闭解码器
        +setObserver(observer: IMediaCodecObserver): 设置回调
    }
    class IMediaCodecObserver {
        +outData(data): 得到编码后数据
    }
    IMediaCodec --> IMediaCodecObserver : calls on output
```

3. 图像/声音处理管线

YUVFrame与ImageFrame分开表示，YUVFormat也与ImageFormat分开表示。

``` mermaid

        +getOutFormat(): 得到输出格式，图像是长宽，声音是采样率/通道数
```
