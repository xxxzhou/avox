- **mac 切流彩色马赛克(偶发, 拖入新视频时) → 已修 a5af7c7**: 症状 = 画面变成「橙/红/蓝/绿
  色带 + 边界噪点」马赛克(正常应为紫黑), 随后**冻结**; 用户配方 = **显示 HDR→SDR→切回, 再拖
  文件**(即宿主重挂平台视图的动作)。根因 = 重挂会把 `CAMetalLayer` 重置回 `RGBA8Unorm`(SDR),
  而引擎直通态(`bF16Pipeline`/16F 管线)不变、标志没变故不触发 `hdr pipeline flip` 重建 ⇒
  **16F 管线绘进 8bit 目标 = Metal 未定义行为**。判据: ①日志(修后)`layer format drift: target
  f16:0 pipeline f16:1 -> re-apply layer config`; ②帧级转储(env `AVOX_METAL_DUMP=<dir>`,
  每流头 12 帧落盘「解码输入 pb 平面 + 渲染目标纹理」)显示坏帧目标 4B/px 而管线 f16=1、
  输入帧干净、输出几何与输入完全对齐、仅颜色炸开 ⇒ 纯色彩通路; ③别往解码/几何查(转储已
  排除)。修 = `MetalRender::renderCVPixelBuffer` 每帧核实际目标格式 vs `bF16Pipeline`, 不符即
  `applyLayerHdrConfig` 回写层配置并**弃本帧**(新格式对下一个 drawable 生效)。验收 = 用户按
  原配方反复跑: 守卫命中 4 次、717 帧转储零花屏帧、无法再复现。panvox 侧配套「表面重挂补发
  堵漏」在 `c2970e8`, 与引擎守卫互补。
- **mac 切流/关闭闪退(Metal 完成线程 SIGSEGV) → 已修 a5af7c7**: 判据 = `.ips` 栈
  `EXC_BAD_ACCESS at 0x0`、线程 `com.Metal.CompletionQueueDispatch`、栈顶
  `avox::MetalRender::renderCVPixelBuffer` 完成 block → `_CFRelease(CVMetalTexture)` →
  `CVMetalTextureCache::bufferBackingNotInUse` → `CFArrayAppendValue(NULL)`。根因 =
  `closeTextureCache()` 随 `releaseGraph()`(每次 `hdr pipeline flip`/关流都走)直接释放缓存,
  帧纹理却要到命令缓冲完成才释放 ⇒ 缓存先死。修 = 缓存与 device 同生命周期 + 「在飞帧计数
  归零才释放」。修后日志 `texture cache retire deferred, inflight:N` = 命中过原崩溃窗口并
  安全兑现(实测两轮拖动压力 17 次)。**排 crash 先看 `~/Library/Logs/DiagnosticReports/` 的
  `panvox-*.ips`**, 同栈即定案, 别奔解码查。

- **多声道素材「声音怪」(对白极轻/只剩音乐环境声, Mac 专属) → 已修 fe6ccc1(1002)**: macOS 分支把解码侧声道数(7.1=8ch)直接设给 AudioUnit, AUHAL 对声道数不匹配**按序直通不做矩阵下混**, C(对白)/环绕声道在立体声设备被丢; 判据 = 解码 PCM 声道能量分布(ffmpeg `-f s32le` 拉流 python 算 RMS, 实测 FC 占 96%/88% 的两条素材同病, L/R 主导的才无感)。Windows 不病: WASAPI 走 GetMixFormat。日志特征: `AudioUnit render init success, channels:8`(修后应为设备声道数)。修 = AU 创建后查 `kAudioUnitProperty_StreamFormat`(output scope) 取设备真实声道/采样率作 FFResample 下混目标(下混管线本已就位, renderDesc=8ch 时 bSameDesc 旁路), 查询失败按 stereo 兜底。**用户体感描述「声音怪」先问清方向(人声缺/爆音/变速), 人声缺=对号本条**。

- **黑屏有声(画面全黑、音轨正常、零 buffering)+ `[FF][hevc] PPS id out of range` 风暴(手机/微信导出 HEVC 双 PPS 流) → 已修(1003)**: 这类导出的 hvcC 与首样本常带**两个不同 id 的 PPS**(实测 IDR 切片 `slice_pic_parameter_set_id=0`、非 IDR 切片 `=1`, `ffmpeg -bsf:v trace_headers` 可证, 两 PPS 缺一即对应切片族全灭)。`addConfigPacket` 旧语义按 NAL 类型整体替换只留最后一个 → extradata 缺另一半 PPS。叠加两刀放大: ①configPackets 混入水印 SEI(hvcC array[3] 常见, ASCII `xmm100c}` 类)时 parseConfigs 整段判失败 → params 从 SPS 尺寸(544x960 编码尺寸)回退容器尺寸(540x960 显示尺寸) → 误判 `video size changed` → updateSize 硬解重置, 把第一次 init 恰好还凑合的参数集组合换死; ②VDecoderTask 只认 updateSize 重置, 纯 add 不重建。症状: `[FF][hevc] PPS id out of range` + `Skipping invalid undecodable NALU: 19`(IDR) + `Could not find ref with POC` 风暴, 视频窗纯黑(抓帧 mean=0.0)而音频正常。**修**: addConfigPacket 按参数集 id 替换(同 id 更新/异 id 并存; id 提取注意 h265 PPS 的 ue(v) 在 2 字节 nal 头之后——第一版漏跳导致两 PPS 算出同 id 复现原病); parseConfigs 跳过非 VPS/SPS/PPS NAL; H265 SPS 尺寸应用 conformance window 裁剪(544→540, 免无谓重置)。**判据**: ①片源体检先行——参考解码器软解+dxva2 硬解全通则片源无病; ②avcodec 级探针(引擎同款 extradata+原始包直喂)能出帧而引擎黑 = 矛盾在 configPackets 组装层, 别往 avcodec/渲染查; ③引擎拼的 hvcC 数组数少于文件真 hvcC(`hvcC` box python 解析对比)即坐实替换丢参。
- **iOS 真机「全黑不出画」与「出画一两秒后定格」= 两个不同病灶, 别混判(1003, 修在 panvox 侧)**: 两者都表现为「黑/卡」, 但一个是**从没出画**、一个是**出过画再定格**, 定谳前先问清用户是哪种(用户原话「画面只出来一次」「只有一二秒的画面, 后面就卡住了」即后者)。
  - **全黑不出画** = `PVVideoMetalView` 的 `CAMetalLayer.drawableSize` 恒 `0×0`。该 layer 挂进 Flutter 平台视图(UiKitView)后 UIKit 的 `bounds × scale` 自动同步不生效, MoltenVK 按 bounds 自算 extent 把交换链建起来了、层上却无 drawable 可出(原生 Metal 腿则 `nextDrawable` 恒 nil)。**修**: `layoutSubviews` 里显式钉 `drawableSize = bounds × contentsScale`(幂等, 每帧布局收敛, 且 `want > 0` 才写)。
  - **出画一两秒后定格**(音轨/进度/时钟照走, 只是画面不动) = 上一会话为治「层内容不上屏」加了 `presentsWithTransaction = YES`。该开关语义是 **drawable 要等 Core Animation 事务提交才上屏**, 而 **VK/Metal 渲染线程没有 runloop、没有隐式事务** —— Flutter UI 一停止动画(首帧布局完成/界面静止)就再没人提交事务, 画面随即定格。**修**: 改回关(该属性不设即默认 NO, 与 HEAD 语义一致); 原「不上屏」问题已由上面的显式 `drawableSize` 收敛解决, 不需要它。
  - **判据(同机 A/B, 可复用)**: 容器 `Documents/panvox/pwt.txt` 写 `1`/`0` 切该开关(插件读一次即缓存), 同一二进制 + 同一片源各 4 轮 —— 关 = early/late 抓帧差异恒 769860 像素(**在更新**), 开 = 差异恒 0(**定格**), 8/8 干净切分。**抓帧判定纪律**: 必须配时间码与「色数」指标, 只看 ROI 亮像素会把首页 UI/加载渐变误判成「有画面」(踩过)。
  - **不中此族的旁证(先排除渲染链, 别瞎插针)**: 引擎侧 `rw-in`/`og-in`/`tick present` 全 30fps 稳态、`ready:1 cmd:1 tex:1`; `mtl cb:` 探针 `status 4 err:none` 且整轮无错误帧(⇒ **不是 GPU PageFault**, 当日「VT 缓冲池回收致 PageFault」的假设就此否证); `vk-in record:` 全程只有 1 条(⇒ 图没被逐帧重建, `bResetFlag` 假设也否证)。**渲染在跑、只是没人提交事务上屏** —— 这是「出一两秒就卡住」的完整解释。
  - **硬解/软解两条腿都中**: mp4 硬解 GPU 腿(`bGpu:1 inFmt:4`)与 avi 软解 CPU 腿(`bCpu:1 inFmt:0`)在修后各 3 轮均在更新(软解腿差异 ~694000), 故本族**不是某条解码腿的问题**, 是层/事务层面的。

- **显示格时间戳截断族(硬解 VT 独有, Win/软解无感)**: PocRestamper 按帧长铺显示格, 遇非整除帧长或重锚错位即出周期性抖动, 三宗:
  - **A. 每几秒跳一下(丢帧追赶), 无 buffering 无 crash → 已修 79abb44**: 丢 ctts 的 B 帧流(moov 里 0 个 ctts 有 stss, 迅雷拼装 mp4 高发)PocRestamper(eb106f0) 按 33ms 平坦格推进, 对 30000/1001(33.367ms) 每帧欠 0.367ms → 视频钟持续落后音频 → 每 ~4.5s 攒满丢帧门限静默丢一帧(drop 日志被注释)。**FFmpeg 车道走 dts 链不吃包 pts 故 Win 无感; VT 车道透传包 pts 吃满漂移**(IOSVDecoder 用 packet.pts 喂 CMTime)。判据: `-log-packet` 包 pts 显示序增量恒 33(旧)/33 与 34 交替(修复)。修 = 显示格 µs 化(与 c3f92b0 同 ms 截断族)。
  - **B. 同类片源仍每 2s 跳一下 → 已修(0927); 别因「79abb44 已修」就结案**: 根因 = PocRestamper::updatePoc 的 IRAP 分支原 `fullPoc += pocStep`, 用**解码序前一帧**的 POC 定位 IDR 显示格, 而它不一定是该 GOP 显示序末帧(自适应 B 位置)→ IDR 抢到已占用的格(**重复 pts**)+ 留一空格; 重复 pts 触发 VideoTrack::restampFramePts 的 `pts < lastInPts + nominalFrameMs/2`(=16ms) 单调守卫 → 后续帧被强制成**纯 33ms 格**(29.97 需 33/34 交替)→ 每帧快 0.367ms, ~43 帧后超 16ms 阈值**一次性跳回半帧**, 每 IDR(60 帧≈2s)一轮。**判据三连**(缺一不可): ①`grep -E "restamp|reorders"` 见 `poc restamp active: ... (ctts lost)` 或 `SPS VUI declares reorder frames`; ②`-log-decode` 输出序增量出现 **16**(半帧), 34ms 占比仅 ~18%(正确 36.7%); ③`-log-packet` 里**每个 IDR 的 pts == 前 2 帧的 pts**(撞格, 10 个 IDR 中 7 个)。软解对照干净(34ms 37.2%, 走 dts 链单调不触发守卫)。修 = IRAP 分支改 `fullPoc = maxFullPoc + pocStep`(GOP 内维护 maxFullPoc)+ **VUI 预激活**(SPS 声明 `bitstream_restriction_flag && num_reorder_frames>0` 即首帧 activate; 首帧 dispUnits=0 恒等, 带 ctts 的正常流下一帧被 `pts!=dts` 旁路闸拦下)。**验收**(同片源 12s, Mac VT): IDR 撞格 7/10→0/10; 34ms 占 (33+34) 17.9%→37.0%(理论 36.7%, 四次重跑 36.9~37.1%); 16ms 半帧 4→0; IDR 间距 1968/1969 抖动→恒 2002ms(=60×33.367ms)。片源参数: POC lsb 仅 5 位(`log2_max_pic_order_cnt_lsb_minus4=1`, wrap=32), 自适应 B 位置, stss IDR 每 60 帧; **moov 可能在文件头**(本例 11.7MB 在 ftyp 后, 与「moov 在尾」的常见拼装片相反)。**验证坑**: 改动给 PocRestamper 加了成员(sizeof 变), 只重编 `.cpp` 再手工重链 = 「新头文件对象 + 旧头文件库」错配 → `make_unique<PocRestamper>()` 按旧尺寸分配、新 `.o` 写新成员即**堆越界**, 症状 `BUG IN CLIENT OF LIBMALLOC: memory corruption of free block`(EXC_BREAKPOINT/SIGTRAP) 而栈落在无关 AppKit/CoreUI/CoreSVG —— **极具误导性, 必须整库重建**。
  - **C. seek 到任意位置后画面持续抖动 → 已修(0927)**: PocRestamper 输出的是**帧计数轴**(`pts = pts0 + 显示位×帧长`), 只在连续播放时与容器时间轴重合; seek 后容器 dts 大跳而轴**原地续数** → 错开整段(实测 seek 到 5053s 后轴停在 10.4s, 容器已到 5051s, 偏差 5,040,626ms≈84min)→ `AVSource::alignPacketPts` 报 `diff too large,no sync` 把**音频拉到视频轴** → VT 按错误时间轴排帧。原有自愈没救: feed() 只认 `dts < lastDts - 帧长×2`(**回跳**), **前向 seek 完全不触发**, 轴值与容器陈旧值重合时也不写回 → `pts!=dts` 旁路闸永不触发。判据: `-log-packet` 里 seek 落点首包的 pts 与 dts 差**数千万 ms**(正常只差毫秒取整, ≤7ms)+ `alignPacketPts ... diff too large,no sync`; 落点必是关键帧故一定有重锚机会。修 = feed() 在 **IRAP** 上校验本轴 vs 容器时间, 偏差超 `kRebaseOffMs`(=1s) 即重锚显示格原点到该 IRAP 的 **dts**(IRAP 解码位次==显示位次; 用 dts 因单调无野值)。**阈值不可省**: 无条件每 IRAP 重锚会把轴钉到容器时钟, 而本片首样本 dts 自身偏离网格 7ms → GOP0→GOP1 冒一次 **41ms 杂格**; 加阈值后与修复前逐格一致。**验收**(seek 到 5053s): 落点 pts 10437→5051063(=dts, 与音频 5051072 差 9ms); `diff too large` 有→0; 输出间隔 33:734/34:108/35:103/36:12/133:1 → 33:620/34:358(34ms 占 12.8%→36.6%); 连续播放 150s 零回归。现场认日志 `poc restamp rebase: axis off <N> ms (seek)`。
- **后向 seek 后画面脱离音轨 → 已修 24ff54d(全平台, 与上同族但不同组件)**: 往回拖进度条后画面时间轴停在旧位置, 与音轨各走一条。根因 = `VideoTrack::restampFramePts` 的单调守卫(`pts < lastInPts + 帧长/2` → 续格 `lastInPts+帧长`)只认倒跳、把 seek 重入的大倒跳当成 B 帧重排乱序; 后向 seek 时旧位置残留帧的 pts **大于**目标位, 逃过 `seekDiscardPts`(只丢目标位**之前**的帧)进入帧队列并顶高 `lastInPts` → 新位置的帧全被续格前推到旧轴。**前向 seek 残留帧 pts 小于目标位本就被丢, 所以只有后向拖中招** —— 「某些时间段/某些操作才抖」的典型成因。判据: `-log-packet` 与 `-log-decode` 同开, 比同一时刻**包 pts** vs **解帧 pts**(实测 `wall_long.mp4` seek 200s→20s 后 包 33567 / 解帧 213299; 正常只差管线延迟 ~6.9s)。修 = 守卫前加大跳旁路 `|pts - lastInPts| > kFrameJumpMs`(=1s) 即以本帧重开格; 重排乱序都是帧级小跳(≤100ms)不会误伤。验收: `wall_long` 后向 seek 后 包 34233~46233 / 解帧 27333~39333 同轴; 本片后向 seek 60s 稳态 34ms 占 36.4%、前向 3000s 36.7%、半帧 0; 连续播放 150s 零回归。
- 全片**零规律散点跳画**(一次一帧洞)、`[FF][h264] Invalid NAL unit size (声明>实际)` 与 `partial file` 风暴同现、moov stco/stsz 逐样本字节完好 = 网关按连接随机掐杀读段: 每次抓段 = avio_seek 新建连接过一次掐杀彩票, 重试耗尽后 EIO 漏给 avio_read 把已缓冲半截样本当成功 → mov.c 拼出截断包喂出 Invalid NAL → 丢 AU → 跳; moov 表区(如 4.2MB)再读被掐 = 同源。→ 已修 e409b32(抓段重试预算 3→10, 单连被掐率 ~25% 时连杀 10 次≈百万分之一)。**判据: 同内容区段换时间重放 corrupt 位置漂移 = 读路径, 位置钉死 = 文件真坏**(curl+moov 对账定谳, avcc 长度前缀逐样本比对)。
