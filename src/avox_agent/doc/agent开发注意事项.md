# Agent 开发注意事项

> 来源：通读《AI Agent 深度解析》(zh-CN, v1.2, 306 页, 10 章) 提炼的精练清单，面向 avox_agent 这类自研 Agent SDK 的工程实践。
> 全书核心公式：**Agent = LLM + 上下文 + 工具 + 约束/验证/纠正**（后三者 = Harness）。

## 0. 总纲：从"能跑"到"可靠"

- Demo 靠 LLM+上下文+工具即可跑；生产形态要长期可靠，必须补**约束**（限定能做什么）、**验证**（自动判断做对没有）、**纠正**（错了怎么办）。
- 行业重心已从"给工具让它能做事"转向"可靠地做事"——模型能力商品化，竞争优势在 Harness。
- 构建有效 Agent 三原则：**保持简单**（每多一层抽象都是调试盲区）、**保持透明**（可见轨迹=可调试+建立信任）、**设计好 ACI 接口**（Agent-Computer Interface，从 Agent 视角而非程序员视角设计）。
- 反模式示例：看不到退款政策（缺上下文）、不知道调哪个 API（缺工具）、编造退款结果（缺验证）、用户发现退款没发生（缺纠正）。
- 编排光谱：先单个 LLM 调用 → 需求可拆固定步骤用**工作流**（流程代码写死、攻击面限单节点）→ 需动态决策才用**自主 Agent**（必须设计停止条件：任务完成/输出 final_answer/无工具调用/最大轮次/错误超限，否则死循环）。
- 模型选择：选对模型比优化提示词更有效；绝大多数 Agent 需要支持**思考(Reasoning)** 的模型；别忽视**输出 token 速度**（每轮都要等输出完成，20 轮每轮慢 2s = 多等 40s）和多模态是否硬需求。

## 1. 上下文工程（决定能力上限）

### 1.1 KV Cache 是前置架构约束（全书技术密度最高，三条必记）

1. **系统提示词和工具定义一旦定下就字节级不变**——改一个空格，整段前缀缓存失效，延迟成倍、成本上升。
2. **动态信息永远追加到末尾**——时间戳/用户状态/路由提示作为新 user 消息追加，绝不拼进 system。
3. **用标准 API 消息格式，不自行拼接 "USER:/ASSISTANT:" 文本**——偏离训练格式削弱多步思考；把工具结果当 user 消息传入会误触发服务端清理历史思考链（"草稿纸被收走"）。

- 工具定义保持**固定顺序**：动态排序整段缓存失效，且对选工具能力几乎无收益。
- 别用**滑动窗口**裁剪历史——丢失关键工具结果，Agent 忘记已有成果、反复执行相同调用、错误率上升。
- KV Cache（模型内部优化）≠ Prompt Cache（API 服务层，跨请求复用相同前缀，直接关系到计费）：Anthropic 需显式 cache_control 断点、写入约 1.25x 加价、最小约 1024 token、TTL 约 5 分钟；OpenAI 自动缓存。
- 子 Agent 的提示词/工具定义/消息前缀要与父 Agent **字节级对齐**，才能命中服务商 Prompt Cache。
- 已有 avox_agent 实践：`routingHint` 追加到末条 user 消息而非 system（`系统提示词.md`），即本条规则 2 的落地。

### 1.2 状态栏 / 元信息注入（Context Distillation）

- 动机：上下文学习本质是**检索而非推理**——模型不擅长从原始记录归纳统计（"打过几次电话"不会自动被数出来）。把分散的隐式状态提炼成显式**键值对**（"衣物:9件(合格7 次品2)"，不用散文），贴近生成位置注意力最高。
- 三条可直接照做的经验：
  1. **状态栏用代码维护**，别让 LLM 批量统计（比不用还差）；20 行正则即可达标准答案级；实在要 LLM 也须逐条抽取+代码汇总。
  2. **删原始上下文前，先确认状态栏覆盖所有会被问的问题**——一条答非所问的状态栏是"假权威"，会把模型带偏（多跳交叉查询时准确率可断崖崩塌）。
  3. **状态栏准确率当一线指标盯**——模型几乎无条件相信状态栏，写错就原样进最终答案；数据必须来自可靠观测，不可来自可被污染的数据源。
- 状态栏最有价值的不是模型本可自己数出来的（那只是省力），而是它**根本无从推断的外部事实**——把"闭卷考试"变"随时查一眼真实世界"。
- 时间感：只给时间戳没用，要**"读数+操作手册"成对给**（时间紧就交付 / 慢调用要诊断 / 真墙就绕开）。工具调用计数器有效是因为"到顶就停"规则显然，节奏类判断则必须配策略。
- 实现：API 层以一条 user 角色消息插入上下文末尾（不改 system），`<agent_status>` 标签包裹；语义上是 Harness 注入，不是用户输入。
- 更新两种：频繁+长轨迹→**持久追加**（缓存友好但陈旧累积）；短轨迹→每轮替换。
- 状态栏常见构成：TODO 列表（放轨迹末尾，防 Agent 过分关注局部子任务、忘记原始诉求/核心约束）、事件的侧信道信息（精确时间/位置/距上次回复间隔）、环境当前状态（系统时间/工作目录/异常提醒"该工具已重复调用 N 次"）、可用能力清单（skill 元数据，变化频率最低）。实验数据：启用 TODO 平均 15 次迭代完成 vs 无 21 次；详细错误信息（类型+参数 JSON+调用栈+针对性修复建议）让错误场景找替代方案成功率 60%→95%。
- 注意力位置偏好：模型对**开头和结尾**信息回忆精度更高、中间易被忽略 → 关键信息放开头或结尾；第一个 token 吸收异常高的注意力（softmax 的数学必然，非模型缺陷）。

### 1.3 上下文压缩

- 压缩的两个价值：长度/成本约束 + **把"需思考才能得到的结论"变成"可直接检索的知识"**（猫舍 90 黑 10 白，提前写统计模型立即检索到）。
- 压缩对象是对话历史中的 tool results；System+Tools 永远不动。**接近阈值批量压，别每轮都压**（每压一次破坏一次缓存）。
- 压缩保留优先级：架构决策/关键约束**不得摘要**；已修改文件清单完整保留；验证状态(pass/fail)必须保留；未解决 TODO/回滚笔记必须保留；工具输出可删仅留结论。
- **标识符必须原样保留**：UUID/hash/IP/端口/URL/文件名/PR 号/commit hash——错一位后续工具调用直接失效。
- 上下文感知压缩（带 query + current context）效果最好（token 减 77%）；组合摘要优于个体摘要；对噪声直接删除、不做摘要。
- 压缩 vs 隔离：**隔离优于压缩**——把读大量文件/大范围搜索委派给子 Agent，只回传几百 token 结论，主上下文前缀完全不受影响（但子 Agent 任务描述必须自包含）。

### 1.4 提示工程

- 检验标准：聪明新员工读完提示词不知道该怎么做，Agent 也一样。
- **流程驱动（SOP 分步+每步异常处理）> 上百条零散规则堆砌**。消融实验：保留全部规则但打乱结构、拆散有序流程 → 成功率降 30%+，关键规则被跳过。
- 业务规则必须细化到可执行程度（"NEVER use percentage_based_one_time for refunds"），模糊规则行为极不稳定；业务规则是产品设计问题，产品经理参与，工程师只负责准确编码。
- 语气/风格影响表达有限；**信息组织方式影响巨大**。模型表现差先做消融逐项关组件，别整体重写。
- Few-shot：两三个精心挑选、覆盖边界情况的例子 > 十个大同小异；位置放 system 或伪造首轮消息；一旦确定保持字节稳定，**不逐请求动态检索"最相关"示例**（每次改写前缀缓存失效）。

## 2. 工具设计（手脚）

### 2.1 ACI 原则

- 粒度：整合功能相似+场景重叠的工具（三个 extract_xxx → read_document(file_type)）；**工具超 100 个时最先进 LLM 也易选错**。
- 通用优于专用：代码解释器（沙盒内装 sympy/pandas）> 十几个专用计算器；除非有安全/权限/性能理由（如 grep 各平台语法不一，仍要专用封装）。
- 描述的艺术：写清**"何时用"**（"需要实时信息或查找未知事实时"）而不仅是"能做什么"；**边界同样重要甚至更重要**——大多数调用失败是模型不知道"不能做什么"（"只能按文件名匹配，不能搜内容"），列出反例。
- 参数用**具体例子**代替抽象规范（"timestamp: RFC3339, 例如 2024-03-15T14:30:00Z"）；每个工具附 1-5 个真实调用示例（准确率 ~72%→90%）。
- **Agent 频繁选错工具时，优先检查工具描述而不是怀疑模型能力**；修正描述（边界不清/缺反例/参数含糊）投入产出比远高于换模型。

### 2.2 参数保真（最隐蔽的坑）

- 禁止**静默转换**（悄悄"修正"输入，如把中文弯引号转直引号导致 old_string 永远匹配不上）、**静默注入**（追加模型不知情的参数）、**静默截断**。
- 核心原则：**模型感知的世界与工具操作的世界不能存在系统性偏差**；确需规范化必须在描述中说明并回告模型。
- 截断必须显式可见（"已显示 1-200 行，共 5000 行，可用 offset 继续"）；大输出头尾各返若干行 + 完整存临时文件 + 引导 read_file。

### 2.3 工具安全（执行工具的设计核心）

- **约束优先于指导**：代码/权限强制"做不了" > 提示词"建议别做"；真正可靠的约束待在模型下面那层人工审查过的地基里。
- 服务端真值校验是最后守门员：关键操作（退款/取消）的政策事实绝不信模型自报参数（模型可能幻觉或被动注入操纵）；自报与真值不一致记录告警。
- 输入验证：路径遍历/命令注入/类型格式；**快速失败**——异常输入立即拒绝，不尝试"智能修正"。黑名单只是基础（禁 rm 可用 `$(echo rm) -rf /` 绕过），需语义解析理解命令意图。
- **Sidecar 机制**：轻量 LLM 与主模型流式并行、对工具调用起门控；**刻意只看结构化调用数据（工具名/参数），不看主模型自由文本**——防止注入话术被复述进思考过程骗过审查；危险操作放行前不会真正执行。
- **提议者-审核者（Proposer-Reviewer）**：独立第二视角。不同模型家族+能力相近（Haiku 审 Opus 跟不上）；底层规则约束完全一致（否则互扯皮）；审批失败把拒绝理由作为工具结果喂回轨迹、不盲目重试；适合不可逆/高影响操作。
- 事后验证要诀在**模态切换**（基于代码的文档→渲染成视觉检查排版），同一模态审查易陷相同盲区。
- 沙盒层级：**venv 不是沙盒**（只隔离包依赖）。OS 级（Seatbelt/seccomp）→ 容器（Docker）→ microVM（Firecracker）；任一之上都要资源配额（CPU/内存/磁盘/网络）。生产/不可信输入用容器甚至 microVM。
- 网络出口默认断网+按需白名单代理放行；**凭证文件根本不挂载进沙盒**（不可见即不可泄露）。
- 持久记忆跨会话防线：写入长期记忆的内容需与外部内容同等信任审查。

### 2.4 事件驱动与异步

- 核心矛盾：**训练同步 / 部署异步**——LLM 被训练成"发出工具调用后下一条必须是工具结果"，真实世界随时打断。
- 紧急事件（用户停止/监督指令/支付失败）→**取消式**：停止当前操作、清空队列、把事件追加轨迹末尾、立即重新调用 LLM。
- 常规事件→**队列式**：入队不打断，当前周期完成后一次性追加批量处理（批处理提效）。
- 打断工具执行需**占位符**修复配对（"工具正在后台执行，请优先处理新事件"）——否则 LLM 会**编造工具结果**（幻觉），因为训练时 99% 轨迹调用后紧跟真实结果。**只在真正紧急时才打断**。
- 批量事件模型常只关注最后一个 → 状态栏标记 `[未处理事件1/4]` + 末尾汇总提示。
- 事件建模四维：来源（谁）/渠道（方式）/内容（什么）/上下文（背景）。第三方消息不是用户发的，但 Agent 要理解它。
- 用轻量分类 LLM 作**事件路由器**按语义判定处理策略（"马上停下来"取消式 / "今天天气怎样"并行式 / "报告用中文发我"队列式）。
- 异步工具接口：把"启动"与"完成"解耦（initiate_phone_call 立即返回任务 ID + 状态，完成走事件通知），工具名称与描述要传达异步语义。

### 2.5 工具数量控制与主动发现

- 工具定义常占上下文很大部分（每个数百 token）；数量一多，全量注入很快撑爆上下文、选择精度崩、变更破坏缓存。
- **渐进式披露三层**（Skills 范式）：L0 元数据（name+description，仅数百 token 常驻）→ L1 完整 SKILL.md 按需加载（作 tool result 进轨迹）→ L2 子文档/脚本按需深入。description 写"何时用/何时不用"像**路由条件**而非功能介绍（缺反例→路由准确率明显下降、不相关任务频繁误触发）。
- 三种注入方式权衡：注入 system（指令遵循最强，但改 system 破坏缓存）→ 中间文件读取（不碰缓存，但弱模型识别指令差）→ **末尾 meta + 专用 Skill 工具按需加载**（生产方案，路由与执行分离、增量发送——每个 skill 首次出现才发送，稳态增量零）。
- 主动工具发现：Agent 执行中意识到能力缺口时，用自然语言声明"我需要什么能力"，系统按需匹配注入（MCP-Zero：~2800 工具比全量注入省约 98% token）；弱模型在上百工具场景也靠它保持可用。
- KV Cache 微调（动态加载的代价）：system 固定（角色+基础工具约 2K token）+ 状态栏维护工具名列表（约 200 token）+ 新工具完整 schema **作为 user 消息追加末尾**——前缀稳定、缓存命中率约 95%。注意 schema 只在被发现那一轮追加一次，此后固定在原位置，不是每轮重新搬运。真正导致重算只有两种：Prompt Cache TTL 过期、修改/移除/重排已加载工具集。
- MCP 信任边界（接第三方工具=新攻击面）：①**工具描述投毒**（description 原样进上下文，恶意服务器可夹带指令，注入载体从用户输入换成工具定义且每次会话生效）②恶意/被劫持服务器（供应链攻击）③同名工具遮蔽（诱导敏感参数路由到攻击者）④凭证管理（OAuth token 被诱导用于非预期操作）。缓解：接入前把 description 当不可信输入审计、锁定服务器版本拒绝静默更新、最小权限凭证（范围+有效期，不复用高权限个人凭证）；运行时靠 Sidecar 独立审查。
- 5 个 MCP 服务器可引入约 55K token 工具定义；Cursor 方案"工具名索引常驻 + 定义按需查"总 token 降 46.9%。

### 2.6 感知工具与协作工具

- 感知工具共性挑战：返回信息量远超处理能力（一次搜索数万字符）。应对：输出超阈值（如 10000 字符）时基于当前查询意图自动压缩；搜索返回**结构化候选列表**（标题/位置/摘要）而非全文拼接；结果多时分页/游标，默认返前若干条+注明总数，由 Agent 决定是否翻页。
- 读取类支持 offset/limit；超阈值截断必须显式可见。
- **只读红利**：感知工具不改外部世界 → 结果可安全**缓存**（相同查询直接复用）+ 可放心**并行**；执行工具必须严格控制调用顺序与副作用。
- 多模态输出形态：直接返回图像（保留布局但费 token）vs OCR/解析转文本（精简但可能丢空间结构如表格行列）；布局敏感内容（UI/复杂表格）保留图像。
- 协作工具：子 Agent 上下文传递四策略（**最小化 → 手动筛选 → 自动裁剪 → LLM 生成上下文对象**，后者适合复杂任务，可含隐私规则"不传递支付信息"）；子 Agent 提示词四要素（角色定义/上下文来源标注 `[FROM_MAIN_AGENT]`/任务边界/输出格式标准化——统一 JSON 降低主 Agent 解析负担）。

## 3. 记忆与知识

### 3.1 用户记忆

- 记忆提取三特征：**选择性**（不记临时信息）、**抽象化**（提炼通用偏好）、**结构化**（标记类型）。
- 四种格式（按成本↑）：Simple Notes（便宜但丢关联）→ Enhanced（叙事完整但更新难、段落越长嵌入越糊）→ JSON Cards（刚性分类，跨维度信息表达不了）→ **Advanced JSON Cards**（backstory/person/relationship/时间戳，可消歧多个"张医生"）。关键少量数据用 Advanced，大量事实用 Simple，生产走混合。
- 进阶：把记忆写成**可执行代码**（带类型对象+函数编码约束），聚合统计/冲突检测/约束执行由确定性解释器而非 LLM 心算——"去年出几次国"检索式记忆仅 6-43% 正确率，代码形式 ~99%。
- 冲突检测用版本化：当前地址只留最新，工作经历保留历史；记忆库需定期"睡眠整合"（异步后台整理、去冗余、相对日期转绝对日期），否则退化为低信噪比堆积。
- 隐私：用**本地模型**做 PII 检测与脱敏（日志本身含敏感信息，发云端脱敏违背初衷）；超高吞吐用正则快速过滤 + LLM 深挖混合。

### 3.2 RAG

- 分块：**结构感知切分**（按章节/段落）为生产默认；块 256-1024 token、重叠 10-20%；分块切断代词/时间/实体上下文是固有缺陷。
- 混合检索 = 稠密 + 稀疏（BM25 精确关键词）+ **神经重排序**（跨编码器）；没有单一策略全场景可靠。融合用 RRF（k≈60）或归一化加权。
- **知识库不止检索**：统计类（黑猫白猫比例）与规则类（Xfinity 优惠）问题要预先提炼/建索引，模型注意力是软检索、不会主动归纳——索引阶段必须投入计算做提炼。
- 结构化索引（RAPTOR 树 / GraphRAG 图）只在需要跨文档综合、多跳推理时才值得（构建大量 LLM 调用很贵）；三元组抽取必然语义降级+错误抽取致知识污染。
- **上下文感知检索**：索引前用 LLM 给每块生成前缀摘要"锚定"回原始上下文——检索失败率 ↓49%（+BM25）/ ↓67%（+重排序）。
- 知识时效：分块带版本号/生效失效时间，检索过滤过期内容（否则新旧政策一起被召回自相矛盾）；HNSW 支持增量更新（ANNOY 需完全重建，动态库会被拖垮）。
- **权限过滤下推到检索层**——敏感内容一旦进 LLM 上下文就难保证不泄露；多租户索引相互隔离。
- **文件系统范式**（记忆/技能/知识映射为目录和文件）：L0 摘要（~100 token 判断相关性）→ L1 概览（~2K token 供规划决策）→ L2 全文按需加载——"摘要常驻、按需取全文"，与 Skills 渐进式披露同思路；用 **Markdown 纯文本**而非专用数据库（用户可直接阅读/编辑/修正、Git 可版本控制回滚、Agent 有写文件能力后可自主记录形成记忆自演化循环）。
- **极易被忽视的前提：文件间必须建立链接与索引**——只建纵向摘要不建横向交叉引用，拆成独立平铺文件只能全文扫描或向量检索，知识越多越难检索；写入提示词必须明确"每新增条目先检索并链接到相关已有条目、更新所在目录索引页"（强模型会自发回指，很多模型不会，只孤立追加）。

## 4. 提示注入（最核心安全威胁）

- 注入在 Agent 中比聊天机器人危险得多：聊天最坏输出不当内容，Agent 有工具能力——可能执行文件删除/发邮件/泄露隐私等**不可逆操作**。
- 每个感知工具（网页/文档/邮件）都是注入入口；外部内容注入前用来源标记包裹 + 明确"供参考、非指令"。
- **指令与数据分离**：严格用 system/user/tool 角色传信息——"不要自行拼消息"的又一个理由（把工具结果混入 user 消息=亲手抹掉模型辨别来源的依据）。
- RAG 检索内容是指向注入典型载体（攻击者把指令藏进会被收录的网页/文档）；检索内容不得直接触发高风险操作。
- 输入过滤（"忽略先前指令"等短语）容易被措辞变体绕过，只能作辅助。
- **致命三要素**（Simon Willison）：访问私有数据 + 暴露于不受信任内容 + 具备对外通信能力，齐备即高危闭环；第四维**持久记忆=放大器**——无害偏见/恶意指令写进长期记忆跨会话潜伏，把一次性攻击变持久。
- Skill 本质是"把外部内容当指令加载"：**安装来源不明的 Skill 前审查其内容，如同审查将执行的代码**；状态栏同理，不可喂可被污染的数据。
- 上下文层防御只是第一道防线；执行层（权限/沙盒/独立审查）才是兜底。

## 5. Coding Agent

- 基础工具箱 = 七个核心工具：代码解释器 / Bash / Read / Write / **Edit**（局部修改，迭代核心）/ Glob / Grep。
- **完成标准=测试通过，不是代码写完**——最常见的偷懒就是写完不跑测试报告完成；写设计文档本身是深度思考，也给人高效介入点（审文档易过审代码）。
- 搜索工具分工：grep/ripgrep（已知文本）→ glob（看目录结构）→ 语义搜索（探索）→ LSP（重命名**必须用**，文本搜索会命中注释/字符串）。从粗到细：语义→正则→符号追踪调用链。
- 文件编辑方案："旧字符串→新字符串"最稳起步；大段改动用首尾匹配更经济；行号方案仅在 IDE 深度集成（实时维护行号映射）下可靠，否则行号漂移失效。
- 上下文精细管理：文件读取按行号范围读片段并**附加行号标注**（模型可精确引用"src/main.py 第42行"）；命令输出头尾截断+完整存临时文件；文件写入完成自动跑 linter，结构化错误作为返回值（即时反馈）。
- 环境信息（工作目录/git 分支/变更概览）动态注入上下文末尾，不硬编码进 system（KV Cache）。
- Sessionless/状态持久化：文件系统状态天然持久（workspace 挂持久存储）；进程状态（cwd/环境变量/后台任务）记录到工作区文件，唤醒按记录重建；闲置超时销毁前序列化。
- **错误恢复分类学**（四层）：
  - API 层：限流/超时/断连——**可重试**（先分类再计数：值不值得重试 vs 要不要重试）。
  - 工具层：幻觉调用/参数畸形/执行异常——原样重试无意义，必须改输入或策略。
  - 上下文层：溢出/压缩失败/轨迹结构损坏（调用缺配对结果）。
  - 控制流层：死循环（反复同样操作）+ 死亡螺旋（错误恢复逻辑自身又调 LLM、再错、连锁）。
- 检测：重复调用指纹（"工具名+参数"哈希）+ 连续失败计数（每条恢复路径独立计数器）；**流式连接最危险是静默卡死**（连接成功但数据流停），需独立空闲看门狗超时杀挂起流并重试。
- 恢复分级升级：①静默重试（指数退避+随机抖动；**后台辅助调用失败直接放弃**，否则挤占主链路配额形成重试放大）→ ②降级/接续（输出触顶先提升上限、仍不够追加续写指令；主模型过载降级备用模型）→ ③暴露用户（自动手段用尽才呈现，附已尝试动作）。
- 工具层错误不终止会话，**把错误变成模型输入**（结构化错误+约束提示），喂回的错越具体成功率越高。
- 终止：每条恢复路径设**熔断上限**（阈值来自产线数据而非拍脑袋）；全局最大迭代轮数+会话预算上限+连续失败升级人工。错误路径上禁用会再次调模型的副作用逻辑。

## 6. 评估（可靠的前提）

- **评估对象是"模型+Harness"组合体**，不是模型。表现差先用 **model swap**（固定 Harness 换模型）区分瓶颈：换强模型不涨→Harness 问题；换弱模型大跌→模型问题。消融=关 Harness 组件定位内部。
- 评估环境五要素：数据集（初始态+目标+可选参考解）、环境状态（可重置）、工具接口（**原子操作而非高层抽象**，迫使 Agent 规划）、Rubric、执行协议（终止条件）。
- 人机交互评估要点：**渐进式信息透露**（传统 benchmark 一上来全盘托出需求，现实用户只说"我的航班好像有问题"）；用户模拟 LLM；双重验证（DB 最终状态 + 对话关键词）+ 二元奖励。
- 数据集防泄漏：答案唯一性 + 专门创建的附件文件 + 参数化生成 + **canary GUID**（Terminal-Bench：模型能输出含 GUID 即说明基准已泄漏进训练集）。**评估题必须与训练数据严格隔离**。
- LLM-as-a-Judge：Rubric 四准则——基于专家指导 / 全面覆盖（含陷阱 Pitfall）/ 权重 + **否决项**（客服中幻觉=否决维度，与质量正交）/ 自包含可操作。
- 防长度偏差：Rubric 显式惩罚冗长、配对比较控制长度相近、定期审计评分与长度相关性。
- **校准前置**：先建人工金标集（100-200 案例），评判模型与人类一致率 kappa>0.7 才大规模用；评判模型或 Rubric 每次更新都要重校。
- 同源模型问题（Goodhart）：Agent 与评判同家族，Agent 学会利用评判偏好 → **多源异构评判**（Agent 用 Claude、评判用 GPT+Gemini）。
- 指标区分：**Pass@k**（至少一次成功=能力天花板）vs **Pass^k**（k 次全部成功=稳定性/回归）vs **Best@k**（开放任务质量上限）。60% 单次成功率：Pass@5≈99% 而 Pass^5≈7.8%——混用会误判。
- 统计显著性：分差小于噪声带宽（≈p±2√(p(1-p)/n)）不做切换决策；每个配置跑 3-5 次不同种子取均值报波动；**配对分析**（同批任务逐题比胜负，McNemar 思路）比独立成功率相减灵敏得多；多假设并行要收紧置信门槛（Bonferroni 式）+ 独立复现才采信。
- 可观测性：trace/span 树（一次任务一条 trace，每次 LLM/工具调用一个 span）；OpenTelemetry + OpenInference 标准；异步采集不拖慢响应。**生产失败轨迹→脱敏→沉淀为评估集回归用例**（评估集从静态集合变成随产品演化的活资产）。
- **成本三层次与优化**：①模型推理——两个被忽视的放大器：**上下文累积效应**（第 1 轮 1000 + 第 2 轮 2000 + 第 3 轮 3000 = 6000，不是 3×1000；KV Cache 复用保前缀稳定可降 30-60% 输入成本）和**思考 token**（不展示但计费，每轮多 500-2000 token 成本翻 3-5 倍）；②工具调用——外部 API 费 + **工具返回注入上下文的 token 费**（一次搜索返回 2000-5000 token 且在后续每轮重复计费）；③基础设施。**成本优化核心不在选便宜模型，而在控制轮次和上下文增长**。
- 设**每任务成本上限**——Agent 陷入循环或探索过深时自动终止，防单次任务异常高额费用；按任务类型/模型/用户维度追踪 token 和费用。
- 内部评估基础设施：消融总开关（**启动路径极早期注入**）；AB 测试（多臂而非二元；**机制指标 ≠ 目标指标**——"计划文件更短"是机制，"会话级成本降"才是目标；护栏指标防底线变差）；双层特性开关（编译时物理移除 + 运行时服务下发、本地缓存、宁可读稍旧不能阻塞启动）；提示词敏感性（可确定性渲染 + 版本化快照 + **每次提示词变更跑回归像 CI**）。

## 7. 多 Agent

- **何时优于单 Agent 的唯一判据：协作是否引入单个 Agent 生成时无法获得的新信息。**
  - 辩论/自我审查=无新信息，无效甚至有害（GPT-4 无外部反馈自我审查准确率反降；LLM 不会自我纠正推理）。
  - 代码执行反馈/渲染截图/工具验证=有新信息，显著提升（视觉反馈让 Claude 3.5 Sonnet 26.4%→51.9%）。
- 成本红线：多 Agent token 约为普通对话 **15 倍**，收益必须覆盖数倍到数量级开销。
- 对等协作（2-3 角色迭代互反馈）解"过早终止"，三类：**偷懒式假完成**（写完代码没跑测试就报完成）/ **过早放弃**（一条路走不通就宣布办不成）/ **假成功**（以为办成实际闭环没走完，如对方口头同意退款但用户还需在 App 确认一步）。共同根源：在验证之前"完成"只是模型的一句宣称。**Loop 工程的瓶颈在验证器不在模型**——由验证器（测试/渲染/工具反馈）判定何时可停，而不是模型自己说停就停。
- 提议者-审核者是核心范式（Reviewer 渲染执行结果+独立评估+结构化改进建议）；**不能一个 Agent 自己生成再自己审查**——审查若不引入新信息就只是"让模型再想一遍"，GPT-4 无外部反馈自我审查准确率反而下降。
- 共享 vs 不共享上下文：共享=2-3 角色串行接棒、信息零损耗但膨胀快，**超窗口约 50% 就切不共享**；不共享=并行/隔离，子 Agent **返回结构化摘要而非全量轨迹**（Manager 上下文随子任务数缓慢线性增长而非爆炸）。
- 管理者模式：Manager 把子 Agent 当工具；**规划者是系统瓶颈——把最强模型和最精心设计的提示词分配给 Planner**，而不是平均分配。
- 文件系统分区（数据平面）：私有工作区（试错留存，主上下文精简）/ 共享空间（产物交换，并发冲突高发处）/ 外部挂载（只读为主）/ 系统内置（全局只读）。并发冲突与信息泄露多源于区域混置。
- 并发控制：**乐观锁**（每文件版本号，写时校验，防止基于过时状态决策）+ **工作副本隔离**（每 Agent 独立分支/worktree，冲突收敛到合并点）——"隔离优于压缩"的同源应用。
- 失败模式：**错误级联放大**（术语 Agent 把 "reasoning" 译错 → 后续 Agent 沿用 → 校对因"一致性"判高质量——一个错误经多 Agent 因一致性获得更高可信度）。打断链靠**交叉验证**（独立视角只看原始证据和最终结论，不看前序思考）+ **确定性工具反馈**（单测/编译器/DB 是最可靠的"断链器"）。
- 控制平面三件套：消息总线（结构化信封：发送者/目标/消息类型/负载；点对点连接数随 Agent 数平方增长）；状态查询（推送状态机：已提交/执行中/需输入/已完成/失败 + 超时心跳）；执行终止（**优雅终止优先**，子 Agent 定期检查终止信号；级联终止有竞态，主 Agent 用锁/幂等保证仅结算一次）。

## 8. 自我进化 / 学习（简要）

- **学习不会自动发生，必须显式设计**——注意力是检索而非归纳，无限上下文不带来自动学习，反而因上下文腐化检索变差。
- 三种范式分工：后训练固行为（改权重，贵而慢）/ 上下文学习快速迭代（会话结束即失）/ **外部化学习**（沉淀到文件/知识库/工具——最易被忽略的一条路径）。RAG 记事实、后训练固行为、ICL 快速迭代。
- 产物判断：纯事实→知识库条目；频繁且参数复杂→代码工具；常变且涉策略→Skill 文档。
- 从失败中学习：错误模式库 + 负面规则（"不要再用 X 做 Y"）；Reflexion 用语言反思存入情景记忆、不改权重。
- **记忆投毒是最内生的攻击面**：任务中接触的网页/工具输出未审查就沉淀为长期记忆 = 攻击从一次性变持久。防御三层：写入前审查+来源标记；**经验与指令通道隔离**（检索出的经验以"参考资料"而非"命令"身份注入）；检索时注入检测。
- 工具生成（Agent 写代码造新工具）：生产系统把最多算力压在**测试验证环节**，有验证闸门（回放+评判器确认）才入库——有 bug 的工具被反复调用，危害远大于一次性推理错误。
- 长任务跨会话续跑：状态放**文件**不放上下文（progress.json），功能清单用 **JSON 而非 Markdown**（结构化格式更稳定读写），所有功能项 `passes:true` 才算完成；Initializer Agent 首轮拆任务清单+建骨架+初始 git commit，后续 Coding Agent 从进度文件+git log 恢复现场。任务一旦超半小时，崩溃恢复不是可选项而是必选项。
- 系统提示词自动优化：靠边界案例（edge cases）+ Coding Agent 生成精确 diff + 人类专家审核（保留人工把关、可解释可追责）；验收 = 原保留任务集表现不退化 + 边界案例集正确率提升（新规则不破坏既有正确行为）。

## 9. 多模态与实时交互（简略）

- 语音三范式：级联（ASR→LLM→TTS，模块清晰但延迟累积、情绪韵律丢失）→ 端到端 Omni（保留非文字信息但仍靠 VAD 猜轮次）→ 全双工（微轮次约 200ms 持续听+说，消解轮次本身）。主线=**摆脱 VAD 对轮次的猜测**。
- 延迟预算按排队定律（总延迟≈空载×1/(1-ρ)）；VAD 等待+ASR 转录期间 LLM 完全闲着是最大浪费点；全链路流式化（边听边转/按标点切句输出/句级 TTS 流式合成）可压到 600-800ms。
- **快慢解耦**（2026 主流）：交互模型只维持对话在线，深推理/工具调用委派后台更强模型——交出的不是孤立查询而是整段对话上下文，结果流式回传、挑不打断用户的时机织入；快模型**绝不在状态摘要确认完成前说"办好了"**。语音实测延迟 ~0.58s vs 单模型 8.64s。
- 语音合成更像人：把"哪里停顿/什么语气"的决策权交给主 LLM，输出文本+控制标记（`[THINKING]`/`[SEARCHING]`/`[EMO:happy]`/`[SPEED:0.8x]`），TTS 当多模态生成器；voice cloning 数十条参考语音按标记选择，几周即可落地。
- Computer Use 三关键维度：动作空间 / 视觉定位 / 模型架构。定位三路线：DOM/A11y 结构化索引（最精确稳定，仅限网页）→ 视觉标注 Set-of-Mark（界面元素编号，模型选编号=选择题，免分割模型漏检误检）→ 纯坐标预测（需海量 GUI 截图+位置数据训练）。
- **坐标缩放坑**：模型对坐标的理解依赖训练分辨率，必须按**宽高比**选目标分辨率（2560×1440 选 FWXGA 1366×768，而非硬拉伸进 4:3 的 1024×768），否则坐标系统性偏移。
- 观察接口 AOI（重设计观察而非动作接口）：帧间关键帧捕获（像素门跳帧，静止画面近零成本）+ 音量门控 ASR + **把帧叙述成持久文字**（"刚弹出的提示说日期改到 4 月 28 号"——真正起作用的不是选哪几帧，而是文字留存量；即使原图被清理出上下文，文字记忆仍在）。8 个模型免重训提升 +17~+48 个百分点。注意按模型逐个挑部件，塞太多图像 token 反而挤占推理。

## 10. 通用工程原则（横切）

- **约束优先于指导；验证优先于宣称；隔离优于压缩；数据/环境 > 算法。**
- 延迟：排队定律——总延迟 ≈ 空载 × 1/(1-ρ)，生产 ρ 0.5-0.8 → 2-5 倍，服务器不能长期高负载。
- 快慢解耦跨场景可迁移（语音快对话+慢军师 / Computer Use 快语音+慢操作+纯文本契约 / 机器人长程规划+快执行）；判断值不值得请"慢军师"：瓶颈在"想不想得到"还是"来不来得及反应"。
- 用消融与对照实验做数据驱动决策，别靠直觉；新模型公开基准更好不意味着在你任务上更好，只有自己评估集能定。

## 11. 对照 avox_agent 现状（自查清单）

**已做对**：system prompt 骨架外部化 + 动态能力目录（目录轻/schema 重按需）；`routingHint` 追加末条 user 消息保 KV Cache 前缀稳定；skills 渐进式披露（description 为路由主信号）；`read` 带 offset/行号、`grep` 定位+分段读、`run_code` 兜底；cmd/skill/helper 统一 `ToolRuntime` 管理；上下文压缩按上一次请求的真实 `promptTokens` 判阈值（不是字符估算），压缩不删历史只在投影层遮蔽，切点保证工具消息配对平衡。

**需警惕 / 可改进**：
- 工具描述：每条工具补"何时用 + 边界/反例 + 参数示例"，别只写能做什么；选错工具先查描述。
- 参数保真：检查是否对模型输入做了静默规范化；任何截断必须显式可见。
- 错误恢复：是否已有重复调用指纹/连续失败计数/熔断上限；SSE 流式连接是否有空闲看门狗防静默卡死。
- 评估：`runSkill`/`run_code` 产生的轨迹是否回流成回归用例；有无消融开关、提示词版本快照+变更跑回归。
- 记忆：是否跨会话持久化用户偏好；若做，注意外部化存储 + 写入前审查防记忆投毒。
- 事件/异步：SSE 已有；打断处理（占位符修复配对）是否实现，避免模型编造工具结果；批量事件加状态栏标记。
- 多 Agent：目前单 Agent 为主；若引子 Agent，记住"返回结构化摘要 + 隔离优于压缩 + 规划者配最强模型"。

## 12. 常见反模式速查（排查用）

1. system 里嵌时间戳/动态内容 → 整段缓存失效、成本上升（应追加到末尾或用工具获取）。
2. 自拼 "USER:/ASSISTANT:" 纯文本消息 → 偏离训练格式、破坏多步思考；工具结果误当 user 消息触发思考链清理。
3. 滑动窗口裁剪历史 → 丢失关键工具结果、Agent 忘记已有成果、反复执行相同调用。
4. 动态调整工具顺序 / 逐请求动态选 Few-shot → 缓存持续失效且选工具能力几乎无收益。
5. 规则堆砌不流程化 / 业务规则含糊 → 成功率降 30%+、行为不可预测（应 SOP 分步+产品经理细化）。
6. 工具描述只有"能做什么"没有"何时用/不能做什么/示例" → 选错工具、调用错误率 +45%。
7. 工具静默截断/静默转换输入 → 模型基于不完整或失真信息下判断，且无法诊断。
8. 用 LLM 维护状态栏/批量统计 → 比不用还差；状态栏答非所问 → 假权威带偏模型。
9. 压缩丢标识符（UUID/commit hash/URL/文件名）→ 后续工具调用全部失效。
10. 每轮都压缩 / 高频破坏缓存 → 应在上下文接近阈值时批量压。
11. 自主 Agent 无停止条件 → 死循环/过度执行（部署前沙盒测试+护栏+人机检查点）。
12. 工具调用失败盲目原样重试 → 先分类：限流/超时可重试，参数错/权限不足必须改输入。
13. 打断工具执行不给占位符 → 模型编造工具结果（幻觉），只在真正紧急时才打断。
14. 批量事件只处理最后一个 → 状态栏标记 `[未处理事件1/4]` + 末尾汇总兜底。
15. 接第三方 MCP 不审计 description → 工具描述投毒/凭证泄露（接入前当不可信输入审计）。
16. 用 Pass@k 当稳定性证据 → 混用误判（验证稳定性用 Pass^k，探索天花板用 Pass@k/Best@k）。
17. 多 Agent 辩论/自我审查无外部反馈 → 无新信息、无效甚至有害（有效性=是否引入新信息）。
18. 网页/工具输出不审查就沉淀进长期记忆 → 记忆投毒跨会话潜伏（写入前审查+来源标记+检索时注入检测）。
